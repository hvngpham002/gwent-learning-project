# 2026-04-24 Gwent Overhaul Plan

This directory is the planning source of truth for rebuilding the current game implementation into a deterministic, data-driven Gwent engine that can support:

- the current card set and any future card set;
- a card/deck authoring workflow;
- a deck builder;
- human vs AI, player vs player, and AI vs AI modes;
- large-scale simulations and future machine-learning experiments.

This is a plan only. It intentionally does not prescribe immediate code changes.

## Assumptions

- No blocking clarifying questions. The plan proceeds with conservative defaults.
- The current app should remain playable during the migration.
- The rulebook in `docs/gwent-rules.md` remains the rule authority.
- The existing audit findings under `audit/` are treated as known defects, not isolated bugs to patch one by one.
- Future card population should not require editing rule code unless a new ability type is introduced.
- The project can stay in React + TypeScript + Redux Toolkit, but the game rules should move into a pure TypeScript core that does not depend on React or Redux.

## Diagnosis From The Audit

The current code works for a limited Northern Realms mirror match, but the audit shows that its foundations are too coupled for the requested future:

| Problem cluster | Audit evidence | Architectural consequence |
|---|---|---|
| Impure and non-idempotent state transitions | `R-001`, `F-5.19`, `F-6.4` | Simulations, tests, replay, and ML need deterministic transactions. |
| Component-level orchestration duplicates reducer truth | `R-008`, `F-6.2`, `F-6.3` | Game end and round end need one authoritative resolver. |
| Card identity and zone ownership are weak | `R-004`, `R-011`, `R-012` | Spies, Decoy, Medic, Scorch, replay logs, and ML traces need stable card instances and controller metadata. |
| Rules are split between UI, thunks, reducers, helpers, and AI heuristics | `R-005`, `R-006`, `F-5.17`, `F-8.1`, `F-9.2` | Human and AI must consume the same legal moves and action resolver. |
| Card content is hardcoded and incomplete | `F-2.1` through `F-2.7`, `F-7.*`, `F-10.4` | Deck builder and future cards require a catalog, validator, image conventions, and import/export. |
| Effects are represented as booleans or shadow arrays | `R-003`, `R-009`, `R-010` | Rule effects need explicit sources, scopes, owners, and lifetimes. |
| Async UI state can race rule execution | `R-002`, `R-007`, `F-4.10`, `F-4.11`, `F-6.3` | UI animations and timers must observe engine state, not drive rule state. |

## Target Architecture

The overhaul should create a pure game engine that owns rules, legal moves, random choices, and state transitions. React and Redux become adapters around that engine.

```text
src/
  game/
    catalog/              # card, leader, deck, faction schemas and validators
    core/                 # pure engine, no React, no Redux
      state/              # match state, zones, seats, card instances
      rules/              # legal moves, action resolution, ability registry
      scoring/            # single strength pipeline
      rng/                # seeded RNG interface
      events/             # event log and replay support
    adapters/
      redux/              # store slice around core MatchState
      ui/                 # selectors/view models for React
      ai/                 # bot policies consuming legal moves
      simulation/         # headless match runner
  data/
    catalog/              # source card JSON/TS packs
  tools/
    cards/                # validation/import/export helpers
```

### Core Principles

1. One action enters the engine, one transaction comes out.
2. Every rule path is seat-neutral. There is no permanent "AI is opponent" assumption.
3. Legal moves are generated by the engine and used by human UI, bots, PvP, and simulations.
4. Cards have stable source IDs and runtime instance IDs. Rule state refers to instances.
5. All random choices use an injected seeded RNG.
6. Effects have source, owner, target scope, and expiry.
7. The UI can select, animate, and confirm actions, but it cannot invent rule outcomes.
8. AI evaluation can be heuristic, search-based, or learned, but it must choose from legal moves.

## Cluster Roadmap

| Cluster | Goal | Phases |
|---|---|---|
| A. Baseline and safety net | Freeze current behavior, create regression fixtures, establish audit-driven acceptance gates. | 0 |
| B. Data foundation | Replace hardcoded deck assembly with validated card catalog, image conventions, card authoring, and deck presets. | 1-2 |

| D. App migration | Connect React/Redux to the engine and restore playable human vs AI with current cards. | 8-10 |
| E. Content and game modes | Build deck builder, card studio workflow, PvP, and AI vs AI on top of the same engine. | 11-12 |
| F. Simulation and ML | Add headless simulations, observation/action interfaces, logs, training baselines, and evaluation. | 13-14 |
| G. Cleanup and hardening | Remove legacy paths, close audit findings, document extension process. | 15 |

## Orchestrator Workflow

This chat instance acts as the orchestrator.

1. The orchestrator picks the next phase and issues an implementation spec.
2. A separate implementation instance executes that phase only.
3. The implementation instance reports back using the report template in [handoff-workflow.md](handoff-workflow.md).
4. You relay that report here.
5. The orchestrator compares outcome against this plan, updates the next spec, and pivots if needed.

Each phase should be small enough to review. Phases may be split if an implementer uncovers risk, especially in Cluster C.

## Key Non-Goals

- Do not attempt to fully populate every official card before the engine is correct.
- Do not train ML before legal moves, deterministic simulation, and event logging exist.
- Do not add networked PvP until local PvP and seat-neutral engine paths work.
- Do not patch human/AI divergences one by one if the phase should instead remove the duplicate path.

## Open Decisions To Revisit

- Whether card catalog source files should be JSON, TypeScript, or both. The plan defaults to JSON-compatible data plus TypeScript schema validation.
- Whether in-app Card Studio writes only to localStorage/exported JSON or is paired with a local dev server file-write endpoint. The plan defaults to export/import first.
- Whether multiplayer starts as local same-device PvP or networked PvP. The plan defaults to local same-device PvP first.
- Whether ML uses an external Python environment later. The plan keeps TypeScript simulation logs stable so Python can consume them later.
