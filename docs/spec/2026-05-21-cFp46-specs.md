# cFp46 Specs: Glicko Rating Layer For Benchmark Artifacts

## Summary

`cFp46` starts the Batch B evaluation-ladder path after cFp45 paused further
hand-tuned `legal-heuristic-v1` threshold work. It adds a deterministic,
research-local Glicko-style rating layer over existing public benchmark
`records.jsonl` artifacts.

This phase must not change AI behavior. It turns completed benchmark match
records into rating/RD reports so future policy changes can be compared with
uncertainty instead of only raw win/loss totals.

## Research Grounding

Use the Batch B decision note as the controlling project decision:

- Ratings are post-engine evaluation infrastructure.
- Raw fixed-suite match records remain the source of truth.
- Ratings must report uncertainty/RD and sample counts.
- Do not collapse policy, deck, faction, and suite context into one unlabeled
  scalar.
- Glicko is a first local rating layer, not a gameplay policy, exploitability
  metric, hidden-state model, or product difficulty system.
- TrueSkill compatibility is future work; do not implement TrueSkill in cFp46.

Use the Glicko annotation for formulas and interpretation:

- default rating: `1500`;
- default RD: `350`;
- report interval: `rating ± 1.96 * RD`;
- draws score as `0.5`;
- high RD means the estimate is unreliable;
- low sample counts must remain visibly uncertain.

## Rating Inputs

The rating layer must read public artifact files only:

```text
docs/research/literature/ai/benchmark-results/<suiteId>/latest/records.jsonl
docs/research/literature/ai/benchmark-results/<suiteId>/latest/summary.json
```

Use only public `BenchmarkMatchRecord` fields:

- `suiteId`
- `benchmarkRunId`
- `matchupId`
- `seed`
- `mirrorGroupId`
- `mirrorIndex`
- `seats[seat].policyId`
- `seats[seat].deckPresetId`
- `seats[seat].faction`
- `winner`
- `resultBySeat`
- `status`
- `replayStatus`
- `stableFingerprint`

Do not read raw engine state, command logs, event logs, observations, hands,
decks, deck order, unsafe debug results, runtime card instance ids, or decision
trace payloads.

Ignore records that are not completed playable results:

- `status !== "completed"`
- `winner === null`
- either seat result is `"none"`
- `replayStatus === "failed"`

Count ignored/skipped records in the rating manifest/report.

## Rating Entities

Create ratings for multiple named scopes. Each scope must be separate in the
artifact output and report.

Required scopes:

1. `policy`
   - key: `policy:<policyId>`
   - label examples: `legal-heuristic-v1`, `legal-heuristic-v0`
2. `policy_deck`
   - key: `policy_deck:<policyId>|<deckPresetId>`
   - label examples: `legal-heuristic-v1 / official nilfgaard starter`
3. `policy_faction`
   - key: `policy_faction:<policyId>|<faction>`
   - label examples: `legal-heuristic-v1 / nilfgaard`

Optional if it stays simple:

4. `policy_matchup`
   - key: `policy_matchup:<policyId>|<matchupId>`
   - Useful for spotting matchup-specific uncertainty, but do not let this
     replace the three required scopes.

Do not produce a single global "AI strength" number without these labels.

## Glicko Algorithm Requirements

Implement Glicko-1 style rating-period updates in pure TypeScript.

Configuration:

```ts
rating = 1500
rd = 350
q = Math.log(10) / 400
rdFloor = 30
```

For cFp46, treat the whole input artifact as one rating period per scope. That
means:

1. Build all games for the scope from all eligible records.
2. Initialize every entity to rating `1500`, RD `350`.
3. Compute each entity's post-period rating/RD from all of its games in that
   artifact using the pre-period ratings/RDs for all opponents.
4. Clamp final RD to `rdFloor` minimum.
5. Do not apply inactivity RD growth in cFp46.

Use the standard Glicko-1 formulas:

```text
g(RD_j) = 1 / sqrt(1 + 3 * q^2 * RD_j^2 / pi^2)
E = 1 / (1 + 10^(-g(RD_j) * (r - r_j) / 400))
d^2 = 1 / (q^2 * sum(g(RD_j)^2 * E * (1 - E)))
r' = r + (q / (1 / RD^2 + 1 / d^2)) * sum(g(RD_j) * (s_j - E))
RD' = sqrt(1 / (1 / RD^2 + 1 / d^2))
```

Outcome scores:

- win: `1`
- draw: `0.5`
- loss: `0`

If an entity has zero eligible games, it should remain at default rating/RD and
be marked `unrated` or omitted from the scope output. Prefer omitting zero-game
entities from generated artifacts.

Determinism requirements:

- Sort input records by `suiteId`, `matchupId`, `seed`, `mirrorIndex`, and
  `stableFingerprint` before building games.
- Sort entities by scope, rating descending, RD ascending, key ascending.
- Stable pretty-print JSON keys the same way existing benchmark artifacts do.

## Artifact Output

For each rated suite, write:

```text
docs/research/literature/ai/benchmark-results/<suiteId>/ratings/latest/manifest.json
docs/research/literature/ai/benchmark-results/<suiteId>/ratings/latest/ratings.json
docs/research/literature/ai/benchmark-results/<suiteId>/ratings/latest/report.md
```

Required manifest fields:

- `schemaVersion: "benchmark-rating-artifact-v1"`
- `ratingSchemaVersion: "benchmark-rating-v1"`
- `suiteId`
- `sourceRecordsPath`
- `sourceRecordCount`
- `eligibleRecordCount`
- `ignoredRecordCount`
- `generatedAt` or deterministic placeholder if existing artifact style avoids
  wall-clock time
- file hashes for `ratings.json` and `report.md`
- hidden-info safety note

If timestamps would make artifact hashes unstable across reruns, do not include
wall-clock timestamps. Use the source benchmark run id or a deterministic
`generatedFrom` field instead.

`ratings.json` should include:

- config;
- source summary;
- entries grouped or filterable by scope;
- top entries per scope;
- warnings for small sample/RD interpretation.

`report.md` should include:

- source suite and record counts;
- Glicko config;
- top-level policy ratings;
- policy/deck ratings;
- policy/faction ratings;
- clear interpretation warnings:
  - "ratings are not exploitability";
  - "high RD means uncertain";
  - "do not compare ratings across different suite pools unless the report says
    they share a source";
  - "ratings are research-local and not product difficulty."

## Tests

Add focused tests for:

1. Glicko formula sanity:
   - a win raises winner rating and lowers loser rating;
   - a draw between equal default entities keeps both ratings close to 1500
     while reducing RD;
   - RD decreases after eligible games and never drops below `rdFloor`.
2. Batch/rating-period behavior:
   - order of records does not change output;
   - mirrored records are handled as separate games but do not leak seat ids.
3. Scope behavior:
   - `policy`, `policy_deck`, and `policy_faction` scopes are produced;
   - labels include policy/deck/faction context.
4. Artifact safety:
   - generated rating JSON/Markdown do not include hidden-info hazard strings;
   - output is deterministic across two builds from the same fixture.
5. CLI/artifact integration:
   - use a temporary output directory or pure serializer where possible;
   - avoid brittle tests that require spawning `tsx` on Windows if that is
     already a known local issue.
6. AI Lab:
   - metadata points at cFp46 after implementation;
   - AI Lab says ratings are artifact-backed and research-local, not browser-run
     or product difficulty.
