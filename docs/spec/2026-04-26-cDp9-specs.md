# Implementation Spec: Cluster D, Phase 9 - Batch Simulation Seed Suites And Diagnostics

## Goal

Add a bounded, deterministic batch simulation layer over the cDp8 single-match headless runner.

This phase should let the project run a small named seed suite, aggregate completion/failure metrics, and verify replay diagnostics across multiple AI-vs-AI games without React, Redux, browser APIs, filesystem writes, JSONL export, or ML training code.

The point is to make simulation reliability visible before building training data. A future ML export should start from this batch layer, but this phase should not produce a training dataset yet.

## Architecture Position

Current state after `cDp8`:

- legacy UI remains the default route;
- engine UI is opt-in through `?engine=1` or `VITE_ENGINE_UI=1`;
- the pure engine owns setup, legal moves, command execution, prompts, scoring, round resolution, game end, and deterministic RNG;
- `legal-heuristic-v0` selects from legal moves using hidden-info-safe seat observations;
- `src/game/sim` can run one current Northern Realms vs Nilfgaard AI-vs-AI match to completion;
- the single-match runner returns compact step logs, command logs, events, final state, summary metrics, and structured terminal statuses;
- replay currently checks final state essentials from a single command log;
- no batch seed suite, aggregate diagnostics, or per-suite completion summary exists yet.

Phase 9 should compose cDp8. Do not fork the engine, duplicate rule logic, or change the browser UI.

### 2. Add named seed suites

Add a small seed-suite model.

Suggested shape:

```ts
export interface SimulationSeedSuite {
  id: string;
  label: string;
  description: string;
  seeds: readonly (string | number)[];
  defaultMaxSteps?: number;
}
```

Add at least one exported current suite, suggested:

```ts
export const currentSimulationSmokeSuite: SimulationSeedSuite = {
  id: "current-smoke-v1",
  label: "Current catalog smoke suite v1",
  description: "Small deterministic NR vs Nilfgaard legal-heuristic-v0 regression suite.",
  seeds: ["sim-smoke-001", "..."],
  defaultMaxSteps: 300,
};
```

Seed criteria:

- include `sim-smoke-001`, because cDp8 verified it naturally exercises a Medic prompt;
- use a fixed ordered list, not generated random seeds;
- target 5 to 10 seeds total;
- pick seeds that complete under the default max step budget with current `legal-heuristic-v0`, unless a deliberately failing suite is added separately for tests;
- keep the suite fast enough for normal unit tests;
- document if any seed exists specifically for prompt or long-run coverage.

Optional registry helpers are fine:

```ts
export const simulationSeedSuites = {
  "current-smoke-v1": currentSimulationSmokeSuite,
} as const;

export const getSimulationSeedSuite = (id: string): SimulationSeedSuite | null => ...
```

Do not add a large tournament matrix in this phase.

### 3. Define batch input and output types

Add structured types for batch execution.

Suggested input:

```ts
export interface HeadlessSimulationBatchInput {
  suite?: SimulationSeedSuite;
  suiteId?: string;
  seeds?: readonly (string | number)[];
  maxSteps?: number;
  policies?: Partial<Record<SeatId, EnginePolicy>>;
  verifyReplay?: boolean;
  includeRawResults?: boolean;
}
```

Resolution rules:

- if `suite` is provided, use its seeds;
- else if `suiteId` is provided, resolve it through the suite registry;
- else if `seeds` is provided, use those seeds;
- else use `currentSimulationSmokeSuite`;
- `maxSteps` should prefer explicit input, then suite default, then the cDp8 runner default;
- `verifyReplay` should default to `true`;
- `includeRawResults` should default to `false`.

Suggested run record:

```ts
export interface SimulationBatchRunRecord {
  seed: string | number;
  matchId: string;
  status: SimulationTerminalStatus;
  winner: SeatId | "draw" | null;
  stepCount: number;
  commandCount: number;
  eventCount: number;
  roundsResolved: number;
  promptsResolved: number;
  averageLegalMoves: number;
  finalGems: Record<SeatId, number>;
  error?: SimulationError;
  replay?: SimulationReplayDiagnostics;
  fingerprints: SimulationRunFingerprints;
  rawResult?: HeadlessMatchSimulationResult;
}
```

Suggested batch summary:

```ts
export interface SimulationBatchSummary {
  suiteId: string | null;
  totalRuns: number;
  statusCounts: Record<SimulationTerminalStatus, number>;
  winnerCounts: Record<SeatId | "draw" | "none", number>;
  completionRate: number;
  maxStepRate: number;
  replayCheckedCount: number;
  replayFailedCount: number;
  promptRunCount: number;
  promptResolutionCount: number;
  averageSteps: number;
  averageCommands: number;
  averageRoundsResolved: number;
  averageLegalMoves: number;
  policiesBySeat: Record<SeatId, string>;
  seedsByStatus: Record<SimulationTerminalStatus, (string | number)[]>;
  failureCodes: Record<string, number>;
}
```

Suggested batch result:

```ts
export interface HeadlessSimulationBatchResult {
  suite: SimulationSeedSuite | null;
  seeds: readonly (string | number)[];
  runs: SimulationBatchRunRecord[];
  summary: SimulationBatchSummary;
}
```

The implementation can add fields, but keep the default batch output diagnostics-oriented and compact.

### 4. Keep default batch output hidden-info cautious

The default batch result must not include full `finalState`, full `commandLog`, full events, full observations, hand arrays, or deck order.

Use cDp8 single-run results internally, but collapse each run into a compact record by default. Only include the raw cDp8 result when `includeRawResults: true`.

Document this clearly:

- default batch output is suitable for diagnostics;
- raw results are useful for debugging/replay;
- neither default batch output nor raw command logs are a finalized hidden-info-safe ML dataset;
- future ML export still needs explicit redaction, observation hashing, action encoding, and reward design.

### 5. Implement replay diagnostics

Add a replay diagnostic helper that wraps cDp8 replay in a non-throwing result.

Suggested shape:

```ts
export interface SimulationReplayDiagnostics {
  checked: boolean;
  status: "passed" | "failed" | "skipped";
  commandCount: number;
  mismatches: string[];
  error?: string;
}
```

The helper should:

- skip when `verifyReplay` is `false`;
- call `replayHeadlessMatchCommands` with the run seed and command log;
- catch replay exceptions and report `failed`;
- compare final essentials:
  - phase;
  - winner;
  - gems;
  - round history;
  - current round;
  - command count if useful;
- not promise cross-version replay compatibility;
- not serialize full states into diagnostics.

If a non-completed run has a command log, replay diagnostics may still run and compare the final partial state. If that is awkward, skip non-completed runs and document the decision. The important rule is that replay failures are counted and do not abort the whole batch.

### 6. Add deterministic run fingerprints

Add lightweight fingerprints for diagnostics and determinism checks.

Suggested shape:

```ts
export interface SimulationRunFingerprints {
  commandTypes: string;
  eventTypes: string;
  summary: string;
}
```

The fingerprints should be deterministic across repeated runs of the same code and seed.

Acceptable implementation options:

- stable JSON over compact public-ish fields;
- a small local string hash helper over stable strings;
- command type sequence joined with delimiters for `commandTypes`;
- event type sequence joined with delimiters for `eventTypes`.

Do not use filesystem writes. Avoid Node-only APIs unless they are clearly isolated from browser-facing code. Do not include full card IDs from hidden zones in default fingerprints.

### 7. Implement batch runner

Add a public function, suggested:

```ts
export const runHeadlessSimulationBatch = (
  input: HeadlessSimulationBatchInput = {},
): HeadlessSimulationBatchResult => ...
```

The runner must:

1. Resolve the seed list deterministically.
2. Run `runHeadlessMatchSimulation` once per seed.
3. Continue after per-seed failures.
4. Build compact per-run records.
5. Optionally run replay diagnostics per seed.
6. Aggregate status counts, winner counts, prompt counts, replay failures, failure codes, and averages.
7. Return one deterministic in-memory result.

Batch error behavior:

- invalid suite id can throw a clear programmer error or return a structured empty failure result, but tests must pin the chosen behavior;
- empty seed list should be handled explicitly, not accidentally reported as a successful suite;
- policy exceptions from individual runs should remain per-run `policy_failed` statuses, not batch-level crashes;
- replay diagnostic failures should not abort later seeds.

## Acceptance Criteria

- `src/game/sim` exports a batch simulation runner.
- A named current smoke seed suite exists and is exported.
- The default batch run uses the current smoke suite.
- The current smoke suite runs multiple deterministic seeds through the cDp8 headless runner.
- Per-seed failures do not abort the batch.
- Batch summary includes status counts, winner counts, completion/max-step rates, prompt counts, replay counts, failure-code counts, averages, policies by seat, and seeds grouped by status.
- Replay diagnostics can be enabled and default to enabled.
- Replay diagnostics failures are reported in run records and aggregate counts instead of thrown through the whole batch.
- Batch output excludes raw cDp8 final states, command logs, events, observations, hand arrays, and deck order by default.
- `includeRawResults: true` is explicitly supported or explicitly rejected. If supported, docs must warn that raw results are debug-only and not ML-safe.
- Deterministic fingerprints or equivalent compact determinism fields exist.
- Same suite, same policies, same max steps produce equal batch summaries and fingerprints.
- A low `maxSteps` batch produces `max_steps_exceeded` records and aggregates without throwing.
- A throwing policy produces per-seed `policy_failed` records and aggregates without throwing.
- Docs explain batch usage and ML boundary.
- `docs/PROJECT_STATE.md` is updated.
- `audit/reports/2026-04-26-cDp9-report.md` exists.
- `npm test` passes.
- `npm run ci` passes.
- `npm run ci:browser` passes or is explicitly documented if local browser permissions block it.
- `git diff --check` passes.

## Notes For The Coding Instance

- Treat this as a diagnostics layer over cDp8, not a new simulator.
- Keep the public API small and deterministic.
- Prefer compact records and aggregate counts over full state dumps.
- Continue after individual seed failures.
- Use exact cDp8 single-run results internally, then deliberately collapse them for batch output.
- Do not use wall-clock time in deterministic summaries.
- If adding a hash helper, make it stable and local. Do not add a dependency just for hashing.
- Keep browser smoke green; this phase should not need UI changes.
