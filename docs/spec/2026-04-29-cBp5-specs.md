# Implementation Spec: Cluster B, Phase 5 - Official Leaders, Starter Presets, And Linked Side Decks

## Goal

Finish the official catalog foundation needed for all five factions to appear as playable product decks.

This phase should:

- promote the official leader data into permanent leader catalog packs;
- add placeholder catalog metadata for official leader abilities that are not engine-executable yet;
- add official starter deck presets for all five factions while preserving the existing current Northern Realms and Nilfgaard defaults;
- add linked side-deck support in Deck Builder V1 so Skellige Berserker/Vildkaarl decks can be validated, persisted, and played end-to-end;
- keep rule execution unchanged: only the already implemented `clear_weather` leader remains executable.

Do not implement new leader rules, Avenger, Summon, AI strategy, route promotion, visual redesign, or image downloading in this phase.

## Current Context

cBp4 promoted official non-leader cards. cBp4.1 resolved the Skellige Berserker combined-card cleanup by adding:

- `skellige.berserker` -> `linkedSourceIds[0] = "skellige.vildkaarl"`
- `skellige.vildkaarl` tagged `side_deck_only`
- `skellige.young-berserker` -> `linkedSourceIds[0] = "skellige.young-vildkaarl"`
- `skellige.young-vildkaarl` tagged `side_deck_only`

cCp9 already made Mardroeme/Berserker engine behavior work when replacement cards are present in the acting seat's side deck. The missing bridge is product data and Deck Builder support for linked side-deck replacements.

The official Game8 scrape has `22` leader candidates:

- Northern Realms: 5, already present as current catalog leaders.
- Nilfgaard: 5, already present as current catalog leaders.
- Monsters: 5, currently missing from permanent leader packs.
- Scoia'tael: 5, currently missing from permanent leader packs.
- Skellige: 2, currently missing from permanent leader packs.

Many official leader abilities are not executable yet. They still need permanent catalog metadata so leader records can validate and render, but their status must remain `placeholder` unless already implemented.

## Product And Architecture Decisions

Use these decisions unless the user explicitly changes them later:

- Permanent catalog data remains plain TypeScript source data.
- Product catalog data must not import from the scrape JSON or cBp3 staging modules at runtime.
- Tests may import both permanent catalog data and cBp3 staging data to assert coverage.
- Existing current Northern Realms and Nilfgaard deck presets must remain unchanged in ID, name, leader, main deck, side deck, and card counts.
- The default pre-game selection remains `current-northern-realms` vs `current-nilfgaard`.
- New official starter presets may be exposed through `currentDeckPresets` after the two current presets, but they must not replace or shadow the current defaults.
- Placeholder leader abilities are allowed on leader records and starter decks. Deck Builder may warn, but it must not block a deck solely because the leader ability is placeholder.
- Only `clear_weather` leader commands are executable in legal moves. Placeholder leader records must not create illegal or fake command paths.
- Side decks are not a free-form deck-building surface in this phase. They are linked replacement support for `side_deck_only` cards referenced by main-deck cards, especially Skellige Berserkers.
- Keep `side_deck_only` cards hidden from the normal main-deck card pool.

- `official-northern-realms-starter`
- `official-nilfgaard-starter`

- Export the new presets through `src/data/catalog/deck-presets/index.ts` and `src/data/catalog/index.ts`.
- Preserve `currentNorthernRealmsDeckPreset` and `currentNilfgaardDeckPreset` exactly.

- Each official starter deck must validate through `validateDeckPresets`.
- Each official starter deck must be playable according to `validateDeckPreset` with zero error issues. Placeholder leader warnings are acceptable.
- Each main deck must contain:
  - at least `22` battlefield cards;
  - no more than `10` special cards;
  - only neutral cards plus cards from its own faction;
  - no `side_deck_only` card.

- Skellige starter requirements:
  - include at least one Berserker base card (`skellige.berserker` or `skellige.young-berserker`);
  - include at least one `skellige.mardroeme`;
  - include side-deck replacement entries for the Berserker base cards it uses;
  - side-deck replacement counts must match the linked Berserker main-deck counts.
- Non-Skellige official starter presets should have `sideDeck: []` unless a future linked side-deck need is explicitly present.
- Do not add official starter presets for factions that cannot validate.

### 5. Support Linked Side Decks In Deck Builder V1

Update the deck-builder view model and UI so linked side-deck replacements are first-class, but still narrow.

Required view-model behavior:

- Keep `isSideDeckOnlyCard(card)` as the shared predicate.
- Add a pure helper that derives linked side-deck requirements from a deck's main deck:

```ts
replacement source id -> required count
```

The count is the sum of main-deck counts for cards whose `linkedSourceIds` include that `side_deck_only` replacement.

- Add a pure helper that synchronizes `deck.sideDeck` to those linked requirements.
- Any Deck Builder mutation path that changes main-deck contents or faction should either:
  - keep the side deck synchronized automatically, or
  - expose an obvious "sync side deck" action and block play until synchronized.

Prefer automatic synchronization for add/remove/faction-change/reset/duplicate/import paths unless it creates a surprising data-loss case. If you choose a manual sync action, document the reason in the report.

Validation changes:

- Remove the blanket Deck Builder V1 error that rejects every non-empty `sideDeck`.
- A non-empty side deck is valid only when all of these are true:
  - every side-deck source ID exists;
  - every side-deck card is tagged `side_deck_only`;
  - every side-deck card belongs to the deck faction or a future neutral side-deck convention;
  - every side-deck entry is linked from at least one main-deck card;
  - every side-deck count exactly matches the derived linked requirement.
- Suggested error codes:
  - `unknown_side_deck_card`
  - `invalid_side_deck_card`
  - `wrong_faction_side_deck_card`
  - `unlinked_side_deck_card`
  - `side_deck_count_mismatch`
- Continue to reject `side_deck_only` cards in `mainDeck` with `side_deck_only_main_deck`.

UI changes:

- Add a compact "side deck" section to `AuthenticDeckBuilderScreen`.
- Show linked replacement cards and counts when the active deck has side-deck requirements or side-deck entries.
- Use existing `authentic-button` classes and existing deck-builder typography. Do not introduce a new visual language.
- Do not add a free-form side-deck card pool.
- Do not show `side_deck_only` cards in the main card pool.
- If side-deck sync is automatic, the UI should make that clear with a small status line such as `linked replacements`.
- If side-deck sync is manual, the UI must provide a lowercase `sync side deck` button styled like the other deck-builder secondary buttons.
- Preserve existing lowercase button labels.

Persistence/import/export behavior:

- LocalStorage deck persistence must preserve valid `sideDeck` arrays.
- JSON export/copy must preserve `sideDeck`.
- JSON import must either preserve a valid `sideDeck` or normalize/sync it deterministically. Invalid side decks must produce visible import/validation errors, not silent bad decks.
- Duplicate and reset-to-catalog should preserve or rederive side decks correctly.
- Play-from-builder must pass the selected deck's side deck into the engine start path unchanged after validation.
