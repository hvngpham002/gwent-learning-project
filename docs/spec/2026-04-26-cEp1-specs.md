# Implementation Spec: Cluster E, Phase 1 - Authentic UI Foundation

## Goal

Establish the production UI foundation for the selected `docs/ui-handoff/` design without changing game rules or replacing the current playable routes.

This phase should create the visual and component substrate for the future authentic match screen:

- production Direction A design tokens;
- catalog-aware display metadata for factions, rows, and abilities;
- an authentic card rendering path with hidden-card back and missing-image fallback;
- a small opt-in product UI harness/gallery for review and browser smoke;
- no rule logic, no deck builder, no match-table migration yet.

The result should make `cEp2` possible without asking that phase to solve typography, tokens, card visuals, display metadata, route plumbing, and visual smoke all at once.

## Architecture Position

Current state before `cEp1`:

- legacy Redux UI remains the default route;
- the engine shell is opt-in with `?engine=1` or `VITE_ENGINE_UI=1`;
- the engine shell is functional but intentionally diagnostic/button-driven, not the final product UI;
- the selected final UI direction is documented in `docs/overhaul-plan/cluster-e-ui-plan.md`;
- `docs/ui-handoff/` contains the design handoff and prototype references;
- the handoff prototype is not production code.

After this phase:

- `/` still renders the legacy UI by default;
- `?engine=1` still renders the existing engine shell;
- a new opt-in authentic UI foundation route renders through `?engine=1&ui=authentic`;
- the authentic route is a gallery/harness only, not a playable match replacement;
- shared UI assets/components are ready for `cEp2`.

## Scope

### 1. Add production design tokens

Add a production stylesheet for the selected Direction A handoff.

Suggested file:

- `src/styles/gwent-tokens.css`

Requirements:

- import it exactly once from the normal app style entry path, such as `src/main.tsx` or `src/styles/global.css`;
- include the selected Direction A token values from `docs/ui-handoff/prototype/tokens.css`;
- preserve the handoff's visual intent: parchment/warm paper background, dark ink, ink-red accent, brass/gold secondary detail, faction colors, `EB Garamond`, and `JetBrains Mono`;
- avoid breaking legacy UI by scoping broad layout/background rules to a product wrapper such as `.gwent-authentic`;
- do not globally restyle `body` beyond safe font/token definitions already consistent with the project;
- do not import or depend on the prototype HTML.

Font handling:

- prefer a simple CSS `@import` or documented web-font import for `EB Garamond` and `JetBrains Mono`;
- if the implementer chooses not to load external fonts in code, the report must call that out and keep appropriate serif/monospace fallbacks.

### 2. Add catalog-aware display metadata

Add display metadata helpers for product UI rendering.

Suggested files:

- `src/components/gwent/displayMetadata.ts`
- or `src/components/gwent/factions.ts`, `rows.ts`, `abilities.ts`

Requirements:

- metadata must map current catalog IDs/types, not prototype-only string assumptions;
- include faction display names, faction accent colors/classes, short labels/glyphs where useful;
- include row display labels and glyphs for close/ranged/siege;
- include ability display labels/glyphs for current catalog ability IDs and known placeholders;
- include leader ability label fallback for current catalog leader metadata;
- expose deterministic fallback helpers for unknown/placeholder values;
- keep this module UI-only and data-display-only.

Forbidden:

- no rule calculations;
- no legal-move generation;
- no imports from legacy `src/utils/gameHelpers`;
- no imports from legacy `gameSlice`, `gameThunks`, `gameSelectors`, `useReduxAI`, or `AIStrategyCoordinator`.

### 3. Add an authentic card rendering path

Add a reusable card visual component for the authentic UI.

Suggested approach:

- create `src/components/gwent/AuthenticCard.tsx` and `src/components/gwent/AuthenticCardBack.tsx`;
- or extend `src/components/card/GwentCard.tsx` with `variant: "classic" | "authentic"` only if this can be done without importing engine/catalog code into the legacy card path.

Recommendation: create new `src/components/gwent/` components for this phase. The current `GwentCard.tsx` computes legacy display strength using `gameHelpers`, so extending it directly risks dragging legacy rule assumptions into the new product UI.

Requirements:

- render from a catalog-card-like view model, not from legacy `src/types/card.ts` only;
- support at least these fields: `sourceId`, `name`, `faction`, `kind`, `strength`, `rows`, `abilities`, `tags`, `image`, and optional `description`;
- support sizes equivalent to the handoff vocabulary: `xs`, `sm`, `md`, `lg`, and `xl` if practical, with stable dimensions;
- render unit strength only when appropriate;
- distinguish hero, unit, special, and leader/pseudo-leader states where current data allows;
- show row and ability glyphs/labels without needing rule logic;
- show faction stripe/accent;
- render hidden cards through a card-back component that never receives or exposes hidden card identity;
- use a deterministic SVG/art fallback when the image path is missing or fails to load;
- keep text inside the card bounds at mobile and desktop sizes;
- add accessible labels for cards and backs.

Image/fallback handling:

- do not require the user to populate real card art before the UI works;
- missing images should fall back to a deterministic `SvgCardArt`-style presentation using faction/source/name metadata;
- do not write image files in this phase;
- do not make browser network calls to fetch card images.

### 4. Add an opt-in authentic UI harness

Add a small product UI harness/gallery behind `?engine=1&ui=authentic`.

Suggested files:

- `src/components/gwent/AuthenticUiHarness.tsx`
- `src/components/gwent/authentic-ui.css`
- updates to `src/App.tsx`
- updates to `src/appMode.ts`
- updates to `tests/appMode.test.ts`

Requirements:

- `/` must still render legacy UI;
- `?engine=1` must still render the existing `EngineGameManager`;
- `?engine=1&ui=authentic` must render the new authentic harness;
- if `VITE_ENGINE_UI=1` is set without `ui=authentic`, keep the existing engine shell behavior;
- the harness should use current catalog cards, not prototype stub data;
- include visible examples of:
  - at least one Northern Realms card;
  - at least one Nilfgaard card;
  - at least one neutral card if present;
  - at least one unit card;
  - at least one special/weather/card with ability metadata if present;
  - a card back/hidden card;
  - missing-image fallback behavior if current catalog images are not available;
  - compact faction/row/ability metadata chips or swatches.
- include stable `data-testid` selectors for browser smoke:
  - `authentic-ui-harness`;
  - `authentic-card`;
  - `authentic-card-back`;
  - `authentic-metadata-swatch` or equivalent.

The harness should look like the handoff's tactical table direction, but it is not expected to be the full match screen. It can be a product foundation/gallery with a compact top bar and sample card rows.

## Non-Goals

Do not:

- replace the default route;
- replace `EngineGameManager`;
- build the full match table;
- implement pre-game setup;
- implement deck builder;
- implement Card Studio;
- change engine rules, legal moves, scoring, prompts, AI policy, simulation, or export code;
- port `docs/ui-handoff/prototype/match-engine.jsx`;
- port `docs/ui-handoff/prototype/tweaks-panel.jsx`;
- use prototype stub `CARDS`, `GAME_MODES`, `OPPONENTS`, `CARD_POOL`, or `LEADERS_NR` as production data;
- add a new UI library or icon package;
- add drag/drop;
- add screenshots as committed artifacts unless the project already has an approved visual-regression workflow.

## Boundary Rules

New product UI code may import:

- React;
- CSS;
- current catalog data/types;
- display metadata helpers;
- generic utility helpers that do not compute game rules.

New product UI code must not import:

- `src/utils/gameHelpers`;
- `@/utils/gameHelpers`;
- `calculateTotalScore`;
- `calculateRowStrength`;
- `useReduxAI`;
- `AIStrategyCoordinator`;
- `gameSlice`;
- `gameThunks`;
- `gameSelectors`;
- `GameBoard`;
- `src/ai/strategy.ts`;
- prototype files under `docs/ui-handoff/`.

The existing legacy card component may remain unchanged. If it is modified, do not change its default visual behavior or legacy call-site behavior.

## Implementation Hints

Suggested route helper shape:

```ts
export type EngineUiVariant = "shell" | "authentic";

export const getEngineUiVariantFromSearch = (search = ""): EngineUiVariant => {
  const params = new URLSearchParams(search.startsWith("?") ? search : `?${search}`);
  return params.get("ui") === "authentic" ? "authentic" : "shell";
};
```

Then `App.tsx` can choose:

- legacy UI when `shouldUseEngineUi(...)` is false;
- authentic harness when engine UI is enabled and variant is `authentic`;
- existing `EngineGameManager` otherwise.

Do not treat `ui=authentic` without `engine=1` as a route switch unless the implementer clearly documents and tests that behavior. Recommended behavior: require `engine=1`.

Suggested catalog sample selection:

- take the first few source cards from current catalog exports;
- deliberately include a hidden `AuthenticCardBack`;
- if an image URL fails, render fallback in component state;
- avoid displaying raw `sourceId` in visible text unless it is inside a dev-only/debug area. The browser smoke should not need source IDs.

## Acceptance Criteria

This phase is complete when:

- `/?engine=1&ui=authentic` renders an authentic UI foundation/harness;
- `/` still renders legacy UI;
- `/?engine=1` still renders the existing engine shell;
- production Direction A tokens are available without globally breaking legacy UI;
- authentic card and card-back components render current catalog data;
- missing card art does not break rendering;
- display metadata covers current factions, rows, abilities, and unknown fallbacks;
- no new product UI path imports forbidden legacy rule or AI modules;
- hidden card backs never receive or render hidden identity;
- Playwright smoke covers desktop/mobile route presence and no horizontal overflow;
- `docs/PROJECT_STATE.md` is updated;
- the required report is created.

## Reporting Directive For Coding Agent

Stay within `cEp1`. If you find that the authentic card component needs engine board state, legal moves, prompt state, deck-builder state, or a match-screen layout to proceed, stop and report the boundary instead of expanding scope.

Pay special attention to:

- accidentally importing legacy rule helpers through the old card component;
- leaking catalog/source/internal IDs in visible UI text;
- global CSS collisions with legacy UI;
- mobile horizontal overflow;
- prototype stub data sneaking into production;
- treating this harness as a playable match UI.
