## Required Behavior Design

Implement a conservative round-resource budget for non-elimination rounds.

The exact helper names are up to the implementer, but the shape should be close to:

```ts
type RoundResourcePressure = "none" | "watch" | "high" | "critical";

function getRoundResourceBudget(features, handShape): number
function buildRoundResourcePressure(features, selectedMove, handShape, roundInvestmentAnalysis): ...
```

The budget must be based only on hidden-info-safe public/own-observation data:

- round number;
- own gems and opponent gems;
- own/opponent passed flags;
- own hand count;
- own board card count / non-hero unit count / hero count / horn count;
- future hand quality bucket;
- positive future unit/hero move count;
- whether selected move spends a hand card;
- whether selected move is card advantage;
- score delta;
- catch-up status.

### Budget Intent

The policy should become more willing to pass or sacrifice a non-elimination round when all are true:

1. own gems > 1;
2. opponent has not passed;
3. pass is legal;
4. the best candidate spends a hand card;
5. the candidate is not card advantage;
6. the candidate is not a free/useful leader action;
7. current-round board investment is already high for the hand quality and round;
8. playing the candidate would leave future hand quality thin/poor or no useful unit tempo;
9. the policy is not on a last-gem fight line.

### Suggested Initial Budget

Use conservative thresholds; avoid making v1 timid.

Suggested first-pass constants:

```ts
base budget:
  healthy future hand: 5 own board cards
  thin future hand: 4 own board cards
  poor future hand: 3 own board cards

round adjustment:
  round 1: no adjustment
  round 2: -1 if own gems > opponent gems, else no adjustment
  round 3: no resource-budget pass; round 3 is for spending remaining resources

score adjustment:
  scoreDelta >= 10: -1, because the current round is already favorable
  scoreDelta < -15: +1, because more investment may be needed to contest

minimum budget floor: 2
maximum budget cap: 6
```

These exact constants can be adjusted if tests show obvious over-pass/under-pass, but the report must record any deviation.

### Required Exceptions

Never block these solely because of round-resource budgeting:

- last-gem fight lines (`ownGems <= 1`);
- card-advantage moves, especially Spy;
- free useful leader moves;
- a single-move catch-up that wins the current round cheaply;
- a match-winning play when opponent is on last gem;
- a one-card hand where there is nothing meaningful left to preserve;
- prompt resolution or round resolution.

### Catch-Up Rule

If the AI is behind but has a single-card catch-up available, cFp36 should not blindly pass just because the board budget is exceeded. It should still be able to play a cheap catch-up when:

- the candidate catches up to `minimumScoreToWinRound(features)`;
- overkill is small;
- the candidate does not leave future unit tempo completely empty; or
- the candidate is card advantage.

If the catch-up is expensive and would leave no future unit tempo on a non-elimination round, passing/sacrificing is allowed.

### Round 3 Rule

Do not use round-resource budgeting to pass in round 3 simply to preserve future hand. There is no future round after round 3. Round 3 behavior can still pass if normal policy says the round is unwinnable or already won, but cFp36's resource budget should focus on rounds 1 and 2.

## Diagnostic Requirements

Extend `AiDecisionRoundInvestmentAnalysis` with safe aggregate fields. Suggested fields:

```ts
readonly roundResourceBudget: number;
readonly roundResourcePressure: "none" | "watch" | "high" | "critical";
readonly resourceExhaustionRecommended: boolean;
readonly resourceExhaustionReason:
  | "none"
  | "round_budget_exceeded"
  | "thin_future_hand"
  | "poor_future_hand"
  | "last_useful_unit"
  | "round_three_no_budget"
  | "exception_card_advantage"
  | "exception_last_gem"
  | "exception_leader"
  | "exception_match_winning_play";
```

Field names can differ, but the diagnostic must show:

- budget value;
- current board investment count used by the budget;
- pressure bucket;
- whether cFp36 recommended preserving resources;
- why it did or did not apply.

Update all hidden-info scanners so these enum/string fields are allowed and card/source IDs are still rejected.

## Tests

Add focused tests in `tests/game/engineAiPolicy.test.ts`.

Required scenarios:

1. Round 1, non-elimination, opponent active, own board already over budget, future hand thin/poor, best candidate spends hand and is not card advantage -> v1 passes.
2. Same as above, but candidate is Spy/card advantage -> v1 plays the Spy.
3. Same as above, but candidate is a useful `use_leader` move -> v1 uses leader or at least does not pass solely due to resource budget.
4. Last gem, behind, useful unit can still fight -> v1 does not resource-budget pass.
5. Opponent on last gem and candidate wins match -> v1 plays the match-winning card.
6. Round 3 with low future hand quality -> cFp36 resource budget does not recommend passing just for future preservation.
7. Healthy hand / low board investment -> v1 continues normal useful move selection.
8. Cheap single-move catch-up with acceptable future hand -> v1 can still play catch-up.
9. Expensive catch-up that leaves no future unit tempo on non-elimination round -> v1 may pass/sacrifice.
10. Explanation parity: `explainLegalHeuristicV1Decision(...).move` equals `legalHeuristicPolicyV1.selectMove(...)` for cFp36 resource-budget fixtures.
11. Trace includes the new resource-budget fields and enum reasons.
12. Product diagnostic hidden-info scan accepts safe resource-budget enums and rejects card-name/source-id-like injected values in the new round-investment subtree.
13. Existing cFp29 Medic timing, cFp30 weather placement, cFp32 stop-loss, and cFp33 Scoia'tael first-turn tests still pass.

If the tests need helper fixtures, keep them local to `engineAiPolicy.test.ts` or use existing test helpers already in that file. Do not introduce a broad test DSL unless it removes real duplication.
