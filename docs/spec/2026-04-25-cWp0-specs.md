# Implementation Spec: Cluster W, Phase 0 - Project Workflow and CI Baseline

## Goal

Stabilize the project workflow before Cluster D continues. The game architecture has moved beyond the original dated plan: we now have a pure engine, an opt-in engine UI shell, phase specs, reports, and multiple implementation agents. This phase should make project governance explicit so future work does not drift.

The deliverable is a durable workflow baseline:

- one current-state source of truth that every coding instance must read and update;
- a repo-root `AGENTS.md` that tells agents how to work in this repository;
- a stable overhaul-plan directory name;
- CI checks that enforce build/test hygiene and prevent known architectural regressions;
- a clear branch, commit, report, and versioning strategy.

This phase is intentionally thorough. It should not change gameplay behavior.

## Architecture Position

This phase is inserted before Cluster D Phase 5. Treat it as workflow hardening, not a game feature phase.

Current state:

- Cluster A Phase 0 baseline is complete.
- Cluster B Phases 1-2 catalog foundation and current catalog migration are complete.
- Cluster C core engine is complete through setup, legal moves, command transactions, abilities, scoring, round/game resolution, and reports.
- Cluster D app migration is in progress:
  - `cDp1`: Redux engine adapter;
  - `cDp2`: opt-in engine UI shell;
  - `cDp3`: human card play through engine legal moves;
  - `cDp4`: leader and prompt controls through engine legal moves.
- Legacy UI still remains the default app route.
- Engine UI is still opt-in through `?engine=1` or `VITE_ENGINE_UI=1`.
- Scripted preview AI still only mulligans zero and passes.

The existing `docs/2026-04-24-overhaul-plan/` directory is still useful, but the dated directory name and stale phase index are now confusing. This phase should convert it into stable planning documentation and add a living state document.

### 6. Add CI workflow

Create:

- `.github/workflows/ci.yml`

Required behavior:

- Run on:
  - `pull_request`;
  - `push` to `dev`;
  - `push` to `main` if `main` exists or is expected.
- Use Node 22 unless there is a concrete reason not to.
- Use `actions/setup-node` with npm cache.
- Use `npm ci`, not `npm install`.
- Run the local aggregate CI command from `package.json`.
- Upload `dist/` as a build artifact on successful push to `dev` or `main` if simple.
- Set reasonable concurrency so repeated pushes cancel older CI runs for the same branch.

Suggested workflow shape:

```yaml
name: CI

on:
  pull_request:
  push:
    branches: [dev, main]

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run ci
      - uses: actions/upload-artifact@v4
        if: github.event_name == 'push'
        with:
          name: dist
          path: dist
```

Adjust only if the final script names differ.

### 8. Add architecture check scripts

Create a `scripts/` directory if it does not exist.

Required scripts:

1. `scripts/check-forbidden-imports.mjs`
   - Scan engine UI and engine adapter paths.
   - Fail if forbidden legacy imports or identifiers are present.
   - Paths to scan should include:
     - `src/components/game/EngineGameManager.tsx`
     - `src/components/game/engine/`
     - `src/store/selectors/engineSelectors.ts`
     - `src/store/slices/engineSlice.ts`
     - `src/store/thunks/engineThunks.ts`
   - Forbidden patterns should include at least:
     - `src/utils/gameHelpers`
     - `@/utils/gameHelpers`
     - `gameHelpers`
     - `calculateTotalScore`
     - `calculateRowStrength`
     - `useReduxAI`
     - `AIStrategyCoordinator`
     - `gameSlice`
     - `gameThunks`
     - `gameSelectors`
     - `GameBoard`
   - Output should list file and matched pattern.

2. `scripts/check-project-state-update.mjs`
   - Enforce that `docs/PROJECT_STATE.md` is changed when relevant files changed.
   - It should support CI and local usage.
   - Suggested behavior:
     - Determine changed files from a base ref.
     - On PR CI, compare against the PR base SHA or branch.
     - Locally, allow `--base <ref>` and default to `HEAD~1` if no base is supplied.
     - If relevant files changed and `docs/PROJECT_STATE.md` did not, fail with a clear message.
   - Relevant files should include:
     - `src/**`
     - `tests/**`
     - `docs/spec/**`
     - `audit/reports/**`
     - `docs/overhaul-plan/**`
     - `.github/**`
     - `package.json`
     - `package-lock.json`
     - `AGENTS.md`
     - `README.md`
   - Exempt changes only when the changed set is limited to files that genuinely do not affect project state, such as `.gitignore` comments or typo-only docs. If implementing exemptions is too complex, keep the check simple and document that it is intentionally strict.

3. `scripts/check-worktree-clean.mjs`
   - Fail if tracked files differ after CI commands.
   - Use `git diff --exit-code` or equivalent child process call.
   - Do not fail on untracked `.claude/` in local runs unless a strict flag is passed.
   - In CI, no `.claude/` should exist anyway.

Use Node scripts rather than shell pipelines so the checks are cross-platform and easier to read.

### 9. Handle generated build metadata

The repo currently has tracked TypeScript build metadata that can be dirtied by `npm run build`.

Required outcome:

- build/test commands should not leave tracked generated metadata modified;
- CI should fail if a build dirties tracked files.

Recommended implementation:

- Add `*.tsbuildinfo` to `.gitignore`.
- Stop tracking existing `tsconfig.app.tsbuildinfo` if it is tracked.
- If `tsconfig.node.tsbuildinfo` or other build info files exist or are generated, ignore them as well.
- Confirm `npm run build` no longer creates tracked-file diffs.

Do not remove source files or TypeScript config files.
