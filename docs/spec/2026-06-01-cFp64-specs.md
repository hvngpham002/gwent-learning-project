## Summary

cFp63 repaired the sampler's public-known source subtraction so each public
runtime card instance is counted at most once across public zones/lists. That
repair was correct and should stay, but it falsified the duplicate-reference
hypothesis for the committed starter artifacts:

- `benchmark-v1-starter-matrix-v1`: still 3,979 valid / 63 invalid cFp61 roots.
- `benchmark-v1-starter-matrix-robust-v1`: still 32,146 valid / 341 invalid cFp61 roots.
- cFp62 still classifies all 404 invalid roots as `public_zone_count_deficit`.
- Duplicate public-reference totals are 0 in both suites.
- Duplicate fixed-known-hand-reference totals are 0 in both suites.

cFp64 is the next evidence phase. It must add a scalar-only public-zone
provenance casebook that explains where the remaining public-zone count deficits
come from. It must not implement search, sampler relaxation, gameplay behavior,
or another speculative repair before the provenance evidence exists.

The expected output is a deterministic artifact family under
`sampler-public-zone-provenance/cFp64/` plus a compact decision note that
recommends exactly one next phase.

## Research Grounding

cFp58 remains the controlling search-readiness decision. It permits benchmark
sampler infrastructure, but requires hidden-info safety, explicit invalid-root
accounting, and determinization-risk measurement before strength claims.

cFp60 built known-preset priors and public action abstraction. cFp61
materialized hidden source-multiset samples for valid official-starter roots.
cFp62 showed the invalid roots are narrow `public_zone_count_deficit` cases.
cFp63 proved duplicate public references are not the cause in committed
current/robust artifacts.

cFp64 must not jump to search. It should classify the remaining public-zone
deficits with enough scalar provenance to choose whether cFp65 should be:

1. a narrow sampler accounting repair;
2. an explicit valid-root-only probe with skip accounting; or
3. another scalar instrumentation pass.

## Analyzer Contract

### Input

Use the same root-observer path as cFp62 so the analyzer observes current code
and produces deterministic artifacts. The cFp64 analyzer may call or reuse:

- `buildSamplerInvalidRootAnalysis`;
- `buildPublicKnownZoneCountSummary`;
- `buildPublicKnownSourceSubtraction`;
- known-preset prior metadata;
- scalar fields from the cFp61 materialization root record;
- scalar fields from the cFp62 invalid-root record.

Do not parse committed JSONL files as the only source of truth. The analyzer
should be runnable from current code over the current benchmark suites.

Allowed input categories:

- public root metadata already used by cFp61/cFp62;
- public zone counts by zone family;
- opponent-seat known-preset prior counts as aggregate card totals only;
- scalar materialization invalid reason counts;
- scalar invalid-root classification fields.

Forbidden input categories:

- true opponent hand card identities;
- true opponent deck card identities or order;
- hidden runtime card ids;
- raw `cardsById` serialized in artifacts;
- raw command logs, event logs, final state, raw legal moves, or unsafe debug
  payloads in artifacts.

### Required Scalar Evidence

For each invalid root record, include only scalar/count/bucket fields. Suggested
shape:

```ts
type PublicZoneProvenanceLabel =
  | "single_zone_board"
  | "single_zone_row_horn"

  | "provenance_ambiguous";

  schemaVersion: "sampler-public-zone-provenance-root-v1";
  samplerRunId: string;

}
```

Exact names may differ, but the artifact must stay scalar-only.

### Zone Families

Compute public-zone family counts from existing cFp62-safe information. At
minimum, preserve these families:

- opponent board units;
- opponent row horns;
- opponent discard;
- opponent removed-from-game;
- opponent weather;
- acting hand known opponent-owned cards;
- prompt-revealed opponent hand cards;
- other public known.

Add only scalar counts. Do not add card ids, source ids, card names, raw zone
paths, source-count maps, or per-card lists.

### Classification Order

Classify each invalid root exactly once. Use a deterministic order similar to:

1. `round_end_public_zone` if `phase === "round_end"` and public-zone count is
   nonzero.
2. `zero_public_zone_unexpected` if public-zone count is zero despite the cFp62
   classification.
3. Single-zone labels if exactly one zone family has a nonzero count.
4. `mixed_public_zones` if two or more zone families have nonzero counts.
5. `provenance_ambiguous` as the fallback.

The implementation may refine the single-zone labels, but it must document the
order in code comments or tests and in the decision note.

### Summary

The summary should include:

- total root count;
- invalid provenance root count;
- source benchmark suite id;
- match count;
- cFp62 invalid classification counts observed;
- provenance label counts;
- phase counts;
- round counts;
- faction/policy/deck/matchup counts;
- prior-deficit bucket counts;
- dominant-public-zone counts;
- public-zone-shape counts;
- duplicate public/fixed-known-hand reference totals;
- hidden-info safety note;
- explicit non-search warning;
- recommended next step.
