# Implementation Spec: Cluster C, Phase 29 - Cancel Leader Current-Round Suppression

## Intent

Implement the final remaining official leader ability from
`docs/leader-ability-matrix.md`: `cancel_leader` for
`nilfgaard.emhyr-var-emreis-the-white-flame` (Emhyr var Emreis:
The White Flame).

This closes Tranche 4 and completes the current official leader ability
matrix. The settled product decision is:

- active one-shot leader;
- usable as a current-round suppression tool, not a whole-match lock;
- can be used proactively on the White Flame player's normal turn;
- can also be used as a reaction before an opponent active leader resolves;
- if it cancels an active leader as a reaction, the opponent leader is still
  consumed with no refund;
- if it suppresses a passive, pure scoring / ability policy recalculates
  immediately for the current round;
- suppression clears before the next round starts;
- setup-time effects that already happened, such as Daisy's `draw_extra_card`,
  are not retroactively undone.

Keep this phase focused on the pure engine, legal moves, prompt plumbing,
bounded AI policy compatibility, hidden-info-safe observations/exports,
minimal product UI status/prompt compatibility, tests, and living docs. Do not
bundle deck-builder work, Card Studio work, route promotion, broad UI redesign,
ML export/training work, legacy UI migration, or unrelated rule fixes.

## Rule Semantics For cCp29

### Terminology

Use **suppressed this round** rather than whole-match cancelled in new code and
docs wherever possible.

The historical ability ID is still:

```text
cancel_leader
```

The event name may remain:

```text
leader_cancelled
```

because the official/card-facing wording is "Cancel your opponent's Leader
ability." The event payload must make the current-round scope explicit.

### State Model

Add an explicit current-round suppression field to `SeatState`.

Recommended shape:

```ts
leaderCancelledRound: number | null;
```

or, if the implementer strongly prefers clearer naming:

```ts
leaderSuppressedRound: number | null;
```

Pick one name and use it consistently. If using the clearer
`leaderSuppressedRound` name, update report/docs to note that it is the engine
field for the `cancel_leader` card text.

The helper contract should be:

```ts
isLeaderSuppressedThisRound(state, seatId) ===
  state.seats[seatId].leaderCancelledRound === state.round
```

or the equivalent for the chosen field name.

Initialize the field to `null` in `startMatch`.

Clear the field for both seats before the next round starts. The field should
not remain true/stale in product UI after round transition. It is acceptable to
also rely on the round-number comparison defensively, but still clear the field
at round transition so serialized state remains easy to inspect.

Do not reset `leaderUsed` at round transition. `leaderUsed` remains
once-per-match, as today.

### Suppression Scope

Suppression affects only the target seat's **leader ability** during the
current round.

It must suppress:

- active `use_leader` legal moves for the target seat during the current
  round;
- active leader command execution for the target seat during the current round
  via the normal legal-move gate;
- current-round scoring passive policies:
  - `weather_half_penalty` / King Bran;
  - `double_close`;
  - `double_ranged`;
  - `double_siege`;
  - `double_spies`;
- current-round non-scoring passive ability policy:
  - `random_medic` / Invader of the North.

It must not retroactively undo:

- setup-time `draw_extra_card`;
- cards already moved by a resolved active leader;
- weather already played by a resolved active leader;
- cards already drawn, discarded, restored, shuffled, scorched, revealed, or
  repositioned by a resolved active leader.

When an active leader is cancelled through the **reaction prompt** before it
resolves, its effect must not happen at all, but that leader is still marked
used. That is the "no refund" rule.

When White Flame is used proactively before an opponent active leader is used,
the opponent leader is not consumed. It is simply locked out for the current
round. If the next round begins and the opponent leader was never otherwise
used, it becomes usable again.

### Cancellable Opponent Leaders

For proactive White Flame use, the opponent is cancellable only when the
opponent has a current-round leader effect that is not already suppressed.

Treat these as cancellable:

- any implemented active leader that is not yet used;
- implemented passive leaders with current-round effects:
  - `weather_half_penalty`;
  - `double_close`;
  - `double_ranged`;
  - `double_siege`;
  - `double_spies`;
  - `random_medic`.

Treat these as not cancellable for proactive use:

- already-used active leaders with no ongoing engine policy left to suppress;
- setup-only `draw_extra_card` by itself;
- unimplemented / placeholder leaders;
- missing catalog leader records;
- an opponent already suppressed for this round.

Do not allow White Flame to cancel another White Flame reaction. In other
words, a `cancel_leader` attempt should not open a nested
`cancel_leader` reaction prompt. This avoids recursive reaction windows and is
the intended cCp29 contract.

### Legal Move: Proactive Use

`cancel_leader` should emit one legal `use_leader` move on the White Flame
seat's own normal turn when all of the following are true:

- phase is `playing`;
- `currentTurn` is the White Flame seat;
- the White Flame seat has not passed;
- the White Flame leader is not used;
- the White Flame leader is not itself suppressed this round;
- no `pendingPrompt`;
- the opponent has a cancellable current-round leader effect per the section
  above.

The move target is:

```ts
{ kind: "none" }
```

Recommended metadata:

```ts
targetRequirement: "none"
targetSeatId: opponentSeatId
targetLabel: "opponent leader"
targetLeaderSourceId?: string
targetAbility?: string
suppressionRound: state.round
```

Add metadata fields only if useful and type-safe. Do not leak hidden info; the
opponent leader is public.

### Command: Proactive Use

For proactive `UseLeader`:

1. validate `target.kind === "none"`;
2. re-check that the opponent has a cancellable current-round leader effect;
3. clone state;
4. set opponent suppression for `state.round`;
5. set White Flame `leaderUsed = true`;
6. emit events;
7. hand off the turn.

Recommended event sequence:

```text
ability_triggered(cancel_leader)
leader_cancelled(mode: "proactive", round, seatId, targetSeatId, targetLeaderCardId, targetLeaderSourceId, targetAbilityId)
ability_resolved(cancel_leader, outcome: "leader_cancelled")
leader_used(White Flame)
turn_changed / turn_set via existing handoffTurn
```

Use existing event naming conventions where possible. If adding new event
payload fields, make them explicit and covered by tests.

### Reaction Prompt: When It Opens

When a seat attempts a non-`cancel_leader` active `UseLeader`, the engine must
offer a reaction prompt to the opposing White Flame seat before resolving the
attempted leader if all of the following are true:

- the attempted leader command is legal for the acting seat before the
  reaction check;
- phase is `playing`;
- no `pendingPrompt`;
- the opposing seat's leader ability is `cancel_leader`;
- the opposing White Flame leader is not used;
- the opposing seat has not passed;
- the opposing White Flame leader is not itself suppressed this round;
- the acting seat's leader is not already suppressed this round;
- the attempted leader ability is not `cancel_leader`.

This prompt is the true reaction window. The attempted leader effect must not
resolve until the reaction prompt resolves.

Recommended prompt shape:

```ts
pendingPrompt.kind === "choose_option"
pendingPrompt.abilityId === "cancel_leader"
pendingPrompt.stage === "leader_cancel_reaction"
pendingPrompt.seatId === whiteFlameSeatId
pendingPrompt.context.leaderCancel === {
  mode: "reaction",
  targetSeatId: attemptedLeaderSeatId,
  targetLeaderCardId: attemptedLeaderCardId,
  targetLeaderSourceId: attemptedLeaderSourceId,
  targetAbilityId: attemptedLeaderAbilityId,
  target: originalUseLeaderTarget
}
pendingPrompt.options === [
  { optionId: "cancel-leader:cancel", label: "Cancel leader", target: { kind: "none" } },
  { optionId: "cancel-leader:decline", label: "Let it stand", target: { kind: "none" } }
]
```

Add a new `PendingPromptStage` value:

```text
leader_cancel_reaction
```

Add a typed context shape rather than relying on unstructured `unknown` if
possible. If the target must remain `unknown` to avoid type cycles with
`LegalMoveTarget`, constrain it in command-side validation before replaying the
attempted leader.

When this prompt opens:

- do not consume the attempted leader;
- do not consume White Flame;
- do not set suppression yet;
- do not hand off the turn;
- keep `currentTurn` as the attempted leader's seat;
- emit `prompt_opened`.

### Reaction Prompt: Cancel Option

When `cancel-leader:cancel` resolves:

1. validate the prompt still describes a legal pending leader reaction;
2. validate the White Flame seat still owns an unused, unsuppressed
   `cancel_leader`;
3. validate the target seat/leader still matches the pending context;
4. set target suppression for `state.round`;
5. set White Flame `leaderUsed = true`;
6. set the target active leader `leaderUsed = true` with no effect;
7. emit cancellation events;
8. clear the prompt;
9. hand off from the original attempted leader seat.

The target leader's effect must not resolve. In particular:

- no weather card is pulled;
- no weather is cleared;
- no cards are scorched;
- no cards are restored/drawn/discarded/shuffled;
- no opponent-hand reveal event is emitted;
- no prompt from the cancelled leader remains open.

Recommended event sequence:

```text
prompt_resolved(cancel-leader:cancel)
ability_triggered(cancel_leader)
leader_cancelled(mode: "reaction", round, seatId: whiteFlameSeatId, targetSeatId, targetLeaderCardId, targetLeaderSourceId, targetAbilityId)
ability_resolved(cancel_leader, outcome: "leader_cancelled")
leader_used(White Flame)
leader_used(cancelled target leader)
turn_changed / turn_set via existing handoffTurn from target seat
```

It is acceptable to swap the two `leader_used` events if the codebase's event
helpers make another order more natural, but tests must lock the chosen order.
The report must call out the event order.

### Reaction Prompt: Decline Option

When `cancel-leader:decline` resolves:

1. emit `prompt_resolved`;
2. clear the prompt;
3. resolve the originally attempted leader exactly once;
4. do not re-open the same reaction prompt;
5. do not consume White Flame;
6. do not suppress the target seat.

This will likely require refactoring `executeLeader` so the actual leader
effect can be resolved by an internal helper with a flag such as:

```ts
resolveLeaderEffect({ allowCancelReaction: false })
```

or another equivalent design. Avoid duplicating every active leader branch in
the prompt resolver.

### Round Transition

When a round resolves and the next round begins:

- clear both seats' current-round leader suppression fields;
- passive helpers should resume in the next round if the leader is still
  present and applicable;
- active leaders suppressed proactively but not used should become legal again
  in the next round;
- active leaders cancelled by reaction remain `leaderUsed = true` and stay
  unavailable for the rest of the match.

Game end does not need a special reset beyond preserving final state.

## AI Policy Requirements

Keep this bounded. Do not attempt a broad strategic AI rewrite.

Required behavior:

- If AI owns a `leader_cancel_reaction` prompt, choose the cancel option by
  default. This is deterministic and ensures the AI can use White Flame as a
  reaction.
- If AI owns White Flame on its normal turn, allow a small proactive heuristic:
  - use it against an opponent current-round scoring passive if suppressing
    that passive improves or preserves the AI's current score differential;
  - use it against an opponent `random_medic` passive only when the opponent
    discard currently contains at least one eligible non-hero unit candidate;
  - do not spend it proactively against an unused active leader unless there is
    no better implemented heuristic basis. Prefer saving it for the reaction
    prompt.
- Do not make AI inspect hidden opponent hand/deck identities to decide.

If the proactive heuristic is too risky, implement only the reaction-prompt
choice and document proactive AI tuning as a follow-up. Do not leave AI unable
to resolve an owned reaction prompt.

- opponent active `UseLeader` opens a White Flame reaction prompt before the

- cancel option consumes White Flame.
- cancel option consumes the attempted target leader with no target effect.
- clear-weather reaction cancel does not clear weather.
- weather-pulling reaction cancel does not move weather from deck.
- discard/draw reaction cancel does not open a discard prompt.
- look-three-cards reaction cancel does not emit `opponent_hand_revealed`.
- prompt clears and turn hands off from the attempted leader seat.
- second use of either consumed leader is illegal.

### Reaction Decline

- decline option consumes neither White Flame nor suppression.
- decline resolves the original attempted leader exactly once.
- decline does not reopen the same reaction prompt.
- original leader then follows its normal handoff/prompt behavior.

- row-horn passive is ignored while suppressed and resumes next round.
- double-spies passive is ignored while suppressed and resumes next round.
- random-medic passive is ignored while suppressed, causing normal Medic prompt

  `cancel_leader`.
- Cancelling White Flame with another White Flame.
- Refunding an active leader cancelled by reaction.
- Retroactively undoing an active leader that already resolved before White
  Flame was used proactively.
- Retroactively undoing setup-time `draw_extra_card`.
- New broad AI strategy beyond bounded prompt/proactive compatibility.
- Deck builder, Card Studio, official porting, asset work, ML/export schema
  redesign, default route promotion, or legacy UI migration.

## Reporting Notes

The report must explicitly call out:

- chosen state field name (`leaderCancelledRound` vs
  `leaderSuppressedRound`);
- event order for proactive cancel;
- event order for reaction cancel;
- whether reaction decline refactored leader resolution or used another safe
  approach;
- how stale "rest of match" wording in `docs/leader-ability-matrix.md` was
  corrected;
- how passive helpers check suppression;
- how AI handles owned reaction prompts;
- whether `npm run ci:browser` was run and the result;
- any remaining leader-rule follow-up now that placeholder count should be 0.
