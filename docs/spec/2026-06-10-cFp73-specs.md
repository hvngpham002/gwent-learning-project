## Summary

cFp72 completed a benchmark-only post-one-ply branching budget probe over the
same valid-root population established by cFp68 through cFp71. It found no
failed/deferred pairs, no source consistency failures, no hidden-info scan
issues, and no `very_large` or `extreme` root budget buckets. The largest
post-one-ply public action count was 14 in the current suite and 15 in the
robust suite.

cFp73 should not execute more game commands. It should add a deterministic,
hidden-info-safe casebook over the committed cFp72 scalar artifacts. The
casebook should classify where the post-one-ply branching budget concentrates
by suite, phase, round, policy, faction, deck preset, matchup, first-ply public
action kind, post-one-ply actor, post-one-ply phase, and threshold bucket.

The goal is to decide the next search-readiness step:

- if large/high-threshold surfaces are narrow and interpretable, cFp74 can be a
  bounded benchmark-only second-ply scaffold design;
- if large/high-threshold surfaces are concentrated in a few suspicious
  categories, cFp74 should be a targeted casebook/repair phase first;
- if cFp73 finds artifact/hidden-info/consistency issues, cFp74 should repair
  cFp72/cFp73 before any deeper probe.

This is still not search gameplay. cFp73 must not run rollouts, evaluate
actions, rank actions, choose moves, estimate values, estimate win probability,
or expose anything in product AI beyond static AI Lab metadata.

## Why This Phase Exists

The current ladder is deliberately incremental:

- cFp68: valid-root-only determinized probe contract with skipped-root
  accounting.
- cFp69: public-action root scaffold.
- cFp70: sampled-world action availability.
- cFp71: one-ply public action outcome skeleton.
- cFp72: post-one-ply next-surface branching budget.

cFp72 says the next surface is mechanically measurable and not obviously
explosive. It does not tell us whether the high end of the surface is localized
or broad. cFp73 should make that distribution legible before any second-ply
command execution exists.

This keeps the project from jumping from "we can count the next surface" to
"we can search." We are still checking scaffolding and budget shape, not
claiming strategic strength.

## Scope

Implement a benchmark-only casebook generator that:

1. reads committed cFp72 artifact sets for the current and robust starter
   suites;
2. validates cFp72 summaries are `probe_ready`;
3. validates `failedOrDeferredBranchingPairCount === 0` in the summary and
   in all casebook input roots;
4. validates no input root has `branchingBudgetBucket` of `failed`,
   `deferred`, `very_large`, or `extreme` unless the casebook explicitly
   records a blocking recommendation;
5. reads cFp72 `branching-roots.jsonl`;
6. reads cFp72 `skipped-roots.jsonl`;
7. emits one scalar casebook row for every cFp72 branching root that matches at
   least one cFp73 selection rule;
8. emits one scalar skipped-root row for every cFp72 skipped root, or carries
   the skipped-root counters into summary plus a deterministic skipped JSONL;
9. aggregates hidden-info-safe counts by threshold bucket, suite, phase, round,
   policy, faction, deck preset, matchup, first-ply public action kind,
   post-one-ply actor, and post-one-ply phase;
10. produces a decision note with a concrete cFp74 recommendation; and
11. updates AI Lab metadata to cFp73 as analysis infrastructure, not search
    gameplay.

cFp73 should not re-run the benchmark suite. It should not rebuild sampled
states. It should not call `executeCommand`, `getLegalMoves`, or any sampler
materialization path. It reads cFp72 scalar artifacts only.

## Casebook Selection Rules

Emit a casebook root row if any of these rules match:

1. `branchingBudgetBucket === "large"`.
2. `nextPublicActionCountMax >= 12`.
3. `largestNextPublicActionBucketSizeMax >= 16`.
4. `nextPublicActionTargetExpansionCountMax >= 10`.
5. `postOnePlyActorCounts.system_round_end_resolver > 0`.
6. `postOnePlyActorCounts.terminal_game_end > 0`.
7. `postOnePlyPhaseCounts.round_end > 0`.
8. `postOnePlyPhaseCounts.game_end > 0`.
9. any failed/deferred/status anomaly count is greater than 0.

Rules 1-4 are budget-shape rows. Rules 5-8 are terminal/transition-context
rows. Rule 9 is a blocker row.

A root can match multiple rules. Store only enum rule labels and aggregate
counts. Do not store raw cFp72 source rows.

## Source Consistency Requirements

The casebook should fail or mark `casebookReadinessStatus` as `not_ready` if:

- cFp72 summary `probeReadinessStatus !== "probe_ready"`;
- cFp72 `branchingRootCount` does not equal the number of cFp72
  `branching-roots.jsonl` rows;
- cFp72 `skippedRootCount` does not equal the number of cFp72
  `skipped-roots.jsonl` rows;
- any cFp72 branching row has `failedOrDeferredBranchingPairCount > 0`;
- any cFp72 branching row has `probeStatus !== "completed"`;

- duplicate root keys exist;
- source artifact hashes cannot be computed.

If readiness is not ready, the CLI should still write artifacts when possible
but exit non-zero unless the implementation adds an explicit `--allow-not-ready`
flag. The default committed artifact must be ready.

## Expected cFp74 Decision Logic

- If there are zero status anomalies and no `very_large`/`extreme` cFp72
