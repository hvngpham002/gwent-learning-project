## Context

The project is moving from engine/UI completion into AI and ML research. The existing roadmap in `docs/overhaul-plan/ai-ml-roadmap.md` captures the right high-level direction, but it predates much of the completed simulation/export work and does not yet define a rigorous literature annotation process.

The user wants the AI/ML plan grounded in existing literature before implementation. The annotation directory must become the source of truth for research claims that affect future AI/ML specs.

The example workflow under `docs/research/examples/dp-scan-paper/` is for a different robotics/path-planning project. This phase must adapt its process to Gwent AI/ML without copying domain-specific planner categories.

## Goal

Establish a project-specific AI literature workflow that:

- creates a durable source-of-truth annotation structure for Gwent AI/ML research;
- defines page-bounded annotation discipline;
- defines paper intake, source package, annotation, triage, and synthesis rules;
- defines the initial literature sweep prompt for this project;
- updates the AI/ML roadmap so future Cluster F specs are downstream of annotated sources;
- records in `docs/PROJECT_STATE.md` that Cluster F is in a research-foundation stage.

No AI implementation work should happen in this phase.

### Purpose Requirements

State that this workflow governs research used for:

- legal heuristic AI policy design;
- benchmark ladder design;
- imperfect-information game modeling;
- self-play and search planning;
- ML observation/action/reward design;
- difficulty tier design;
- future Gwent AI paper or report writing.

State plainly:

> Annotation files under `docs/research/literature/ai/annotations/` are the source of truth for literature-grounded AI/ML claims.

### Directory Contract Requirements

Use the exact project-specific structure in this spec.

Source PDFs or downloaded papers are local reading artifacts and should not be committed unless explicitly licensed and intentionally added later. The workflow should assume `source.pdf` is local-only.

### Intake Requirements

Before annotating a paper, require the agent to:

- search existing annotations;
- search `docs/research/examples/dp-scan-paper/paper/references.bib` only as a reference example, not as this project's live Gwent bibliography;
- search any future Gwent bibliography file if it exists;
- avoid adding low-confidence citations;
- create a manifest before reading a source.

Do not require a Gwent `references.bib` in this phase unless the implementer chooses to add a placeholder note. This phase is workflow setup, not bibliography build-out.

### Source Package Requirements

Define:

```text
docs/research/literature/ai/source/<citekey>/
  manifest.yaml
  source.pdf
```

Manifest template must include:

```yaml
citekey:
title:
authors:
year:
venue:
primary_source: source.pdf
source_type: pdf
status: local-source-available
notes:
```

Also define acceptable `status` values:

- `local-source-available`
- `url-only`
- `missing-source`
- `secondary-lead-only`

### Batch Reading Protocol Requirements

Preserve the strict pattern from the example:

```text
STEP 1 READ        one batch, max 10 pages
STEP 2 ANNOTATE    update annotation file immediately
STEP 3 STOP + ASK  wait for explicit user continue
```

Hard rules:

- read at most 10 pages per batch;
- do not pre-read past the batch boundary;
- write notes for the current batch before checkpointing;
- stop after each batch and wait for the user;
- do not write final relevance / roadmap decision sections until full read is complete;
- every factual claim about a paper needs a page/section anchor;
- project inferences must be labeled `Project inference:`.

Use a checkpoint template adapted to `docs/research/literature/ai/...`.

- `## What This Paper Does Not Establish`

### AI-Roadmap Decision Fields

Each completed annotation must answer:

1. Is this source a direct implementation candidate, benchmark-methodology source, training-method source, difficulty-design source, background-only source, or reject?
2. Does it apply to deterministic perfect-information play, stochastic games, imperfect-information games, or hidden-information card games?
3. Does it require self-play, search, supervised learning, reinforcement learning, CFR-style learning, MCTS/ISMCTS, or another method family?
4. Does it support variable legal action sets or action masking?
5. Does it provide evaluation methodology relevant to this project?
6. Does it support global deck-conditioned agents, faction specialists, or both?
7. What is the smallest faithful implementation or experiment this project could run?
8. What would make adaptation misleading or benchmark-gaming?
9. Should this source affect Cluster F specs, the long-term ML roadmap, both, or neither?

### Spec Integration Rules

Add a strong policy:

- future AI/ML specs may cite chat discussion as motivation, but implementation-affecting research claims must cite annotation files;
- if no annotation supports a research claim, the spec must label it as a project hypothesis;
- benchmark, training, search, self-play, difficulty, and model architecture decisions must point to annotation-backed evidence once this workflow is active;
- `docs/overhaul-plan/ai-ml-roadmap.md` remains a roadmap summary, not the source of truth for literature claims.

## Required Content: Literature Sweep Prompt

Create `docs/research/literature/ai/prompts/lit-sweep-gwent-ai-prompt.md`.

The prompt must ask for a focused literature sweep for this project, including:

- imperfect-information card game AI;
- collectible/trading card game AI;
- Hearthstone, Magic, Legends of Code and Magic, or similar environments when primary sources exist;
- Gwent-like small-deck sequential decision games;
- legal action masking and variable action sets;
- self-play RL;
- MCTS / ISMCTS;
- CFR / Deep CFR / NFSP or related imperfect-information methods;
- policy/value learning for hidden-information games;
- benchmark ladders, Elo/Glicko, matchup matrices, fixed seed suites;
- difficulty scaling and human-like bounded blunders;
- opponent modeling / belief modeling;
- deck-conditioned versus specialist agents.

The prompt must require:

- primary sources first;
- critical classification, not inflated relevance;
- a table output first;
- top-paper notes after the table;
- explicit fields for method family, hidden-information handling, action masking, evaluation method, compute needs, relevance to this project, and implementation risk.

It must also instruct the researcher to avoid:

- blog posts unless they point to primary sources;
- generic RL tutorials;
- claims that self-play will converge without source support;
- papers that require hidden-information cheating without saying so.
