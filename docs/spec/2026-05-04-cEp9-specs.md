# Implementation Spec: Cluster E, Phase 9 - Leader Status And Prompt Polish

## Intent

Make the completed leader system legible in the authentic product match UI.

cCp29/cCp30 finished and audited the official leader matrix. cEp9 should not
add rules. It should surface the engine's existing leader state and prompt
state in a player-readable way inside `/?engine=1&ui=authentic`, especially:

- active vs passive vs setup-time leaders;
- ready / used / unavailable leader state;
- current-round `cancel_leader` suppression;
- prompt-specific copy for leader and card abilities;
- hidden-info-safe labels for prompt options.

Keep this phase product-focused and legal-move-driven. The UI can summarize
public engine state and catalog metadata, but it must not compute rule
outcomes, invent legal targets, or expose hidden card identities.

## Scope

### 1. Leader Status View Model

Add or extend pure view-model helpers in `src/components/gwent/matchViewModel.ts`
for leader status display. The helper should take only public match/UI inputs
and catalog/display metadata.

Required output concepts:

- leader name;
- ability name and status;
- class/category label:
  - active;
  - passive;
  - setup;
  - unknown/custom fallback;
- state label:
  - ready;
  - used;
  - passive active;
  - setup resolved;
  - cancelled this round;
  - unavailable;
  - no target;
- short reason string suitable for score cards / tooltips;
- whether an action button should be enabled;
- whether a suppression badge should be rendered.

Classification should be based on catalog leader ability metadata and the
official promotion manifest buckets where useful. Do not duplicate engine rule
logic for target availability. If the leader is otherwise usable by phase /
turn / pass / prompt / used status but has no legal leader move, use a generic
`no target` reason rather than trying to compute why.

Current-round suppression must come from engine state:

```ts
seat.leaderCancelledRound === state.round
```

or whatever selector/view-model input already exposes that flag. Do not infer
suppression from events alone.

### 2. Score-Card Leader Status UI

Update the authentic match score cards in `AuthenticMatchScreen.tsx` so each
leader visibly communicates status without clutter.

Requirements:

- Display a compact status chip or line near the leader card/name.
- Show `cancelled this round` prominently when suppression is active.
- Show passive/setup leaders as such, not as broken unused leaders.
- Keep the leader card dimensions unchanged.
- Preserve right-click leader inspection.
- Do not add a second leader card or duplicate ability text block.
- Keep copy small and EB Garamond/JetBrains usage consistent with the existing
  authentic UI.

Examples of acceptable short labels:

```text
ready
used
passive active
setup resolved
cancelled this round
no target
```

Do not render raw leader source IDs or runtime card IDs in the normal match UI.

### 3. Leader Action Panel Polish

Improve the existing leader action area without changing legal-move behavior.

Requirements:

- Continue dispatching the exact `UseLeader` command from the selected legal
  move. Do not reconstruct targets by hand.
- Keep cEp8 multi-choice behavior for `play_any_weather`; preserve row hints
  such as `close combat`, `ranged`, `siege`, `ranged + siege`.
- For single active leaders, show a clearer action label when possible:
  - `use leader` is acceptable as fallback;
  - `clear weather`, `choose weather`, `scorch ranged`, `restore card`,
    `draw from opponent discard`, `discard and draw`, `look at hand`,
    `cancel leader` are acceptable if derived from ability metadata / move
    metadata.
- When the leader cannot be used, show a disabled reason from the leader status
  view model rather than silently hiding the concept.
- Do not offer proactive White Flame if the engine legal moves do not offer it.

### 4. Prompt-Specific Presentation

Replace generic prompt text where it is currently too vague with
ability-specific presentation. Keep rendering driven by `pendingPrompt` and
`choose_prompt_option` legal moves.

Required prompt cases:

- `cancel_leader` reaction prompt:
  - title should make the reaction clear, e.g. `Cancel leader ability?`;
  - include public attempted leader name/ability when available;
  - option labels should read as player choices, e.g. `cancel` and `let it
    resolve`, not raw option IDs;
  - do not expose hidden card data.
- `restore_discard_to_hand`:
  - clarify that the card comes from your discard.
- `draw_opponent_discard`:
  - clarify that the card comes from the opponent discard.
- `discard_two_draw_one_from_deck`:
  - stage 1: clarify selecting one or two hand cards to discard;
  - stage 2: clarify selecting one card from your deck, then shuffle;
  - never reveal this deck-choice prompt to the opponent view.
- `look_three_cards`:
  - preserve the existing one-time reveal modal and acknowledgement flow;
  - make sure the surrounding prompt/action copy does not imply it can be
    reopened.
- `medic_revive`:
  - keep the existing selectable card presentation, but make the title/copy
    clearly identify Medic when it appears through the shared prompt surface.

If a prompt kind or ability is unknown, fall back to the current generic
presentation.

### 5. Styling Constraints

- Use existing authentic UI tokens and button classes where possible.
- No large typography inside compact score-card/action/prompt surfaces.
- Do not introduce card-in-card layouts.
- Do not create new decorative gradients/orbs.
- Keep mobile wrapping safe at 390px width.
- Do not change pre-game/deck-builder button styling in cEp9.

### 6. Hidden-Info Safety

Add direct assertions where practical:

- AI hand/deck identities remain hidden.
- Non-owner prompt state does not render hidden prompt option details.
- `look_three_cards` reveals only through the existing acting-seat modal.
- `discard_two_draw_one_from_deck` stage-2 deck options are not visible in the
  opponent view.
- Prompt labels do not include raw instance IDs.

## Out Of Scope

Do not implement:

- engine rule changes;
- new leader abilities;
- new card abilities;
- AI strategy upgrades;
- deck-builder, Card Studio, or official porting changes;
- new route promotion;
- board targeting overhaul;
- round/match-end modal redesign;
- animation redesign;
- broad responsive layout rewrite;
- legacy UI migration.

## Acceptance Criteria

- Score-card leaders clearly display active/passive/setup/used/suppressed
  states.
- `cancel_leader` suppression is legible on the affected leader for the current
  round and clears visually after round transition.
- Leader action controls remain legal-move-driven and dispatch exact engine
  targets.
- Prompt panels use ability-specific titles/copy for the required prompt cases.
- Hidden-info boundaries are preserved and covered by tests.
- `docs/PROJECT_STATE.md`, `docs/ui/authentic-product-flow.md`, and the phase
  report are updated.
