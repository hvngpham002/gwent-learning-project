## Context

`legal-heuristic-v1` now has three useful diagnostic layers:

- cFp25: hidden-info-safe decision traces.
- cFp26/cFp26.1: tie-aware pass/catch-up diagnostics.
- cFp27: hidden-info-safe mulligan diagnostics and conservative low-standalone redraws.

A new product playtest export motivated this phase:

```text

```

Important finding from that export:

- Human deck: `Official Skellige Starter`

- Earlier pass trace:
  - `decisionIndex: 23`

  - AI score: `108`
  - human score: `79`

The human overturned that position. The policy was too willing to treat a small lead above `requiredLead` as safe, especially if the AI's remaining hand shape was poor for a future must-win round. The current diagnostics do not tell us whether those four hidden AI cards were all special/weather/utility cards, but the candidate list shows multiple weather-like negative options and only broad hidden play labels. We need a safer pass gate and better aggregate hand-shape diagnostics.

## Goal

Make `legal-heuristic-v1` less likely to pass a marginally "safe" current round when doing so leaves it strategically dead in the next round.

The patch should:

1. Add hidden-info-safe hand-shape diagnostics to AI decision traces.
2. Make voluntary pass decisions consider hand quality and future-round viability.
3. Preserve last-gem catch-up-impossible pass behavior.
4. Preserve sensible pass behavior when the opponent has already passed.
5. Preserve selected-move parity between `explainLegalHeuristicV1Decision(input).move` and `legalHeuristicPolicyV1.selectMove(input)`.

## Required Implementation

### 1. Add Hidden-Info-Safe Hand Shape Analysis

Extend `src/game/ai/decisionTrace.ts` with a playing-decision hand-shape analysis field.

Preferred exported shape:

```ts
export type AiDecisionHandQuality = "empty" | "poor" | "thin" | "healthy";
export type AiDecisionTempoBucket = "none" | "low" | "medium" | "high";

export interface AiDecisionHandShapeAnalysis {
  readonly unitCardCount: number;
  readonly heroCardCount: number;
  readonly specialOrWeatherCardCount: number;
  readonly totalHandCount: number;
  readonly positiveUnitMoveCount: number;
  readonly positiveNonUnitMoveCount: number;
  readonly bestUnitTempoBucket: AiDecisionTempoBucket;
  readonly bestNonUnitTempoBucket: AiDecisionTempoBucket;
  readonly futureRoundHandQuality: AiDecisionHandQuality;
  readonly specialOnlyHand: boolean;
  readonly noUnitFutureRisk: boolean;
}
```

Exact field names may differ, but the exported information must be equivalent.

Definitions:

- `unitCardCount`: count of hidden own-hand cards with `kind === "unit"`.
- `heroCardCount`: count of hidden own-hand cards with `kind === "hero"`.
- `specialOrWeatherCardCount`: count of hidden own-hand cards with `kind === "special"` or equivalent weather/special kind in the existing observation model.
- `positiveUnitMoveCount`: count of own legal `play_card` candidates with a positive score and a source card classified as unit/hero unit-tempo.
- `positiveNonUnitMoveCount`: count of own legal `play_card` candidates with a positive score but not classified as unit/hero unit-tempo, such as Commander's Horn, Decoy, weather, or other specials.
- `bestUnitTempoBucket`: bucketized best positive unit/hero tempo.
- `bestNonUnitTempoBucket`: bucketized best positive non-unit tempo.
- `futureRoundHandQuality`:
  - `"empty"` when `totalHandCount === 0`;
  - `"poor"` when `unitCardCount === 0` and `totalHandCount > 0`;
  - `"thin"` when `unitCardCount === 1` and `totalHandCount >= 3`;
  - `"healthy"` otherwise.
- `specialOnlyHand`: `totalHandCount > 0 && unitCardCount === 0 && heroCardCount === 0 && specialOrWeatherCardCount === totalHandCount`.
- `noUnitFutureRisk`: `unitCardCount === 0 && totalHandCount > 0`.

Tempo bucket thresholds:

```ts
none: value <= 0 or null
low: 1..5
medium: 6..10
high: >= 11
```

Hidden-info rules:

- Broad aggregate counts are allowed in product diagnostic exports.
- Card names are not allowed.
- Source IDs are not allowed.
- Instance IDs are not allowed.
- Raw `cardIds` are not allowed.
- Raw `linkedSourceIds` are not allowed.
- Raw ability lists are not allowed.
- Candidate labels for hidden AI hand cards must remain `"hidden hand play"`.

### 4. Calibrate Voluntary Pass Safety With Hand Quality

Update the voluntary pass branch in `src/game/ai/legalHeuristicPolicyV1.ts`.

Do not change the last-gem catch-up-impossible branch except where it needs to consume the new shared helper without behavior changes.

Current behavior approximated from diagnostics:

```text
pass when scoreDelta >= requiredLead
```

New behavior should keep that baseline, but require extra safety margin when the AI's future hand quality is poor.

Required concepts:

```ts
passSafetyBuffer = scoreDelta - requiredLead
```

Apply a future-hand penalty only when all are true:

1. `passLegal === true`
2. `opponentPassed === false`
3. `isLastGem === false`
4. `scoreDelta >= requiredLead`
5. current pass would be voluntary, not forced

Recommended exact thresholds:

```ts
const poorFutureHandExtraBuffer = 18;
const thinFutureHandExtraBuffer = 10;
```

Decision rule:

- If `futureRoundHandQuality === "poor"`, voluntary pass requires:

```ts
scoreDelta >= requiredLead + poorFutureHandExtraBuffer
```

- If `futureRoundHandQuality === "thin"`, voluntary pass requires:

```ts
scoreDelta >= requiredLead + thinFutureHandExtraBuffer
```

- If `futureRoundHandQuality === "healthy"` or `"empty"`, existing voluntary pass behavior may remain:

```ts
scoreDelta >= requiredLead
```

Rationale:

- `"poor"` means the AI may be carrying no units into a future round. A small lead above `requiredLead` is not enough.
- `"thin"` means the AI has one unit in a larger hand, still risky but less catastrophic.
- `"empty"` means there is no future hand to preserve; the old pass rule is acceptable.

### 5. Prefer Useful Plays Over Marginal Poor-Hand Passes

When a poor/thin future hand blocks voluntary pass, v1 should select the best useful non-pass move under the existing scored-move ordering.

Requirements:

- If the best useful move has positive score, select it.
- Do not force negative weather/special plays solely to avoid passing.
- If no positive useful move exists, passing is allowed.
- The selected reason should make the branch legible in diagnostics, for example:

```text
future hand poor, pass margin too small - play useful card
```

or

```text
future hand poor, no useful move - pass
```

Exact wording may differ, but tests must assert a stable substring such as `"future hand"` or `"pass margin"`.

### 6. Preserve Opponent-Passed And Last-Gem Behavior

Add guard tests to ensure these paths are not broken:

1. If opponent has already passed and AI is ahead enough to win, AI may pass even with poor future hand.
2. If AI is on last gem and cannot reach the minimum score to win/tie the current round, AI still passes with `reasonKind === "policy-last-gem"` and `policyUpperBoundCanWinRound === false`.
3. If AI is on last gem and has a unit/hero move that can reach the minimum score to win/tie, AI plays it.
