# Implementation Spec: Cluster E, Phase 7 - In-Game Card Studio And Custom Catalog Workflow

## Goal

Build the first full in-game Card Studio for the authentic UI track.

cEp7 should let the user create custom cards and leaders inside the game UI, preview them with the authentic card components, validate them, save them in browser-local storage, import/export them as JSON, use playable custom cards/leaders in the deck builder, and start an engine-backed match with decks that reference those custom sources.

This phase must make custom cards actually playable when they use already-implemented engine abilities. It is not enough to build a decorative form.

## Product Decisions For This Phase

Use these decisions unless the user explicitly changes them later:

- Custom content is browser-local in cEp7.
- The browser never writes files into the repository.
- Card Studio supports JSON import/export for permanent backup and handoff.
- Permanent source catalog authoring remains a documented workflow: export JSON, place real images under `public/images/custom/...`, then a future coding phase or manual source commit can migrate records into `src/data/catalog/`.
- Draft cards/leaders with unimplemented abilities may be saved and previewed, but they must be blocked from playable decks and match start.
- Playable custom cards/leaders must use known, implemented ability IDs only.
- Image workflow supports both:
  - path-based images, recommended for permanent content, for example `/images/custom/my-card.png`;
  - local file upload preview/storage as a browser-local data URL, with size/type guards and clear warnings that it is localStorage-backed content.
- cEp7 includes normal cards and leaders:
  - unit cards;
  - hero cards;
  - special/weather cards;
  - leader cards.

## Architecture Position

Before this phase:

- `/` remains the legacy UI.
- `/?engine=1` remains the diagnostic engine shell.
- `/?engine=1&ui=authentic` opens authentic pre-game.
- `/?engine=1&ui=authentic&view=deck-builder` opens the catalog-backed browser-local deck builder.
- Current catalog cards/leaders come from `src/data/catalog/`.
- Deck builder local decks are stored under `gwent_authentic_decks_v1`.
- Engine match start can receive inline `CatalogDeckPreset` objects, but the runtime catalog used by selectors, legal moves, command execution, scoring, and AI remains mostly hardcoded to `currentCatalogCards` / `currentCatalogLeaders`.

After this phase:

- `/?engine=1&ui=authentic&view=card-studio` opens Card Studio.
- `AuthenticGameApp` owns both local deck store and local custom catalog store for the authentic flow.
- Card Studio can create/edit/delete/duplicate/import/export browser-local custom cards and custom leaders.
- Deck builder receives a merged source set of current catalog plus custom catalog sources.
- Pre-game can resolve and validate local decks that reference custom sources.
- Match start can pass the same runtime catalog source set into the Redux engine adapter.
- Engine adapter selectors, command execution, scoring, legal moves, and AI observation use the active match runtime catalog rather than the static source arrays whenever a custom catalog is present.
- Custom draft content remains visible in Card Studio, but cannot silently enter playable decks or match runtime.

## Scope

### 1. Custom Catalog Data Model

Add a browser-local custom catalog model that wraps catalog-compatible source records with authoring metadata.

Recommended files:

- `src/components/gwent/cardStudioTypes.ts`
- `src/components/gwent/cardStudioStorage.ts`
- `src/components/gwent/cardStudioValidation.ts`
- `src/components/gwent/cardStudioImportExport.ts`
- `src/components/gwent/cardStudioViewModel.ts`

Use different names only if the existing structure suggests something cleaner.

Recommended storage key:

```ts
gwent_custom_catalog_v1
```

Recommended schema:

```ts
interface CardStudioStoreV1 {
  readonly schemaVersion: "custom-catalog-v1";
  readonly cards: readonly CustomCardRecord[];
  readonly leaders: readonly CustomLeaderRecord[];
  readonly activeRecordId?: string;
}

interface CustomCardRecord {
  readonly recordId: string;
  readonly createdAt: string;
  readonly updatedAt: string;
  readonly source: CatalogCardSource;
  readonly imageMode: "path" | "data_url";
  readonly draft: boolean;
}

interface CustomLeaderRecord {
  readonly recordId: string;
  readonly createdAt: string;
  readonly updatedAt: string;
  readonly source: CatalogLeaderSource;
  readonly imageMode: "path" | "data_url";
  readonly draft: boolean;
}
```

Requirements:

- Records must be plain JSON-compatible objects.
- Do not persist runtime engine card instance IDs.
- Do not persist `Map`, `Set`, class instances, functions, or non-serializable browser objects.
- Normalize and validate on read so corrupted localStorage cannot crash the app.
- If localStorage is unavailable or write fails, keep an in-memory store for the session and show a compact warning.
- Preserve unknown-but-parseable records only if they pass enough validation to be edited safely. Otherwise skip them with a warning.
- Keep custom card and custom leader source IDs unique across:
  - current catalog cards;
  - current catalog leaders;
  - custom cards;
  - custom leaders.
- Prefer custom source IDs with a stable local namespace:

```txt
custom_<slug>
custom_leader_<slug>
```

- Use lowercase ASCII, numbers, and underscores only for cEp7 source IDs:

```txt
/^custom(_leader)?_[a-z0-9_]+$/
```

- Avoid colons in custom source IDs because engine runtime card instance IDs currently use colon-delimited strings.
- Auto-generate source IDs from names, but allow an advanced edit path before save.
- If import/create/duplicate would collide, auto-suffix source IDs and names conservatively and show a notice.
- Keep display names independent from source IDs.

### 2. Card Studio Route And Navigation

Add an authentic Card Studio route:

```txt
/?engine=1&ui=authentic&view=card-studio
```

Requirements:

- Extend `AuthenticUiView` in `src/appMode.ts`.
- Keep `/`, `/?engine=1`, authentic pre-game, direct match, deck builder, harness, and component foundation routes unchanged.
- Add entry points:
  - pre-game top/action area: `card studio →`;
  - deck-builder header/action area: `card studio →`;
  - Card Studio should have `← back` returning to the prior authentic surface when opened in-app, or pre-game when opened directly by URL.
- Keep `AuthenticGameApp` as the small route coordinator. Do not introduce a router dependency.
- Card Studio must share the same custom catalog store with deck builder and pre-game while the app is open.
- Returning from Card Studio must preserve browser-local deck and custom catalog state.
- Do not start or mutate an engine match from Card Studio directly. Play happens through deck builder/pre-game.

Visual direction:

- Use the current authentic parchment/table visual vocabulary.
- Keep text compact; this is an editor, not a landing page.
- Recommended layout:
  - top bar with `← back`, title `Card Studio`, import/export actions, and compact storage status;
  - left library column with tabs/filters for Cards, Leaders, Drafts, Playable, faction, and search;
  - middle editor form;
  - right preview/validation panel with live `AuthenticCard` or `AuthenticLeaderCard`, playability status, and issue list.
- Do not put cards inside nested decorative cards.
- Do not duplicate card names below card previews when the authentic card face already shows the name.
- Buttons should follow `docs/ui/authentic-button-style-guide.md`.

### 3. Card And Leader Editor Fields

Card editor must support:

- name;
- source ID;
- faction, including `neutral`;
- kind: `unit`, `hero`, `special`;
- strength;
- rows for unit/hero only;
- abilities from known `CATALOG_ABILITY_METADATA`;
- tags;
- deck limit;
- image path or uploaded image data URL;
- optional linked source IDs for Muster/Summon/Roach-style future relationships;
- optional description/flavor text.

Leader editor must support:

- name;
- source ID;
- non-neutral faction;
- leader ability from known `CATALOG_LEADER_ABILITY_METADATA`;
- image path or uploaded image data URL;
- optional description.

Requirements:

- Use structured controls:
  - listbox/segmented control for faction/kind;
  - row toggles for close/ranged/siege;
  - ability listbox or checkbox group;
  - numeric stepper/input for strength and deck limit;
  - text field for source ID/name/image path;
  - textarea only for description/import JSON.
- Source ID should default from the name and selected record type.
- Editing source ID after a card is already used in local decks is risky. For cEp7, either:
  - block source ID changes once saved and offer Duplicate instead;
  - or update all local decks that reference that source and show an explicit confirmation.
  Blocking saved source ID edits is recommended for this phase.
- Duplicating a card/leader must create a new source ID and name.
- Deleting a custom card/leader must require an authentic confirmation modal if any local deck references it.
- If deleting referenced content is confirmed, remove those references from local decks and show a notice.
- Do not permit deleting current built-in catalog cards/leaders from Card Studio.

### 4. Authoring Validation And Playability

Add Card Studio validation separate from permanent source catalog validation. It should be stricter about playability while still allowing drafts.

Required card validation:

- name is non-empty;
- source ID is non-empty, normalized, and unique across current + custom cards/leaders;
- faction is known;
- kind is known;
- strength is a non-negative integer;
- special cards have strength `0`;
- unit/hero cards declare at least one row;
- special cards declare no rows;
- rows contain only known rows and no duplicates;
- if a unit/hero declares more than one row, it must include `agile`;
- ability IDs are known;
- `none` cannot be mixed with any other ability;
- ability `appliesTo` must include the selected card kind;
- deck limit is an integer of at least `1`;
- heroes default to deck limit `1`, and if a hero tries to exceed `1`, block playability;
- image is either:
  - a non-empty path beginning with `/images/`;
  - or a supported browser-local data URL generated by the upload control;
- linked source IDs, if present, must exist in the merged current+custom card set or be clearly marked unresolved.

Required leader validation:

- name is non-empty;
- source ID is non-empty, normalized, and unique across current + custom cards/leaders;
- faction is known and non-neutral;
- leader ability ID is known;
- image is either `/images/...` path or supported data URL;
- description is optional.

Playability rules:

- A custom card is playable only when all structural errors are clear and every non-`none` ability has `status === "implemented"`.
- A custom leader is playable only when all structural errors are clear and its leader ability has `status === "implemented"`.
- Draft records with planned/placeholder abilities can be saved, previewed, exported, imported, and edited.
- Draft records must not be silently playable:
  - deck builder should either hide them from addable pool or show them disabled with a reason;
  - if an existing/imported local deck references a draft, validation must produce a blocking error;
  - match start must not proceed with a deck that references draft custom content.
- Existing current catalog planned/placeholder warnings should remain as they are today unless this phase explicitly touches that source. Do not accidentally make current catalog decks unplayable because built-in placeholder metadata exists.

Recommended validation output:

```ts
interface CardStudioIssue {
  readonly severity: "error" | "warning";
  readonly code: string;
  readonly field?: string;
  readonly message: string;
}
```

### 5. Image Workflow

Support both path-based and local upload image workflows.

Path mode:

- User enters a browser path such as:

```txt
/images/custom/my-card.png
```

- The preview should try that path and fall back through existing `AuthenticCard` / `SvgCardArt` behavior if the image is missing.
- Show concise guidance near the field:

```txt
Permanent images belong under public/images/custom/.
```

Upload mode:

- Accept at least PNG, JPEG, and WebP.
- Read the file with `FileReader` as a data URL.
- Store the data URL in the browser-local custom catalog record.
- Use the data URL for live preview, deck builder preview, and in-match card rendering.
- Add a size guard before storing. Recommended hard cap: 1 MB per uploaded image.
- Show a warning that uploaded images live in browser storage and should be exported/backed up.
- Do not upload files to a server.
- Do not write files to `public/images/` from browser code.

Export behavior:

- Exported JSON may include data URLs.
- Include a warning in docs that data URL exports can become large.
- Docs should explain how to convert a data URL/uploaded prototype into a permanent `/images/custom/...` path later.

### 6. Import / Export

Add JSON import/export for custom catalog content.

Required supported export shapes:

Single record:

```json
{
  "schemaVersion": "custom-catalog-record-v1",
  "record": {}
}
```

Bundle:

```json
{
  "schemaVersion": "custom-catalog-bundle-v1",
  "cards": [],
  "leaders": []
}
```

Requirements:

- Export selected record.
- Export all custom content.
- Copy selected/all JSON to clipboard.
- Import from pasted JSON.
- Import from file upload.
- Import must never overwrite existing records silently.
- If imported source IDs collide with current catalog or local custom content:
  - assign unique custom source IDs;
  - update intra-bundle `linkedSourceIds` that pointed at renamed imported cards;
  - show a notice listing the rename summary.
- Reject unknown schema versions with structured errors.
- Reject records that cannot be edited safely.
- Allow draft imports if they are structurally valid but not playable.
- Keep import/export logic pure and unit-tested outside React where practical.

Do not implement deck preset export changes in cEp7 unless needed to keep existing deck export working with custom references. The existing deck builder import/export may need to validate against the merged custom catalog, but Card Studio does not need to author generated deck presets in this phase.

### 7. Deck Builder Integration

Make custom playable content available in the existing deck builder.

Requirements:

- `AuthenticGameApp` should pass merged source sets into `AuthenticDeckBuilderScreen`.
- Refactor deck builder helpers to use explicit `DeckBuilderSourceSets` instead of defaulting to `currentCatalogCards` / `currentCatalogLeaders` in React paths.
- Existing unit helper defaults may remain for tests, but production deck builder/pre-game should pass explicit source sets.
- Deck builder pool should include:
  - current catalog cards;
  - playable custom cards matching deck faction or neutral;
  - optionally visible-but-disabled draft custom cards, if this can be done without clutter.
- Wrong-faction custom cards must remain hidden by the existing faction-aware filter.
- Custom cards at deck limit or blocked by special cap must use the same disabled state behavior as current catalog cards.
- Local deck validation must understand custom sources.
- Local deck validation must block custom draft/unplayable sources.
- Local deck validation must block decks whose custom leader is draft/unplayable.
- Existing local decks should not be deleted or corrupted if their custom references are missing; show a blocking validation error instead.
- Pre-game deck options must resolve local decks against the merged source set so custom decks can be selected when valid.
- If a local deck becomes invalid because a custom card/leader was deleted, pre-game must disable it with a clear reason.

### 8. Runtime Engine Catalog Support

This is the most important technical part of cEp7. Custom cards must enter the runtime engine catalog used by match setup, legal moves, command execution, selectors, scoring, and AI.

Requirements:

- Extend `StartEngineMatchOptions` and/or `AuthenticMatchSetupConfig` to carry the active runtime catalog:

```ts
{
  catalogCards: CatalogCardSource[];
  catalogLeaders: CatalogLeaderSource[];
}
```

  Use a different shape if cleaner, but preserve the idea: each match has an explicit source set.

- `createDefaultConfig` in `engineThunks.ts` must use the provided runtime catalog when resolving deck presets.
- `engineSlice` should store the active runtime catalog or a functionally equivalent serializable catalog snapshot in `EngineAdapterState`.
- `engineMatchStarted` should set that runtime catalog.
- `dispatchEngineCommand` must pass the active runtime catalog into `executeCommand`.
- `resolveEngineRoundEnd` must continue using the same active runtime catalog through `dispatchEngineCommand`.
- `engineSelectors.ts` must replace module-level static lookup maps with selectors based on the active runtime catalog.
- `selectEngineLegalMovesForHuman`, `selectEngineLegalMovesForAi`, score selectors, board/hand/discard/weather card view models, and leader status must all resolve custom source IDs.
- `getLegalHeuristicAiCommand` must use the active runtime catalog for:
  - `getLegalMoves`;
  - `buildSeatObservation`;
  - policy command conversion context if needed.
- Hidden-info behavior must not regress. A custom AI deck card must not appear in human-visible text until it is public.
- Headless simulation/export code does not need custom catalog support in cEp7 unless touched accidentally. Do not broaden simulation scope.

Implementation guidance:

- Avoid a global mutable custom catalog singleton.
- Keep the runtime catalog serializable and deterministic.
- Keep current default behavior unchanged when no custom catalog is provided.
- If storing full catalog arrays in Redux is too heavy, store a compact serializable runtime catalog object in the adapter state. Do not store functions or class instances.
- Update tests to catch any remaining hardcoded `currentCatalogCards` usage in engine adapter/authentic product paths that would hide custom cards during a match.
