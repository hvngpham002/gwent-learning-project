# Implementation Spec: Cluster B, Phase 1 - Catalog Schema And Identity Model

## Goal

Create the data foundation for future card population, deck builder work, Card Studio, and simulation. This phase defines catalog types, ability registry metadata, runtime identity concepts, and validators. It must not migrate the existing card data or change gameplay behavior yet.

## Scope

1. Add a new catalog module.
   - Suggested location: `src/game/catalog/`.
   - Keep it independent from React, Redux, DOM, and localStorage.
   - Export through an `index.ts`.

2. Define JSON-compatible source data types.
   - Card source identity:
     - `sourceId`
     - `name`
     - `faction`
     - `kind`
     - `strength`
     - `rows`
     - `abilities`
     - `tags`
     - `deckLimit`
     - `image`
     - optional `linkedSourceIds`
     - optional `description`
     - optional implementation/status metadata if useful.
   - Leader source identity:
     - `sourceId`
     - `name`
     - `faction`
     - `ability`
     - `image`
     - optional `description`.
   - Deck preset:
     - `presetId`
     - `name`
     - `faction`
     - `leaderSourceId`
     - `mainDeck: Array<{ sourceId; count }>`
     - `sideDeck: Array<{ sourceId; count }>`
   - Runtime identity:
     - `sourceId` is stable catalog identity.
     - `instanceId` is runtime identity generated when a deck is instantiated.

3. Define catalog constants and registry metadata.
   - Factions: Northern Realms, Nilfgaard, Monsters, Scoia'tael, Skellige, Neutral.
   - Rows: Close, Ranged, Siege.
   - Card kinds: Unit, Hero, Special.
   - Ability IDs covering current and planned abilities:
     - `tight_bond`
     - `medic`
     - `morale_boost`
     - `spy`
     - `muster`
     - `muster_roach`
     - `agile`
     - `avenger`
     - `scorch_close`
     - `scorch`
     - `skellige_storm`
     - `commanders_horn`
     - `decoy`
     - `frost`
     - `fog`
     - `rain`
     - `clear_weather`
     - `mardroeme`
     - `berserker`
     - `summon`
     - `none`
   - Leader ability IDs should cover the current `LeaderAbility` enum values.
   - Ability metadata should mark whether an ability is implemented by the current code, planned, or placeholder. This is metadata only; do not implement resolver behavior here.

4. Add validators.
   - Prefer small custom TypeScript validators over adding a runtime schema dependency unless you have a strong reason.
   - Validators should return structured errors rather than throwing for normal invalid data.
   - Include validation for:
     - duplicate `sourceId`;
     - missing required fields;
     - invalid faction;
     - invalid kind;
     - invalid row list for card kind;
     - invalid strength;
     - unknown ability ID;
     - unknown linked source ID;
     - invalid or missing image path string;
     - invalid `deckLimit`;
     - duplicate leader IDs;
     - deck preset references to missing cards or leaders;
     - deck preset counts below 1.

5. Add tests.
   - Add active passing tests for valid card, leader, and deck preset validation.
   - Add active passing tests for common invalid data:
     - duplicate IDs;
     - unknown ability;
     - missing linked source;
     - bad row/kind combination;
     - missing deck reference.
   - Existing Phase 0 tests must still pass.

6. Create the required implementation report:
   - `audit/reports/2026-04-24-cBp1-report.md`

## Out Of Scope

- Do not migrate current card definitions into the new catalog yet.
- Do not change `src/data/cards/*`.
- Do not change `src/utils/deckBuilder.ts` except for compile-only cleanup if truly necessary.
- Do not alter current gameplay, Redux state, AI behavior, UI behavior, or deck creation.
- Do not build Card Studio UI yet.
- Do not implement deck builder UI yet.
- Do not implement the pure game engine yet.
- Do not fix audit gameplay findings in this phase.

## Acceptance Criteria

- A catalog module exists and exports source-data types, constants, ability metadata, and validators.
- The model clearly separates `sourceId` from runtime `instanceId`.
- The model can represent current cards and known future cards without name-based hardcoding.
- Validators return structured errors suitable for Card Studio and future CLI/tooling.
- Tests cover both successful and failing validation paths.
- `npm test` passes.
- `npm run build` passes.
- Existing current gameplay code paths are not intentionally changed.

## Things To Watch Out For

- This phase is schema and validation only. Avoid "helpfully" converting existing card data; that belongs to the next phase.
- Keep the catalog JSON-compatible. Avoid functions, class instances, Sets, Maps, or non-serializable fields in source data.
- Do not reuse current runtime card `id` semantics as catalog identity. The audit found duplicate/lost-card risks around ID handling; the new model must be explicit about `sourceId` vs `instanceId`.
- Keep ability behavior out of card data. Card data may declare `abilities`, but resolver code comes later.
- Make validation errors easy to display in a future UI. Include at least a path/code/message shape.
- Keep imports stable with the current alias setup. Phase 0 added Vitest, so tests should use the same alias pattern if possible.
- If TypeScript strictness exposes old unrelated compile errors, make only minimal compile-only fixes and document them.
