# Implementation Spec: Cluster E, Phase 12 - Drag And Card-Flight Polish

## Intent

Make the authentic match table feel like a card game: players should be able to
drag playable hand cards onto visible legal destinations, and successful plays
should receive a restrained card-flight / arrival treatment.

cEp11 made the selected-card targets spatial and keyboard/click accessible.
cEp11.1 added browser coverage for weather targets and match-end ledger flow.
cEp12 should layer drag/drop and motion on top of that foundation without
changing rules, legality, command transactions, hidden-information behavior, or
the existing click/keyboard controls.

This is a product UI polish phase. The engine remains the only authority for
legal moves and state mutation.

## Scope

### 1. Drag Interaction Model

Add drag/drop as an enhancement to the existing cEp11 selected-card target
model.

Requirements:

- Drag may start only from visible human hand cards that are currently playable
  for the human seat.
- AI hand backs, AI deck, human deck, discard browsers, prompt cards, board
  cards, weather cards already in play, and leaders must not become draggable
  in cEp12.
- A simple click/tap without crossing a movement threshold must keep the current
  cEp11 behavior: select/deselect the hand card.
- Starting a drag should also select that card, so the same
  `buildSelectedCardTargetViewModel`-driven row/card/horn/weather targets are
  visible during drag.
- Drag must not compute legality from geometry. It may only dispatch a move id
  that came from the existing legal `PlayCardMove[]` / selected-card target view
  model.
- Invalid drop cancels cleanly and dispatches nothing.
- Escape cancels an active drag.
- Stale state cancels drag: if phase, prompt, turn, selected card, or legal
  move set changes while dragging, the drag preview should disappear and no
  stale move may dispatch.
- Right-click inspection on hand cards must still work and must never start a
  drag or dispatch a move.
- Do not add a drag/drop dependency unless the report justifies it. Prefer
  native pointer events and component-local state.

Recommended implementation shape:

- Keep click/keyboard targets as real buttons for accessibility.
- Add component-local drag state to `AuthenticMatchScreen.tsx` or a small
  extracted hook in `src/components/gwent/`.
- Use pointer events with a small threshold (for example 6-8 px) before
  entering drag mode.
- Use pointer capture or document-level pointer listeners carefully, cleaning
  them up on unmount/cancel.
- Track the active legal drop target by move id through target refs,
  pointer-enter/leave, or `document.elementFromPoint(...).closest(...)`.
  Whichever approach is used, the accepted drop must resolve to a legal move id
  supplied by the selected-card target view model.
- Add stable test IDs / attributes for drag state where needed, such as
  `authentic-drag-preview`, `data-drag-state`, and `data-drop-state`. Names may
  differ if they are documented in the report and browser tests use them.

### 2. Supported Drop Targets

Drag/drop must support every spatial target cEp11 renders:

- `board_row`: dropping a unit/Spy/etc. on the highlighted row target dispatches
  the exact legal `PlayCard` move for that row.
- `card_instance`: dropping a selected card such as Decoy on a visible legal
  board-card target dispatches the exact legal move for that visible card.
- `row_horn`: dropping Commander's Horn on a highlighted horn slot dispatches
  the exact legal horn move.
- `weather`: dropping a selected weather card on the Weather panel target
  dispatches the exact legal weather move.

Global/no-target card plays remain right-rail click/keyboard actions. Do not
invent a fake board or table drop target for Scorch or other global effects in
cEp12.

During drag:

- legal targets should use the same visual vocabulary as cEp11, with a clear
  hover/active state added for the current drop target;
- non-legal destinations should not look droppable;
- the right rail should keep useful copy, for example `drag to a highlighted
  row` / `drag to the weather panel`, but must not replace the existing
  accessible buttons.

### 3. Drag Preview

Render a polished, hidden-info-safe drag preview for the active human hand card.

Requirements:

- The preview should use the authentic card face for the human hand card being
  dragged.
- The original hand strip should not reflow while the preview moves.
- The preview should be `pointer-events: none` so it does not interfere with
  hit testing.
- The preview should track the pointer at a stable offset and stay above the
  board, hand, side rails, and modals.
- The active hand card should receive a subtle lifted/dragging state, but the
  card name and strength must remain legible.
- Cancelled drag should restore the normal hand state.
- Respect reduced motion: when `prefers-reduced-motion: reduce` is active,
  keep the preview usable but skip flourish animations.

### 4. Card Flight / Arrival Motion

Add restrained card-flight or arrival motion for successful plays.

Requirements:

- Motion is presentation-only. It must not delay or gate engine command
  dispatch, engine state mutation, AI action loops, round resolution, or prompt
  resolution.
- It is acceptable to use a short UI-only cleanup timer or animation-end handler
  for removing presentation overlays. Do not use timers for rule transitions.
- Human hand-card plays should show a card-face flight from the source hand card
  toward the accepted target when source and destination rectangles are
  available. If a rectangle is unavailable, fall back to the existing arrival
  pulse.
- Click/keyboard plays should get the same flight/arrival polish where
  practical; drag/drop should not be the only polished path.
- AI plays must not reveal hidden hand origin. AI played cards may receive a
  public arrival pulse once they are public on board/weather/discard, but do not
  animate a face-up card from an AI hidden hand.
- Medic/prompt revival, Scorch/discard, and existing `data-card-motion` pulse
  hooks should keep working. cEp12 may refine their arrival style, but should
  not try to fully animate every zone transfer.
- Decoy's full bounce/replacement choreography may be deferred if the hand-card
  flight and legal board-card drop are implemented. Document that deferral if
  chosen.
- Respect `prefers-reduced-motion: reduce` by disabling flight transforms and
  keeping only immediate state changes or a minimal non-motion highlight.

Recommended implementation shape:

- Capture source and target DOMRects immediately before dispatching a `PlayCard`
  move from click/keyboard or drop.
- Store a short-lived presentation record with the public card view model,
  from/to rectangles, move id, and a unique key.
- Render a fixed-position `authentic-card-flight` overlay above the match
  table. The overlay should not be interactive and should not expose hidden
  card data.
- Remove the overlay on animation end; use a fallback timeout only for cleanup.
- Keep existing `motionByCardId` event-derived arrival classes as the fallback
  for non-human or rectangle-less transitions.

### 5. Accessibility And Fallback Behavior

Drag/drop must not make the existing product path worse.

Requirements:

- All cEp11 click/keyboard targets remain native buttons and remain usable.
- Focus-visible styles remain clear on hand cards, row targets, board-card
  targets, horn targets, weather target, and right-rail fallback actions.
- Keyboard users can still select a hand card and activate legal targets with
  Enter/Space through the existing buttons.
- Mobile/touch users may keep using the existing tap/click target model. If
  touch dragging is implemented, it must not cause mobile overflow or accidental
  page scroll traps. If touch dragging is deferred, state that explicitly in the
  report.
- The UI should announce/label drag state in a minimal accessible way, such as
  an `aria-live` hint or updated right-rail copy. Do not add verbose on-screen
  tutorial text.
- Drag state must close context menus and must not open inspect modals.

### 6. Hidden-Info Safety

Add or keep assertions proving:

- AI hand backs are not draggable and do not expose card names/source IDs;
- drag preview exists only for human visible hand cards;
- page text after drag/drop does not include raw `instanceId`, raw `sourceId`,
  or `seat_a:NNN:` / `seat_b:NNN:` runtime identifiers;
- target labels remain based on public visible card names only.

Public `data-source-id` attributes on visible public cards are allowed for
tests, as in cEp11.1, but the visible rendered text must remain clean.

## Out Of Scope

- Engine rule, legal-move, scoring, prompt, round resolution, game-end,
  catalog, AI, simulation, or Redux adapter behavior changes.
- Route promotion or default-route changes.
- New deck-builder, Card Studio, official porting, pre-game, or mulligan
  behavior.
- A broad animation framework rewrite.
- Full AI card-flight from hidden hand.
- Full Decoy bounce choreography if the legal drag/drop path is implemented and
  the deferral is documented.
- Screenshot approval baselines.
- Drag/drop for board cards, discard cards, prompt option cards, leaders, or
  hidden zones.

## Acceptance Criteria

- A human playable hand card can be dragged to a legal board row target and
  dispatches the exact engine `PlayCard` move.
- Dragging a selected weather card to the Weather panel dispatches the exact
  legal weather move.
- Dragging a selected card to an invalid destination cancels without dispatching
  and without corrupting selection state.
- Click/keyboard targeting from cEp11/cEp11.1 still works.
- A restrained flight/arrival presentation appears for successful human card
  plays when DOMRects are available, with a safe fallback when they are not.
- Reduced-motion users do not get transform-heavy card-flight animation.
- Hidden-info browser assertions still pass.
- `docs/PROJECT_STATE.md`, `docs/ui/authentic-product-flow.md`,
  `docs/testing/browser-smoke.md`, and the phase report are updated.

## Required Tests

Add focused unit/component coverage where pure helpers are added. At minimum,
cover any new helper that maps legal targets, drag state, or flight plans.

Add Playwright coverage in `tests/e2e/engine-shell-smoke.spec.ts`:

- one smoke that drags a playable human hand unit to a highlighted board-row
  target and asserts `Human played`, board arrival, no raw hidden IDs, and no
  stale drag preview;
- one smoke that drags a weather hand card to `authentic-weather-target` using
  the cEp11.1 browser-local deck fixture approach, unless that fixture can be
  reused cleanly in the same test without making it brittle;
- one invalid-drop assertion, either as part of the row-drag smoke or a small
  separate smoke, proving no `Human played` event is added and the preview
  disappears;
- keep or update the existing cEp11/cEp11.1 click smokes so click targeting,
  weather click targeting, match-end ledger, and no-nested-interactive
  assertions still pass.
