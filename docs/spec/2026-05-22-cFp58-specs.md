## Summary

cFp56 stopped the current hand-tuned `legal-heuristic-v1` round-one tuning loop.
cFp57 made rating comparisons phase-aware by freezing current `ratings/latest`
artifacts as `cFp57` snapshots and proving all `cFp57-vs-latest` comparisons
are zero-delta.

The next master-plan step is search readiness, not another heuristic patch and
not immediate full ISMCTS. Batch A explicitly keeps search in scope but requires
determinization-risk measurement, hidden-info boundaries, variant separation,
and evaluation discipline before a benchmark search policy exists.

cFp58 is a design/readiness phase. It must produce a concrete search-readiness
decision note that defines what cFp59 should build first, what it must not
build yet, and how future determinized/ISMCTS/oracle search variants will be
kept legal-move-first and hidden-info safe.

This phase must not change AI behavior.

## Research Grounding

Use the Batch A search-baseline decision as controlling guidance:

- search is viable, but not as a product AI or strength claim yet;
- hidden-info-safe search starts from seat observation and legal moves, not raw
  full state by default;
- full-state oracle search is allowed only as explicitly unsafe benchmark/debug
  diagnosis;
- determinized search, ISMCTS, random rollouts, and oracle/debug variants must
  be reported separately;
- measure determinization risks before treating determinized search as a strong
  baseline.

Use the Batch B evaluation-ladder decision as the evaluation boundary:

- raw ledgers and fixed suites are source of truth;
- ratings are only one view over completed records;
- robustness probes are a later layer and must record observation contract,
  budget, and uncertainty.

Use cFp57 as the immediate input:

- rating artifacts now have named phase snapshots and comparisons;
- no current rating comparison justifies another heuristic patch;
- the next useful phase is search-readiness / ISMCTS probe design.

## Scope

- Create a search-readiness decision note that maps the current engine,
  simulation, benchmark, rating, and export infrastructure to Batch A
  search guardrails.
- Define the first future search probe family and the exact cFp59 build target.
- Define hidden-info-safe observation and determinization contracts for future
  search prototypes.
- Define branching/action-budget metrics and determinization-risk metrics.
- Define explicit variant labels for future search experiments.
- Update AI Lab/product policy metadata to cFp58 as a research planning phase.
- Update `docs/PROJECT_STATE.md`, the AI/ML roadmap, benchmark docs if useful,

Out of scope:

  scoring constants, pass rules, mulligan logic, leader logic, or diagnostics.
- Changing engine rules, legal moves, command execution, prompts, scoring,
  setup, catalog data, deck presets, benchmark suite definitions, failure
  mining, rating formulas, rating artifacts, generated benchmark records,
  product gameplay UI, product difficulty, or browser benchmark execution.
- Reading or exporting hidden private payloads.
- Running H100/Slurm jobs, local LLM jobs, or large search experiments.

## Required Decision Note

Create:

```text
docs/research/literature/ai/decisions/2026-05-22-cfp58-search-readiness-ismcts-probe-design.md
```

The decision note must be compact but concrete. It must include the sections
below.

### 1. Current Substrate Inventory

Table with at least these rows:

- deterministic engine command execution;
- legal move generation;
- `SeatObservation`;
- headless match simulation;
- batch benchmark suite runner;
- safe simulation export / action encoding;
- decision traces and diagnostics;
- failure mining;
- rating snapshots/comparisons.

For each row, state:

- current status;
- why it helps search;
- missing piece before cFp59/cFp60;
- hidden-info risk.

### 2. Search Variant Taxonomy

Define future variants with exact labels and safety class:

- `random-rollout-probe-v0`
- `determinized-pimc-probe-v0`
- `so-ismcts-probe-v0`
- `oracle-pimc-debug-v0`

For each variant, specify:

- hidden-info safety class: `safe`, `risky_requires_sampler`, or
  `unsafe_oracle_debug`;
- allowed input;
- forbidden input;
- intended use;
- not-to-claim warning.

If a different label is chosen, the note must explain why and keep the same
distinctions.

### 3. Observation And Determinization Contract

Define the future search input contract:

- root state starts from `SeatObservation` plus the acting seat's legal moves;
- search may not receive raw opponent hand identities or deck order in safe
  mode;
- own hand identities are allowed because they are visible to the acting seat;
- public board, public discard piles, weather, leader/faction, gems, round,
  passed status, and revealed prompt data are allowed;
- opponent hand count and deck count are allowed;
- decklist prior must be explicitly named:
  - `known_preset_decklist_prior` for benchmark starter suites;
  - `unknown_decklist_catalog_prior` for future custom-deck/product play;
- sampled worlds must be consistent with public counts and known/revealed
  information;
- oracle/debug mode must be a different variant and artifact path.

The note must identify whether the current code already exposes enough data for
safe sampling. If not, list the minimal public fields cFp59 should add.

### 4. Branching And Budget Metrics

Define metrics cFp59 should collect before implementing search strength:

- phase;
- round;
- acting policy id;
- faction;
- deck preset id;
- legal move count;
- move counts by kind;
- play-card source-card count;
- target expansion count;
- prompt-option count;
- mulligan-option count;
- commander horn / weather / row target counts if derivable safely;
- elapsed time per root-state profiling operation;
- deterministic seed;
- root-state public fingerprint.

These metrics must be hidden-info safe and should not include card names,
source IDs, runtime instance IDs, raw move labels, action refs, or command logs
unless the future spec explicitly justifies a safe public encoding.

### 5. Determinization-Risk Metrics

Define cFp59/cFp60 candidate metrics inspired by `long2010understanding`:

- outcome variance across sampled worlds for the same root;
- selected-action rank instability across sampled worlds;
- root-value variance by phase/faction/deck;
- determinization bias versus oracle/debug value, only in unsafe debug mode;
- information-set shrinkage / disambiguation proxy;
- action-union width;
- rollout-policy sensitivity.

Each metric needs:

- a one-sentence definition;
- whether it can be measured in safe mode now;
- what future data or code is required.

### 6. Recommended cFp59 Build Target

Make a clear recommendation for the next implementation phase. The default
expected recommendation is:

```text
cFp59 should implement a hidden-info-safe search-readiness profiler, not a
search-playing policy.
```

The profiler should likely:

- collect root-state branching metrics from existing headless benchmark runs;
- write deterministic public artifacts under the benchmark-results tree;
- include no search rollouts yet;
- update AI Lab metadata;
- produce cFp59 artifacts that can scope a later `determinized-pimc-probe-v0`
  or `so-ismcts-probe-v0`.

If the decision note recommends a different cFp59 target, it must explain why
that is still safer than implementing full search immediately.

### 7. Stop Conditions

The note must define stop conditions for future search implementation:

- if root legal-move branching is too high without pruning;
- if safe determinization cannot be implemented without hidden-info leakage;
- if prompt-stage states dominate the root sample and need separate handling;
- if runtime budgets exceed local 5080 / small academic compute targets;
- if oracle/debug results are being confused with safe policy results.
