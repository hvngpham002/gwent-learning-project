# Implementation Spec: Cluster B, Phase 2 - Current Card Migration And Card Studio Plan

## Goal

Migrate the existing card source data into the new catalog format, add validated default deck presets for the currently playable card set, and document a practical Card Studio workflow for future card authoring. This phase should make card population easier without changing live gameplay behavior unless the catalog output is proven equivalent and the change is explicitly small.

## Scope

1. Add catalog source packs for existing card data.
   - Suggested location:
     - `src/data/catalog/cards/neutral.ts`
     - `src/data/catalog/cards/northern-realms.ts`
     - `src/data/catalog/cards/nilfgaard.ts`
     - `src/data/catalog/leaders/northern-realms.ts`
     - `src/data/catalog/leaders/nilfgaard.ts`
   - Add placeholder empty packs for:
     - Monsters
     - Scoia'tael
     - Skellige
   - Add index exports so future phases can import all catalog packs from stable entry points.
   - Data may live in TypeScript modules for now, but it must remain JSON-compatible: plain arrays/objects, no functions, no Sets, no Maps, no class instances.

2. Migrate all existing source records, not only default-deck records.
   - Convert every card currently defined in:
     - `src/data/cards/neutral.ts`
     - `src/data/cards/northern-realms.ts`
     - `src/data/cards/nilfgaardian-empire.ts`
   - Include heroes, units, specials, and leaders.
   - Preserve existing names, strengths, rows, abilities, descriptions, and images where possible.
   - Map current enum values into catalog string IDs from `src/game/catalog`.
   - Use stable `sourceId` values, for example `neutral.geralt-of-rivia`.
   - Do not use current runtime `id` values as source IDs.

3. Add default deck presets.
   - Suggested location:
     - `src/data/catalog/deck-presets/current-northern-realms.ts`
     - `src/data/catalog/deck-presets/current-nilfgaard.ts`
   - Presets should reference `sourceId` plus count, not card names.
   - Presets should mirror the current playable default deck assembly as closely as possible.
   - If the catalog migration exposes cards that exist in source data but are currently omitted by `createInitialDeck`, document that in the report rather than silently changing live gameplay.
   - Include `sideDeck: []` for current presets so the shape is ready for future side-deck mechanics.

4. Add catalog loading/validation helpers.
   - Add a stable export that gathers current catalog cards, leaders, and presets.
   - Validate all migrated packs and presets with the Phase 1 validators.
   - If helpful, add a small helper that resolves a deck preset into `{ leader, mainDeck, sideDeck }` catalog source records. This helper should stay in catalog/data space and should not need to create current gameplay `Card[]` instances yet.

5. Add tests.
   - Validate all migrated catalog packs.
   - Validate all current deck presets.
   - Assert source IDs are unique across all migrated cards.
   - Assert deck presets reference existing cards and leaders.
   - Assert placeholder future faction packs are valid empty arrays or otherwise intentionally inert.
   - Add count/regression tests comparing the migrated catalog to the legacy source modules at a high level, for example total source records by pack and preset entry counts. Do not require active gameplay to use the catalog yet.

6. Add card-authoring documentation.
   - Add or update docs so a future maintainer knows:
     - where to put an image;
     - where to add card details;
     - how to choose `sourceId` and `assetSlug`;
     - how to add a card to a deck preset;
     - how to run catalog validation/tests.
   - Add a Card Studio implementation plan document covering:
     - form fields;
     - live validation;
     - image preview;
     - localStorage draft save;
     - JSON import/export;
     - unimplemented ability warnings;
     - deck-preset integration.
   - This is documentation/spec only. Do not build the Card Studio UI in this phase.

7. Create the required implementation report:
   - `audit/reports/2026-04-24-cBp2-report.md`

## Out Of Scope

- Do not implement Card Studio UI.
- Do not implement Deck Builder UI.
- Do not implement pure engine match state.
- Do not change Redux game state or live game flow.
- Do not fix audit gameplay bugs.
- Do not populate missing official cards beyond migrating current source data.
- Do not require all factions to be playable yet.
- Do not delete `src/data/cards/*`; legacy data stays until a later cleanup phase.
- Do not add file-write server endpoints for Card Studio.

## Acceptance Criteria

- Existing neutral, Northern Realms, and Nilfgaard source cards/leaders are represented in catalog-compatible packs.
- Empty placeholder packs exist for Monsters, Scoia'tael, and Skellige.
- Current Northern Realms and Nilfgaard deck presets exist and validate.
- Catalog validation passes for all migrated source packs and presets.
- Tests cover migrated catalog validation, uniqueness, preset references, and placeholder packs.
- Documentation explains exactly where to drop images and add card details.
- Card Studio implementation plan exists as a docs artifact.
- `npm test` passes.
- `npm run build` passes.
- Existing live gameplay behavior is not intentionally changed.

## Things To Watch Out For

- This phase is the bridge from hardcoded source files to catalog data. Keep it additive unless you can prove a live switch is behavior-equivalent.
- Some legacy card data may already be incomplete or inconsistent. Do not hide that. Document mismatches in the report.
- Do not "fix" the current default deck by adding cards the active game omitted unless explicitly scoped. The source catalog can contain all migrated records; the current deck preset should clearly state whether it mirrors current gameplay or a corrected future deck.
- Keep ability status metadata separate from rule correctness. A legacy implementation may exist but still be audited as buggy.
- Ensure all migrated data is serializable and exportable later.
- Watch image paths. Use the convention from `card-content-and-tools.md`, but preserve explicit legacy image paths if changing them would require moving assets.
- Do not commit generated build artifacts such as `dist/` or TypeScript build info files.
- If a validator is too strict for legitimate legacy data, report the mismatch and make a narrow schema decision rather than weakening validation broadly.
