# Implementation Spec: Cluster C, Phase 25 - Random Medic Passive Leader

## Intent

Implement the last focused Tranche 2 leader-rule member from
`docs/leader-ability-matrix.md`: `random_medic` for
`nilfgaard.emhyr-var-emreis-invader-of-the-north` (Emhyr var Emreis:
Invader of the North).

The settled post-cCp18 product decision overrides the stale "random Special
replay" text still present in parts of `docs/leader-ability-matrix.md`:

- `random_medic` is a **passive Medic mutation**, not an active leader.
- It does **not** replay a random Special card from discard.
- While this leader is the seat's leader, every **non-hero** Medic source
  controlled by that seat revives a random eligible non-hero Unit from that
  seat's own discard pile instead of opening a player-choice Medic prompt.
- Hero sources that have `medic` are unaffected and continue to use the normal
  prompt-based Medic behavior.

This phase should finish Tranche 2 leader behavior without introducing Tranche
3 or Tranche 4 surfaces.

Do not bundle `discard_two_draw_one_from_deck`, `draw_extra_card`,
`look_three_cards`, `cancel_leader`, UI prompt redesign, AI strategy tuning,
deck-builder work, Card Studio work, simulation/export schema work, or any
legacy UI migration.

## Rule Semantics For cCp25

### Leader Classification

`random_medic` is an implemented **whole-match passive**. It should be derived
from the acting seat's leader identity:

```text
state.seats[seatId].leaderSourceId === "nilfgaard.emhyr-var-emreis-invader-of-the-north"
catalog leader ability === "random_medic"
```

The leader must not emit a legal `use_leader` move.

The leader must not set `seat.leaderUsed`.

The leader must not emit `leader_used`.

Manual `UseLeader` attempts for this leader may keep the existing
unsupported-leader rejection path. They must not mutate state or consume the
leader.

### Source Scope

The passive applies when a Medic ability resolves for a seat that has the
`random_medic` leader policy and the Medic source is **not** a hero:

```ts
source.abilities.includes("medic") && source.kind !== "hero"
```

Examples:

- a normal Medic unit played from hand: random policy applies;
- a normal Medic unit revived by another Medic: random policy applies and can
  chain;
- a hypothetical hero source with `medic`: random policy does **not** apply,
  and normal prompt-based Medic behavior remains intact;
- a seat without the `random_medic` leader: normal prompt-based Medic behavior
  remains intact.

Do not special-case by faction. The leader identity controls the policy.

### Eligible Random Revival Candidates

The random candidate set is the acting seat's **own discard pile**:

```ts
state.seats[seatId].discard
```

Eligible:

- entries physically in the acting seat's discard pile;
- catalog source resolves;
- catalog source kind is exactly `unit`;
- non-hero by kind (`hero` is excluded);
- any unit ability is allowed: Medic, Spy, Muster, Morale Boost, Tight Bond,
  Berserker, Summon, Avenger, etc.;
- side-deck-only / generated non-hero units are eligible if they physically
  reached the acting seat's discard pile;
- off-owner non-hero unit cards are eligible if they physically sit in the
  acting seat's discard pile.

Not eligible:

- hero cards;
- specials;
- weather cards;
- leaders;
- opponent discard;
- hands;
- decks;
- side decks;
- removed-from-game;
- board rows;
- row horn slots;
- weather zone;
- stale discard entries whose instance or catalog source is missing;
- catalog unit sources with no playable rows.

Candidate order should preserve `state.seats[seatId].discard` order after
filtering. The random selection should be uniform over candidate **cards**, not
over row-expanded prompt options.

### Randomness And RNG State

Use the existing deterministic RNG pattern:

```ts
const rng = createSeededRngFromState(state.rng.seed, state.rng.state);
const chosen = candidates[Math.floor(rng.next() * candidates.length)];
state.rng.state = rng.getState();
```

Required behavior:

- if there are zero candidates: emit normal Medic `no_targets`, open no prompt,
  do not advance RNG;
- if there is exactly one candidate: choose it deterministically and do not
  advance RNG;
- if there are multiple candidates: choose with `rng.next()` and write
  `state.rng.state = rng.getState()`;
- identical seeds and identical pre-command states must choose the same card
  and produce the same post-state;
- different RNG states may choose different cards, but tests should not rely
  on statistical probability. Pick deterministic fixture seeds/states.

Do not shuffle any zone for `random_medic`.

Do not leak unchosen candidate IDs through hidden-info-sensitive summaries. Own
discard is public, but the event log should still only need to reveal the
actually revived public card.

### Row Placement

Normal Medic prompts can expose multiple row choices for multi-row units. The
`random_medic` passive removes player choice, so cCp25 uses a deterministic row
fallback after selecting the random card:

1. choose the random candidate card uniformly;
2. choose the first playable row from the card source using canonical row order:

```text
close -> ranged -> siege
```

This row policy is deliberately simple. Do not score-optimize the row and do
not add a prompt. If a future product pass wants smarter row placement, it can
change this policy explicitly.

Spy placement still follows normal Medic rules:

- if the revived source has `spy`, place it on the opponent's board side;
- otherwise place it on the acting seat's board side;
- in both cases, set `controller` to the acting seat and preserve immutable
  `owner`.

### Resolution Semantics

When a non-hero Medic source resolves under `random_medic`:

1. emit the normal `ability_triggered` event for `medic`;
2. build the eligible random candidate set from the acting seat's own discard;
3. if empty, emit `ability_resolved` for `medic` with `outcome === "no_targets"`
   and return;
4. choose the candidate as described above;
5. move the chosen card from discard to the target board row with existing
   `card_moved.reason === "medic_revive"`;
6. emit `card_played` for the revived card, just like normal Medic resolution;
7. emit `ability_resolved` for the Medic source with
   `outcome === "random_revived_card"`;
8. resolve the revived card's abilities normally through `resolveCardAbilities`;
9. run the existing Mardroeme settlement check if the revived card ends on a
   board row.

Do not emit `prompt_opened`.

Do not emit `prompt_resolved`.

Do not set `state.pendingPrompt`.

Do not hand off the turn inside the Medic helper. Preserve the existing
command-level handoff behavior: if no prompt is pending after all ability
resolution, `PlayCard` hands off normally.

### Chained Medic Semantics

If the randomly revived card is itself a non-hero Medic unit and the reviving
seat has the `random_medic` leader, that revived Medic should resolve under the
same random policy. This can chain until no eligible non-hero units remain in
discard.

The chain is finite because each revived card leaves discard before its
abilities resolve.

### Hero Medic Source Exception

If a hero source has `medic`, `random_medic` must not mutate that Medic effect.

For a hero Medic source:

- normal `buildMedicOptions` / `openMedicPrompt` behavior applies;
- if eligible targets exist, a `medic_revive` prompt opens;
- if no eligible targets exist, the normal `no_targets` outcome applies;
- no random selection occurs.

This must be covered with a test-local hero Medic fixture if the current
catalog does not contain one.

## Implementation Guidance

Prefer a small pure helper module:

```text
src/game/core/leaderRandomMedic.ts
```

Suggested exports:

```ts
export interface RandomMedicCandidate {
  readonly cardId: CardInstanceId;
  readonly sourceId: string;
  readonly row: CatalogRow;
  readonly boardSeat: SeatId;
}

export const hasRandomMedicPolicyForSeat = (...): boolean;
export const getRandomMedicCandidates = (...): readonly RandomMedicCandidate[];
export const chooseRandomMedicCandidate = (...): { candidate: RandomMedicCandidate | null; rngState?: number };
```

The exact names may differ, but keep these properties:

- helper reads only `state`, `seatId`, catalog cards/leaders, and source data;
- helper is deterministic and side-effect-free except for a clearly isolated
  chooser if you choose to expose one;
- helper filters candidate **cards** before choosing a row;
- helper preserves discard order before random selection.

Wire this through `src/game/core/abilities.ts` by updating `resolveMedic`.
Avoid duplicating the existing Medic board-placement and follow-up ability
resolution semantics more than necessary; where possible, factor a shared
internal helper so prompt Medic and random Medic cannot diverge on Spy
placement, `controller` reset, `card_played`, Mardroeme settlement, or chain
resolution.

Update `src/game/core/index.ts` if a new helper module should be exported for
tests.

Update `src/game/core/legalMoves.ts` only as needed for comments / passive
classification. `random_medic` should not add a `getLeaderMove` branch.

### Candidate Helper

- empty own discard returns no candidates;
- own discard with one regular unit returns one candidate;
- own discard with hero / special / weather entries returns no candidates for
  those entries;
- opponent discard entries are ignored;
- side-deck-only / generated non-hero units are included if physically in own
  discard;
- off-owner non-hero units physically in own discard are included with owner
  preserved later;
- stale missing-instance and missing-catalog-source entries are skipped;
- multi-row units appear once as a card candidate, not once per row.

### Random Resolution

- playing a non-hero Medic under Invader opens no prompt;
- with no eligible target, Medic emits `ability_resolved` / `no_targets` and
  hands off normally;
- with one eligible target, the target is revived without advancing RNG;
- with multiple eligible targets, the chosen target is deterministic from
  state RNG and `state.rng.state` advances;
- identical seed/state chooses the same target and produces the same post-state;
- selected target moves discard -> board with `card_moved.reason ===
  "medic_revive"`;
- selected target's `controller` becomes the acting seat;
- selected target's `owner` is preserved;
- selected non-Spy target lands on the acting board side;
- selected Spy target lands on the opponent board side and resolves Spy draw
  for the acting seat;
- selected Muster target resolves Muster after revival;
- selected Berserker target transforms if a Mardroeme is already on the chosen
  row;
- `ability_resolved` for the Medic source uses
  `outcome === "random_revived_card"` on success;
- no `prompt_opened` / `prompt_resolved` events are emitted for random Medic.

### Chaining

- if random Medic revives a non-hero Medic, the revived Medic also uses the
  random policy and can revive another eligible unit;
- chain stops cleanly when discard has no eligible non-hero units;
- no prompt is left pending after a pure random chain.

### Regression Guards

- normal Medic under a non-`random_medic` leader still opens the existing
  `medic_revive` prompt;
- cCp22 restore prompt still returns cards to hand only and does not trigger
  Medic;
- cCp24 draw-opponent-discard prompt still returns cards to hand only and does
  not trigger Medic;
- a test-local hero Medic source under Invader still opens the normal Medic
  prompt, proving hero Medic sources are unaffected.
