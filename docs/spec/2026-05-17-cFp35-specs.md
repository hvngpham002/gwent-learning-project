## Summary

cFp34 successfully created deterministic failure-mining artifacts, but the first report shows the next bottleneck is evaluator quality, not policy tuning. `suspicious_pass` dominates the artifact with 315 findings, and inspection shows the condition is too broad: many passes are flagged merely because `roundInvestmentAnalysis.stopLossRecommended === false`, which is normal for voluntary safe passes, preserve-future-hand passes, and some expected round sacrifices.

cFp35 calibrates the failure-mining layer so future v1 tuning starts from high-signal clusters. It must not change legal-heuristic-v1 behavior.

## Problem Statement

The current cFp34 artifact reports:

- 388 total findings.
- 315 `suspicious_pass` findings.
- 34 `round_three_low_resource` findings.
- 21 `weathered_row_play` findings.
- 10 `round_one_overinvestment` findings.
- 5 `medic_timing_risk` findings.
- 2 `matchup_skew` findings.
- 1 `deck_skew` finding.

The non-pass findings are coherent enough to guide future tuning, but the pass cluster is too broad. A huge noisy pass cluster will waste future agents' time and risks pushing cFp36 toward bad policy changes.

The concrete bug in the analyzer is this concept from cFp34:

```text
suspicious_pass if roundInvestmentAnalysis.stopLossRecommended === false
```

That condition alone is not suspicious. It only means the pass was not a stop-loss pass. A pass may still be correct because:

- the opponent already passed and v1 is ahead;
- `passAnalysis.isVoluntarilySafe === true`;
- `roundInvestmentAnalysis.recommendation === "preserve_future_hand"`;
- `roundInvestmentAnalysis.recommendation === "sacrifice_round"`;
- v1 is on a non-elimination round and the policy is intentionally preserving future resources.

## Goals

1. Calibrate `suspicious_pass` finding logic to reduce false positives.

4. Regenerate the failure-mining artifacts after calibration.

## Implementation Tasks

### 1. Calibrate `suspicious_pass`

Update `src/game/benchmark/failureMining.ts`.

The miner should only emit `suspicious_pass` when a pass contradicts the available safe diagnostics.

Emit `suspicious_pass` for selected pass traces when at least one high-signal condition is true:

1. `roundInvestmentAnalysis.recommendation === "continue"`.
2. `passAnalysis.hasSingleMoveCatchUp === true` and `roundInvestmentAnalysis.recommendation !== "preserve_future_hand"`.
3. `passAnalysis.policyUpperBoundCanWinRound === true`, `roundInvestmentAnalysis.recommendation === "fight_last_gem"`, and selected move is pass.
4. `passAnalysis.isVoluntarilySafe === false`, opponent has not passed if that field is available, and neither `preserve_future_hand` nor `sacrifice_round` applies.

Do not emit `suspicious_pass` solely because:

- `roundInvestmentAnalysis.stopLossRecommended === false`.
- `passAnalysis.isVoluntarilySafe === false` while `roundInvestmentAnalysis.recommendation === "preserve_future_hand"`.
- `passAnalysis.isVoluntarilySafe === false` while `roundInvestmentAnalysis.recommendation === "sacrifice_round"`.
- v1 is choosing a documented stop-loss/sacrifice pass.

If the existing trace lacks a field needed to distinguish opponent-passed state, do not guess. Use available safe fields and document the limitation in the report.

### 2. Track Suppressed Pass Candidates

Add a safe aggregate count for suppressed broad pass candidates. This is not a finding; it is instrumentation for the analyzer.

Examples of suppressed categories:

```text
preserve_future_hand_pass
sacrifice_round_pass
voluntary_safe_pass
stop_loss_pass
insufficient_context
```

Store only counts. Do not write raw traces.

### 3. Add Tuning Queue Builder

Add a deterministic tuning queue builder inside `failureMining.ts` or a small companion module.

A queue item should be safe and aggregate, for example:

```ts
export interface BenchmarkFailureTuningQueueItem {
  readonly rank: number;
  readonly clusterId: string;
  readonly title: string;
  readonly findingKinds: readonly BenchmarkFailureFindingKind[];
  readonly severity: BenchmarkFailureFindingSeverity;
  readonly count: number;
  readonly affectedDecks: readonly string[];
  readonly affectedFactions: readonly string[];
  readonly affectedMatchups: readonly string[];
  readonly recommendation: string;
  readonly suggestedNextSpecId: string;
}
```

Initial ranking guidance:

1. Highest priority: coherent behavior findings with direct policy implications.
2. Prefer clusters that appear in benchmark artifacts and product playtests.
3. Prefer clusters affecting multiple decks/factions over one-off cases.
4. Keep matchup/deck skew visible but do not treat it as a direct policy patch without behavior evidence.

Expected cFp35 tuning queue candidates:

- `round_resource_exhaustion`: combines `round_one_overinvestment` and `round_three_low_resource`.
- `weathered_row_low_tempo`: from `weathered_row_play`.
- `medic_no_target_timing`: from `medic_timing_risk`.
- `skellige_matchup_skew`: combines `deck_skew`, `matchup_skew`, and any Skellige-heavy resource findings.
- `remaining_suspicious_pass`: only after calibrated pass filtering.

The queue must be deterministic and sorted by rank, then cluster id.
