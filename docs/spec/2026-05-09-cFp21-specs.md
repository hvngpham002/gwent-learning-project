# cFp21 Specs - Benchmark Ledger And Fixed-Suite Harness

## Purpose

Build the first research-grade benchmark harness for Gwent AI
evaluation.

This phase turns the existing headless simulation batch runner into a
repeatable benchmark layer with:

- typed raw match-result ledger rows;
- fixed benchmark suites;
- deck/policy matchup definitions;
- optional mirrored seat/deck runs;
- deterministic aggregate summaries;
- hidden-info-safe default output;
- Glicko/TrueSkill-ready result schema for future phases.

This is the implementation-adjacent follow-up to:

- `docs/research/literature/ai/decisions/2026-05-09-batch-a-search-baseline.md`
- `docs/research/literature/ai/decisions/2026-05-09-batch-b-evaluation-ladder.md`

Batch B is the controlling decision note: raw result ledgers and fixed
matchup matrices come before ratings, search, or model training.

## Non-Negotiable Boundaries

- No engine rule changes.
- No legal-move semantics changes.
- No AI strategy upgrade beyond adding a deliberately simple benchmark
  baseline policy if needed.
- No UI, route, CSS, browser, deck-builder, Card Studio, or Official
  Porting changes.
- No filesystem writers yet. Keep benchmark output in memory.
- No Python tooling.
- No Glicko, TrueSkill, Elo, approximate best response, ISMCTS,
  determinized search, NFSP, Deep CFR, ReBeL, or model training in this
  phase.
- No raw `MatchState`, `cardsById`, command logs, full event logs,
  hand identities, deck order, or raw card instance IDs in default
  benchmark output.
- Debug/raw output may exist only if explicitly named unsafe/debug and
  excluded from default tests and summaries.

## Desired Architecture

Create a new benchmark layer rather than overloading the existing
simulation batch API.

Recommended module:

```text
src/game/benchmark/
  index.ts
  types.ts
  policies.ts
  suites.ts
  runBenchmark.ts
  ledger.ts
  summaries.ts
```

The benchmark layer should call into `src/game/sim` and the pure engine.
It should not make React/Redux/browser assumptions.

Keep the existing `runHeadlessSimulationBatch(...)` API backward
compatible. Existing tests must continue to pass.

## Implementation Requirements

### 1. Extend Headless Simulation Config Safely

The existing headless runner currently hard-codes current Northern
Realms vs current Nilfgaard decks in `createHeadlessSimulationConfig`.
Benchmarking needs explicit deck/faction/preset control.

Implement a backward-compatible extension such as:

```ts
interface HeadlessSeatSimulationConfig {
  seatId: SeatId;
  playerId?: string;
  controllerKind?: "ai";
  faction: CatalogFaction;
  deckPreset: CatalogDeckPreset;
}

interface HeadlessMatchSimulationInput {
  seed: string | number;
  maxSteps?: number;
  policies?: Partial<Record<SeatId, EnginePolicy>>;
  seats?: {
    seat_a: HeadlessSeatSimulationConfig;
    seat_b: HeadlessSeatSimulationConfig;
  };
}
```

Use the repo's actual catalog/faction types. The exact shape may differ
if the existing `MatchConfig` type gives you a cleaner path.

Acceptance criteria:

- `runHeadlessMatchSimulation({ seed })` remains unchanged and still
  uses current Northern Realms vs current Nilfgaard defaults.
- Benchmark code can run official starter deck presets without mutating
  `currentDeckPresets`.
- The catalog snapshot remains `currentCatalogCards` /
  `currentCatalogLeaders` unless explicitly passed later. Do not add
  custom catalog support in this phase.

### 2. Add A Minimal Benchmark Policy Registry

Create a small benchmark-facing policy registry.

Required policies:

- `legal-heuristic-v0`: existing policy.
- `legal-first-v0` or similarly named deterministic baseline:
  - choose prompt options deterministically by `moveId`;
  - keep all mulligan cards if legal;
  - otherwise choose the first legal move by stable `moveId`;
  - if no legal move exists, return `null`.

This is not a strategic AI improvement. It is a weak comparator to make
the benchmark matrix meaningful before `legal-heuristic-v1`.

If you add the baseline under `src/game/ai/`, export it normally. If you
keep it benchmark-local, document that it is not a product AI.

Do not add a "random" policy in this phase unless you can make it
deterministic without changing the `EnginePolicy` interface. A
deterministic weak policy is enough for cFp21.

### 3. Define Versioned Benchmark Types

In `src/game/benchmark/types.ts`, add versioned public types. Use names
close to these:

```ts
type BenchmarkMatchRecordSchemaVersion = "benchmark-match-v1";
type BenchmarkSummarySchemaVersion = "benchmark-summary-v1";

interface BenchmarkSeatDescriptor {
  seatId: SeatId;
  policyId: string;
  playerId: string;
  faction: CatalogFaction;
  deckPresetId: string;
}

interface BenchmarkMatchRecord {
  schemaVersion: "benchmark-match-v1";
  benchmarkRunId: string;
  suiteId: string;
  matchupId: string;
  seed: string | number;
  mirrorGroupId?: string;
  mirrorIndex?: 0 | 1;
  seats: Record<SeatId, BenchmarkSeatDescriptor>;
  status: SimulationTerminalStatus;
  winner: SeatId | "draw" | null;
  resultBySeat: Record<SeatId, "win" | "loss" | "draw" | "none">;
  roundWinsBySeat: Record<SeatId, number>;
  roundDraws: number;
  finalGems: Record<SeatId, number>;
  stepCount: number;
  commandCount: number;
  eventCount: number;
  averageLegalMoves: number;
  passCount: number;
  promptsResolved: number;
  leaderUses: number;
  replayStatus: "passed" | "failed" | "skipped";
  errorCode?: string;
  errorMessage?: string;
  stableFingerprint: string;
}
```

Adjust fields to match existing types, but preserve these properties:

- schema version;
- suite/matchup/run identity;
- seed;
- seat descriptors;
- status/winner/result;
- round outcome;
- validity metrics;
- replay status;
- stable fingerprint.

Do not include runtime `durationMs` in the deterministic fingerprint.
You may include runtime only as optional metadata if tests avoid exact
runtime equality.

### 4. Benchmark Suite Definitions

Create `src/game/benchmark/suites.ts`.

Required built-in suite:

```text
benchmark-smoke-v1
```

It should be small enough for unit tests and local CI. Use the existing
six simulation smoke seeds unless there is a clear reason to define a
separate short list.

The suite should include at least:

- `legal-heuristic-v0` vs `legal-first-v0`;
- current Northern Realms vs current Nilfgaard;
- mirrored seat/deck/policy run enabled.

Optional but useful:

- one official starter matchup smoke pair, still small enough for tests.

Do not create a large all-vs-all official starter tournament in cFp21.
The harness should support it later, but this phase should keep runtime
bounded.

### 5. Run Benchmark API

Implement a pure in-memory API similar to:

```ts
runBenchmarkSuite(input?: {
  suiteId?: string;
  suite?: BenchmarkSuite;
  maxSteps?: number;
  includeDebugResults?: boolean;
}): BenchmarkRunResult
```

The result should include:

- suite metadata;
- ordered raw `BenchmarkMatchRecord[]`;
- deterministic summary;
- diagnostics for failures;
- no raw state by default.

The API should continue after per-match policy failures, engine errors,
or max-step failures and report them in the ledger and summary.

### 6. Ledger Conversion

Create a conversion helper that maps a
`HeadlessMatchSimulationResult` plus benchmark context into
`BenchmarkMatchRecord`.

Implementation details:

- Determine `resultBySeat` from `winner`.
- Determine `roundWinsBySeat` / `roundDraws` from `finalState.roundHistory`
  internally, but do not expose card identities from that state.
- Use existing replay diagnostics where possible.
- Generate a stable fingerprint from non-hidden, deterministic fields:
  status, winner, round result summary, command/event type fingerprint,
  deck/policy ids, seed, and key counts.
- Do not place raw `finalState`, raw `commandLog`, raw `events`, raw
  `steps`, card instance IDs, hand arrays, or deck arrays on the
  default record.

### 7. Summaries And Matrices

Create deterministic summaries over benchmark records.

Minimum summary fields:

- total matches;
- status counts;
- completion rate;
- max-step rate;
- error code counts;
- replay checked / failed counts;
- policy ids involved;
- deck preset ids involved;
- matchup summaries;
- win/loss/draw counts by policy id;
- win/loss/draw counts by deck preset id;
- average steps/commands/legal moves;
- prompt and leader-use counts.

The summary should support stratification. You do not need a perfect
data cube, but avoid one unlabeled aggregate that hides deck/faction or
suite identity.

Recommended shape:

```ts
interface BenchmarkMatchupSummary {
  matchupId: string;
  totalMatches: number;
  statusCounts: Record<SimulationTerminalStatus, number>;
  resultCountsByPolicy: Record<string, { wins: number; losses: number; draws: number; none: number }>;
  resultCountsByDeck: Record<string, { wins: number; losses: number; draws: number; none: number }>;
  averageSteps: number;
  averageLegalMoves: number;
}
```

### 8. Hidden-Info Safety Tests

Add tests that stringify the default benchmark result and assert it does
not contain:

- `cardsById`
- `finalState`
- `commandLog`
- `"hand"`
- `"deck"` arrays
- `ownHand`
- `opponentHand`
- raw `seat_a:` / `seat_b:` card instance prefixes if those prefixes
  are used in engine instance IDs

It is acceptable for deck preset IDs such as
`current-northern-realms` to appear. The forbidden content is hidden
runtime card identity/order and raw engine state.

### 9. Tests

Add focused tests under `tests/game/benchmarkHarness.test.ts` or a
similarly named file.

Required test coverage:

- built-in suite resolves by id;
- default benchmark smoke suite returns records and summary;
- repeated runs produce the same stable records/summaries, excluding
  runtime fields if any;
- mirrored suite creates two records per seed with swapped seat
  descriptors;
- policy failures are recorded per match and do not abort the suite;
- custom/current deck preset selection reaches the headless runner;
- default output is hidden-info safe;
- summary includes status counts, result counts by policy, result counts
  by deck, replay diagnostics, average counts, and involved ids;
- existing `runHeadlessSimulationBatch` tests still pass unchanged.

## Acceptance Criteria

The phase is complete when:

- `runBenchmarkSuite(...)` exists and returns typed in-memory ledger
  records plus deterministic summaries.
- The built-in `benchmark-smoke-v1` suite runs at least
  `legal-heuristic-v0` versus a deterministic weak baseline over a
  current-deck matchup.
- Mirrored seat/deck/policy runs are supported and tested.
- The default benchmark output is hidden-info safe.
- Existing simulation batch APIs remain backward compatible.
- Documentation and report are updated.
- Required tests/checks pass or any failure is clearly explained as
  unrelated/pre-existing.

## Out Of Scope

- ISMCTS / determinized search

- Elo
- ML export tensorization
- Python notebooks

- Browser UI
- Product difficulty tiers
- Human-in-the-loop evaluation
- Any rule or catalog behavior change
