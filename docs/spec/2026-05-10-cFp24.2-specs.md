# cFp24.2 Specs - Legal Heuristic v1 Pass Safety Patch

## Purpose

Fix the first serious human-playtest issue in `legal-heuristic-v1`:
overconfident voluntary passing while ahead, especially when the AI is on
its last gem and the human has a large hand.

cFp24 introduced v1 as a benchmark-only policy. cFp24.1 exposes it as an
experimental product playtest policy. The first real human playtest found
that v1 is too comfortable passing after a large early Muster play:

- Round 1: AI played Crones, got ahead, then passed while Human had a
  very large hand from Spy plays.
- Human spent several cards and won the round.
- Round 2: AI was on its last gem, played Arachas, got ahead, then
  passed again while Human still had many cards.
- Human closed the match.

The narrow bug is not the legal-move boundary. The engine remains
rules-correct. The policy's pass heuristic is too blunt and must be made
more conservative.

## Current Failure

The current policy contains this voluntary-pass branch in
`src/game/ai/legalHeuristicPolicyV1.ts`:

```ts
if (passMove && features.scoreDelta > 12 && features.ownHandCount < features.opponentHandCount) {
  return passMove;
}
```

That rule was meant to preserve card economy when the AI is ahead and
down on cards. In practice, it treats opponent card advantage as a reason
to pass instead of a danger signal.

It is especially bad on the AI's last gem. A lead of 18-30 points is not
safe when the opponent has 9-12 cards and the AI still has playable
cards. Passing in that state is functionally a surrender that gives the
opponent a deterministic path to close the match.

## Required Behavior

### Preserve Safe Existing Passes

Keep these behaviors:

1. If the opponent has passed and v1 is ahead, v1 may pass.
2. If v1 is behind on its last gem and the visible immediate upper-bound
   estimate cannot catch the opponent, v1 may pass/surrender.
3. If there is no useful playable card or leader move, v1 may pass.

### Replace The Blunt Ahead-By-12 Rule

Remove or heavily constrain the current branch:

```ts
features.scoreDelta > 12 && features.ownHandCount < features.opponentHandCount
```

Replace it with a named helper, for example:

```ts
const canVoluntarilyPassWithLead = (features: LegalHeuristicV1Features) => ...
```

The helper should treat opponent hand size as pressure, not permission.

Minimum expected behavior:

- If `features.ownGems <= 1`, v1 should not voluntarily pass just
  because it is ahead and down on cards.
- If `features.opponentHandCount >= 8`, v1 should require a very large
  safety margin before voluntarily passing.
- A score lead around 18-30 is **not** safe when the opponent has 9-12
  cards and v1 has useful playable moves.
- v1 should prefer a useful play over pass in that state.
- The policy should remain deterministic.

Recommended shape:

```ts
const estimateOpponentHandPressure = (features: LegalHeuristicV1Features) => {
  const perCardPressure = features.ownGems <= 1 ? 8 : 6;
  return features.opponentHandCount * perCardPressure;
};

const canVoluntarilyPassWithLead = (features: LegalHeuristicV1Features) => {
  if (features.scoreDelta <= 0) return false;
  if (features.opponentPassed) return true;
  const pressure = estimateOpponentHandPressure(features);
  const requiredLead = Math.max(features.ownGems <= 1 ? 36 : 24, pressure);
  return features.scoreDelta > requiredLead;
};
```

This is a suggested shape, not a hard requirement. The implementation may
choose slightly different constants if tests make the intent clear. Keep
the helper simple and documented; do not simulate unknown hands.

### Last-Gem Rule

On the AI's last gem:

- v1 may still surrender/pass if it is behind and cannot catch up.
- v1 may pass after the opponent has already passed and v1 is ahead.
- v1 should generally **not** voluntarily pass while the opponent is
  still active and has many cards, unless the lead is far beyond a
  pessimistic hand-pressure estimate.

This specifically addresses the observed Round 2 failure.

### Card-Disadvantage Rule

Card disadvantage alone should not trigger a voluntary pass. It may be
one input into a safety helper, but a large opponent hand should increase
the required safety margin.

## Tests Required

Update `tests/game/engineAiPolicy.test.ts` with focused unit tests using
synthetic `EnginePolicyInput` where possible. Do not rely on a fragile
full-match seed unless there is already a stable helper for it.

Required cases:

1. **Regression: last gem, ahead, opponent has many cards**
   - v1 seat has `ownGems: 1`.
   - v1 is ahead by roughly 18-30 points.
   - opponent has at least 9 cards.
   - v1 has at least one useful playable unit move.
   - Expected: v1 does **not** choose `pass`.

2. **Regression: round 1-style large human hand**
   - v1 seat has more than 1 gem.
   - v1 is ahead by roughly 18-30 points.
   - v1 has fewer cards than opponent.
   - opponent has at least 10-12 cards.
   - v1 has at least one useful playable unit move.
   - Expected: v1 does **not** choose `pass`.

3. **Safe existing behavior: opponent already passed**
   - opponentPassed is true.
   - v1 is ahead.
   - Expected: v1 chooses `pass`.

4. **Safe existing behavior: impossible last-gem catch-up**
   - v1 has `ownGems: 1`.
   - v1 is behind.
   - useful upper-bound cannot exceed opponent score.
   - Expected: v1 chooses `pass`.

5. **Large enough voluntary lead can still pass**
   - opponent has a small hand or v1 has an overwhelming lead.
   - v1 is ahead by more than the helper's safety threshold.
   - Expected: v1 may choose `pass`.

Optional but useful:

- Add a test name that references the human playtest shape:
  `"does not pass on last gem just because it is ahead while opponent has a large hand"`.

## Acceptance Criteria

- The blunt `scoreDelta > 12 && ownHandCount < opponentHandCount`
  voluntary-pass rule is removed or replaced with a safety helper that
  treats opponent hand size as pressure.
- v1 does not voluntarily pass on last gem while merely ahead by roughly
  18-30 points against an active opponent with 9+ cards and useful v1
  moves available.
- v1 does not voluntarily pass in the Round 1-style shape where it is
  ahead by roughly 18-30, down on cards, and the opponent has 10-12
  cards with useful v1 moves available.
- v1 still passes when the opponent has already passed and v1 is ahead.
- v1 still passes/surrenders when behind on last gem and unable to catch
  up by visible immediate upper bound.
- No engine rules, legal moves, UI, routes, adapter shape, deck data,
  policy selector behavior, or hidden-info boundaries change.
- Tests and docs are updated.
- `audit/reports/2026-05-10-cFp24.2-report.md` exists with the required
  sections.
