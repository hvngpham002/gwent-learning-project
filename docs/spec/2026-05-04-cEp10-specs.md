# Implementation Spec: Cluster E, Phase 10 - Round And Match Flow Polish

## Intent

Make round resolution, match conclusion, and post-match navigation feel like a
coherent product flow in the authentic UI.

cEp9 made leader and prompt state legible. cEp10 should do the same for the
round/match lifecycle:

- resolving a round should be visibly distinct from playing the round;
- the round-resolved ledger should explain score, gem loss, next starter, and
  next action clearly;
- match-end should show a compact real round history and real match standing;
- rematch/change-deck/close navigation should be predictable;
- no UI code should compute rule outcomes or advance rules with timers.

This is a product UI phase. The engine already owns pass, round-end legal
moves, scoring, gem loss, cleanup, game end, and next-round state.

## Scope

### 1. Round And Match Ledger View Models

Extend or replace the current round overlay view-model helpers in
`src/components/gwent/matchViewModel.ts`.

Current component-local logic in `RoundOverlay` should move into pure
view-model helpers where practical. Keep React rendering mostly declarative.

Required view-model outputs:

- round overlay key that cannot collide across match runs if the existing state
  already exposes a match/run key; otherwise document why `round-N` remains
  sufficient;
- round number;
- `kind`: `"round"` or `"match_end"`;
- eyebrow;
- title;
- summary rows for round-resolved state:
  - your score;
  - opponent score;
  - each gem loss as `◆ before -> after` where data is available;
  - `gem loss: none` when no one loses a gem;
- next starter label for non-game-end rounds;
- match-end round-history rows:
  - round number;
  - your score;
  - opponent score;
  - result marker (`win`, `loss`, `draw` or a compact display equivalent);
- match-end standing rows from real engine state only:
  - result (`victory`, `defeat`, `draw`);
  - rounds (`humanWins - aiWins`);
  - gems (`humanGems - aiGems`) when available;
- action view models:
  - non-game-end: one primary `next round ->`;
  - game-end with setup callback: `change deck` ghost + `rematch` primary;
  - game-end without setup callback: `close` ghost + `rematch` primary.

Do **not** add fake ranked/MMR/streak data.

Do **not** derive scores, winner, gem loss, or next starter from board cards in
React. Consume `RoundResult`, `roundHistory`, `winner`, current public seat gem
counts, and existing selector/view-model data only.

### 2. Round-End Action State

Refine the right-rail round-end action area in `AuthenticMatchScreen.tsx`.

Requirements:

- When both players have passed and the engine exposes a legal
  `resolve_round_end` move, show one clear primary action.
- The action label should remain compact, e.g. `resolve round`.
- Dispatch the existing `resolveEngineRoundEnd(humanSeat)` / exact engine
  transaction path. Do not compute score or mutate match state in UI.
- If the match is not in `round_end`, do not render stale round-end action
  copy.
- If `canResolveRound` is false, explain the disabled state in existing compact
  right-rail copy only if the action is visible. Do not introduce a second
  action panel.

### 3. Round-Resolved Ledger Behavior

Polish the non-game-end round ledger.

Requirements:

- Use the existing authentic `Alert` ledger direction, not browser alerts.
- Keep the ledger modal over the current match table.
- The round result should read clearly at a glance:
  - victory: `You hold the field.`
  - loss: `<opponent> holds the field.`
  - draw: `Neither side yields.`
- Include a compact score table and gem-loss rows.
- Include the next starter label when the engine provides it.
- `next round ->` only dismisses the overlay. It must not dispatch engine
  commands, start timers, or re-resolve anything.
- Overlay dismissal must not hide or mutate the actual engine round history.
- Overlay should not reopen after dismissal for the same resolved round.
- Returning to setup/rematch/new match must clear any stale dismissed-overlay
  cache.

### 4. Match-End Ledger Behavior

Polish game-end presentation and navigation.

Requirements:

- Use the ledger/crown presentation, not a separate page or browser dialog.
- Match title:
  - human win: `Victory over <opponent>.`
  - AI win: `Defeat against <opponent>.`
  - draw: `Draw.`
- Eyebrow format should remain compact and real, e.g.
  `match concluded · 2 to 1`.
- Round history must use real `roundHistory` entries and must not invent rows.
- Standing must use real engine state only:
  - result;
  - rounds;
  - gems.
- Do not show MMR, rank, streak, ladder, reward, XP, or progression rows.
- `rematch` should restart the same setup and seed behavior currently used by
  `startNewGame`, and should route through mulligan.
- `change deck` should return to pre-game/setup when `onReturnToPreGame`
  exists. It should not show the abandon warning after a completed game.
- Direct `view=match` / no setup callback should show `close` instead of
  `change deck`; closing should dismiss the ledger without inventing a main menu.
- Game-end dismissal should leave the final match state inspectable.

### 5. Accessibility And Interaction

Improve overlay behavior without broad modal rewrites.

Requirements:

- Round and match ledgers must keep `role="dialog"` and `aria-modal="true"`.
- The dialog must have an accessible name tied to the ledger title.
- `Escape` should dismiss a non-game-end round ledger.
- For match-end ledgers, `Escape` may dismiss only if the same result is still
  reachable through visible navigation; otherwise keep explicit buttons only.
  Document the choice in the report.
- Clicking outside should not accidentally dispatch a gameplay command. It may
  dismiss only if implemented consistently with existing authentic modal
  behavior.
- Button styling must use the existing authentic button/alert conventions.
- Keep text compact and mobile-safe at 390px width.

### 6. Hidden-Info Safety

Add assertions where practical:

- Round/match ledgers do not render hidden AI hand/deck card names, source IDs,
  or instance IDs.
- Round history and standing expose only public scores, gem counts, round
  results, and public labels.
- The battle log/recent activity remains hidden-info-safe after round
  resolution and game end.
- Direct match route and product pre-game route both keep AI hidden zones
  backs/count-only.

## Out Of Scope

Do not implement:

- engine rule changes;
- scoring, gem, round-result, or game-end recomputation in UI;
- timers for round or match transitions;
- AI strategy changes;
- deck-builder, Card Studio, official porting, or catalog edits;
- default-route promotion;
- ranked/MMR/progression/reward systems;
- full main-menu route;
- board targeting or drag/drop overhaul;
- new match modes;
- broad animation redesign.

## Acceptance Criteria

- Round-end action remains engine/legal-move-driven.
- Non-game-end round ledger clearly shows outcome, scores, gem loss, next
  starter, and one `next round ->` dismissal action.
- Match-end ledger clearly shows outcome, real round history, real standing,
  and correct `rematch` / `change deck` / `close` navigation.
- Round overlay dismissal does not mutate engine state and does not reopen for
  the same round.
- Rematch and setup/change-deck clear stale overlay state and return through
  the expected authentic flow.
- No hidden AI hand/deck identities are rendered.
- `docs/PROJECT_STATE.md`, `docs/ui/authentic-product-flow.md`, and the phase
  report are updated.
