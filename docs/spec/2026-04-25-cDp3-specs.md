# Implementation Spec: Cluster D, Phase 3 - Engine UI Human Card Play V1

## Goal

Enable the opt-in engine shell to play human cards through the pure engine. Cluster D Phase 2 proved startup, mulligan, scripted preview AI pass, round resolution, and game-end display. Phase 3 should turn the human hand from display-only into a legal-move-driven card play surface.

The target is not a polished final board interaction model. The target is a correct, reviewable vertical slice: select a human hand card, show its engine-provided legal `play_card` targets, dispatch the exact `PlayCard` command, render the resulting board/score/prompt state from engine selectors, and keep every rule transition inside the engine.

## Architecture Position

Current engine shell behavior:

- legacy UI remains default;
- engine UI is opt-in through `?engine=1` or `VITE_ENGINE_UI=1`;
- engine shell starts a current catalog match;
- human and scripted preview AI can mulligan;
- scripted preview AI passes only;
- human can pass;
- round end resolves through `ResolveRoundEnd`;
- generic prompts render if engine state opens one;
- ordinary card play is out of scope and disabled/display-only.

Phase 3 should add human card play to the engine shell only. Do not touch legacy gameplay except compile fallout if unavoidable.

## Scope

1. Drive card play from engine legal moves only.
   - Use `selectEngineLegalMovesForHuman` as the source of truth.
   - Do not write local row legality, weather legality, Horn slot legality, Spy targeting, Decoy targeting, Medic targeting, or pass rules in React.
   - Do not import:
     - `src/utils/gameHelpers.ts`;
     - legacy `gameSlice`;
     - legacy `gameThunks`;
     - legacy `gameSelectors`;
     - `useReduxAI`;
     - legacy `GameBoard`.
   - Do not branch on card ability for rule outcomes. Ability labels are fine; legality and execution must come from engine moves.

2. Add selected-card play state.
   - Reuse or extend `engineSlice` UI-only selection state.
   - It is acceptable to replace `selectedCardIds` with a clearer shape if backward-compatible tests are updated.
   - Suggested state:
     ```ts
     selectedCardId: CardInstanceId | null;
     selectedCardIds: CardInstanceId[]; // still useful for mulligan
     selectedMoveId: string | null;
     ```
   - During mulligan, keep multi-card selection behavior from Phase 2.
   - During playing, card selection should be single-card.
   - Clear play selection after:
     - successful `PlayCard`;
     - `Pass`;
     - `ResolveRoundEnd`;
     - `ChoosePromptOption`;
     - `New Game`;
     - phase changes where the selected card is no longer in human hand.

3. Mark playable human hand cards.
   - A human hand card is playable when at least one legal move exists with:
     - `move.kind === "play_card"`;
     - `move.sourceCardId === card.instanceId`.
   - Only allow selection during `playing`, when the human can act and no prompt blocks ordinary play.
   - Non-playable cards should remain visible but disabled or visually muted.
   - The UI should clearly indicate the selected card and the number/type of available targets.

4. Render target actions from legal move metadata.
   - For the selected card, render one action per legal `play_card` move.
   - Prefer using `move.label` and `move.metadata.targetLabel` for display.
   - Include compact target metadata in the button text where useful:
     - own/opponent side;
     - row name;
     - weather/global target;
     - target card name for card-instance targets when available.
   - Do not require spatial board clicks in this phase. A target action panel is acceptable and safer.
   - If spatial row highlighting is added, it must still dispatch the exact legal move selected from the engine list.

5. Dispatch exact `PlayCard` commands.
   - Clicking a target action dispatches:
     ```ts
     dispatchEngineCommand({
       type: "PlayCard",
       seatId: humanSeat,
       cardId: move.sourceCardId,
       target: move.target,
     })
     ```
   - Do not reconstruct the target object manually from UI labels.
   - Do not mutate local board/hand state after dispatch. The next render must come from engine selectors.
   - Rejected commands should show the adapter error and leave match state unchanged.

6. Support all legal `play_card` target shapes generically.
   - The target action list should be able to display and dispatch:
     - `board_row`;
     - `row_horn`;
     - `weather`;
     - `card_instance`;
     - `none`.
   - This does not mean the shell needs polished UX for each type.
   - If a target shape cannot be displayed nicely, show a simple legal action button rather than disabling a legal engine move.
   - This lets current engine-supported Specials and prompt-opening cards be smoke-tested without custom UI per ability.

7. Preserve and use generic prompt rendering.
   - If a played card opens `match.pendingPrompt`, ordinary card play controls should become inactive.
   - Render prompt options from engine state, as Phase 2 does.
   - Choosing a prompt option dispatches `ChoosePromptOption`.
   - After prompt resolution, selection clears and turn/board state follows engine output.

8. Keep scripted preview AI intentionally simple.
   - The preview AI remains:
     - zero-card mulligan;
     - pass when it owns the playing turn.
   - Do not make the preview AI play cards in this phase.
   - Do not import or call `AIStrategyCoordinator`.
   - This preserves a predictable manual card-play loop: if the AI starts, it passes; if the human plays and hands off, the AI passes; the human can then continue playing until passing.

9. Render updated board and scores after play.
   - After `PlayCard`, board rows must update from `selectEngineBoardRows`.
   - Totals and row scores must update from `selectEngineScoreBreakdown`.
   - Hand/deck/discard counts must update from engine selectors.
   - If a card effect draws cards, opens a prompt, moves weather, discards a special, or moves cards to discard, the UI should reflect those engine state changes without local patching.

10. Improve recent command/event visibility enough for debugging.
    - Keep the compact recent command display from Phase 2.
    - Add recent event names or last transaction event summary if helpful.
    - This is for developer smoke testing, not a full replay UI.
    - Do not expose hidden AI hand card names in default view.

11. Add tests.
    - Add or extend focused tests without mounting a full browser stack.
    - Suggested helper extraction:
      - `getPlayableCardIds(legalMoves)`;
      - `getPlayMovesForCard(legalMoves, cardId)`;
      - `describePlayTarget(move, cardLookup?)`;
      - `shouldDisableHandCard(...)`.
    - Place helper tests near the component helper, for example under `tests/components/`.
    - Extend store adapter tests for an actual `PlayCard` flow through Redux.

12. Add manual smoke coverage.
    - Update the implementation report with a click-through result using:
      - `http://127.0.0.1:5173/?engine=1&seed=dp3-smoke`
    - Required flow:
      1. complete human mulligan;
      2. let scripted AI mulligan/pass as needed;
      3. select a playable human hand card;
      4. choose one legal target action;
      5. confirm the card leaves hand and appears in the engine board/weather/discard zone as appropriate;
      6. confirm score or counts update from engine state;
      7. if a prompt opens, choose a prompt option and confirm state updates;
      8. pass and resolve round through engine controls;
      9. confirm no auto-new-game occurs.

13. Create the required implementation report:
    - `audit/reports/2026-04-25-cDp3-report.md`

## Out Of Scope

- Do not make the engine UI the default route.
- Do not replace legacy `ReduxGameManager`.
- Do not migrate strategic AI.
- Do not add AI card play.
- Do not build final drag/drop or fully spatial board UX.
- Do not build full leader UX.
- Do not build custom per-ability UI beyond generic legal target buttons and generic prompts.
- Do not implement deck builder, Card Studio, PvP, AI-vs-AI simulation, or ML export.
- Do not persist match state, command history, or wins to localStorage.
- Do not add new card rules in React or Redux.

## Acceptance Criteria

- Engine shell still renders only under explicit query/env flag.
- Legacy default app remains selected by default.
- During `playing`, human hand cards are enabled only if engine legal `play_card` moves exist.
- Selecting a playable card shows its legal target actions.
- Clicking a target action dispatches exact engine `PlayCard` command.
- Board, hand, discard, weather, counts, and score display update from engine state after play.
- Prompt-opening cards can be continued through the generic engine prompt renderer.
- Pass and round resolution from Phase 2 still work after card play.
- Scripted preview AI still only mulligans zero and passes.
- No new engine UI code imports legacy rule helpers or legacy AI.
- No new engine UI path computes card legality, row legality, score, round winner, gem loss, game winner, or cleanup outside the engine.
- AI hand card details remain hidden in default human engine view.
- `npm test` passes.
- `npm run build` passes.

## Required Tests

At minimum, cover:

- Helper maps legal moves to playable card IDs.
- Helper returns legal target actions for a selected card.
- Helper describes each target shape used by current legal moves: `board_row`, `row_horn`, `weather`, `card_instance`, and `none`, using fixtures where needed.
- Redux adapter can dispatch a legal human `PlayCard` and move the card out of hand into the expected engine zone.
- Score selector changes after playing a normal Unit.
- Selection clears after successful `PlayCard`.
- Prompt lock disables ordinary play controls and exposes prompt options when `match.pendingPrompt` is present.
- Scripted preview AI still does not play cards.
- No engine UI files import `src/utils/gameHelpers.ts`, legacy `GameBoard`, or `useReduxAI`.

## Notes For The Coding Instance

- Keep the first implementation button-driven if that is faster and more reliable. Spatial row-click UX can come after correctness is proven.
- The legal move object is the contract. Avoid translating it into a homegrown UI rule model.
- If a card has no legal moves, show it as unavailable and let the engine explain through absent moves rather than guessing.
- If a legal move fails, display the adapter error and leave state alone.
- A small, boring UI is acceptable here. Correct command flow matters more than polish.
