# Implementation Spec: Cluster C, Phase 3 - Core Match State And Transactions

## Goal

Create the first pure-engine foundation for Gwent: normalized card-instance state, deterministic match setup from catalog deck presets, a seeded RNG interface, coarse first-class events, and a transaction return shape. This phase should prove the new engine can instantiate a match without preserving the current Redux state shape.

## Architecture Decisions For This Phase

Use the agreed architecture decisions:

1. **Normalized card-instance state**
   - Store card instances once, by `instanceId`.
   - Zones store `instanceId[]`, not card objects.
   - Runtime cards must distinguish `sourceId`, `instanceId`, `owner`, `controller`, and `zone`.

2. **First-class event log**
   - Engine commands should return coarse events from the start.
   - Events are for replay, debugging, UI animation later, and ML logs later.
   - Keep event granularity practical in this phase; do not overdesign every future animation event.

3. **Phase 3 scope = skeleton plus deterministic match setup**
   - Implement setup enough to instantiate decks, hands, leaders, side decks, first player, and event output from catalog presets.
   - Do not implement full legal moves, scoring, abilities, pass, round end, or Redux/UI migration in this phase.

## Scope

1. Add a new pure engine module.
   - Suggested location: `src/game/core/`.
   - Keep it independent from React, Redux, DOM, localStorage, and component code.
   - Export through `src/game/core/index.ts`.

2. Define engine state types.
   - Include:
     - `MatchState`
     - `MatchConfig`
     - `SeatId`
     - `PlayerId` if useful
     - `CardInstanceId`
     - `CardInstance`
     - `ZoneRef`
     - `SeatState`
     - `BoardSide`
     - `RowState`
     - `WeatherState`
     - `MatchPhase`
   - Required state concepts:
     - normalized `cardsById`;
     - per-seat `deck`, `hand`, `discard`, `leader`, `sideDeck`, `removedFromGame`;
     - per-seat board rows `close`, `ranged`, `siege`;
     - per-row `units: CardInstanceId[]`;
     - per-row `horn: CardInstanceId | null`;
     - shared weather entries;
     - current round;
     - current turn;
     - gem/life counters;
     - passed flags;
     - faction;
     - leader source/instance tracking;
     - RNG seed/state metadata sufficient for deterministic setup.

3. Define runtime card instances.
   - A runtime card must include:
     - `instanceId`
     - `sourceId`
     - `owner: SeatId`
     - `controller: SeatId`
     - `zone: ZoneRef`
   - Do not copy full catalog card source data into every instance.
   - The state may keep catalog lookup references separately if useful, but card instances should stay small.

4. Define commands and transaction result shape.
   - Define command types, but implement only setup/start in this phase.
   - Suggested commands:
     - `StartMatch`
     - `ChooseMulligan`
     - `PlayCard`
     - `Pass`
     - `UseLeader`
     - `ChoosePromptOption`
   - Commands not implemented yet should exist as types or documented placeholders, not behavior.
   - Define:
     ```ts
     interface EngineTransaction {
       state: MatchState;
       events: GameEvent[];
       prompt?: PendingPrompt;
     }
     ```
   - `prompt` can be a placeholder type in this phase.

5. Define coarse events.
   - Include event types needed for setup:
     - `match_started`
     - `deck_instantiated`
     - `card_moved`
     - `initial_hand_drawn`
     - `turn_set`
   - Include future event placeholders where helpful:
     - `card_played`
     - `ability_resolved`
     - `prompt_opened`
     - `round_ended`
     - `game_ended`
   - Events must be serializable and deterministic.

6. Add seeded RNG.
   - Add a small deterministic RNG abstraction:
     - seed input string or number;
     - deterministic `next()` or equivalent;
     - deterministic shuffle helper.
   - Do not use `Math.random()` inside the engine.
   - It is acceptable to use a simple local deterministic PRNG for now, as long as tests prove same seed equals same setup and different seeds can differ.

7. Implement deterministic match setup from catalog deck presets.
   - Input should accept two seat configs with:
     - seat ID;
     - player/controller kind metadata if useful;
     - faction;
     - catalog deck preset.
   - Use existing catalog presets from `src/data/catalog`.
   - Instantiate each preset entry count into distinct `CardInstance`s.
   - Generate unique deterministic instance IDs.
   - Shuffle decks through the seeded RNG.
   - Draw 10 cards into each hand.
   - Put leaders into leader zones.
   - Preserve side-deck entries in side-deck zones.
   - Set both gem counters to 2.
   - Set phase to setup/mulligan or equivalent.
   - Set first turn deterministically from RNG unless the type model reserves a future Scoia'tael override hook.
   - Return setup events.

8. Add tests.
   - Same seed and same presets produce identical state and event output.
   - Different seeds can produce different deck/hand order or first player.
   - Repeated card source copies produce unique `instanceId`s while sharing `sourceId`.
   - Every instance has correct `owner`, initial `controller`, and `zone`.
   - Initial hands have 10 cards per seat when the preset has enough cards.
   - Decks shrink by 10 after initial draw.
   - Leaders and side decks are represented in state.
   - No engine code calls `Math.random()`; use a practical test or code-level assertion if feasible.
   - Existing catalog and baseline tests continue to pass.

9. Create the required implementation report:
   - `audit/reports/2026-04-25-cCp3-report.md`

## Out Of Scope

- Do not migrate Redux or UI to the engine.
- Do not preserve or adapt the current Redux state shape.
- Do not implement legal move generation yet.
- Do not implement card play resolution yet.
- Do not implement abilities yet.
- Do not implement scoring yet.
- Do not implement pass, round end, faction passives, or game end yet.
- Do not alter existing live gameplay behavior.
- Do not change current catalog data except for narrow fixes required by setup tests, and document any such fixes.
- Do not add Card Studio UI.
- Do not add ML or simulation runners yet.

## Acceptance Criteria

- `src/game/core` exists and exports pure engine state, command, event, RNG, and setup APIs.
- Engine state uses normalized card instances and ID-based zones.
- Runtime identity clearly separates `sourceId` and `instanceId`.
- Setup can instantiate current Northern Realms and Nilfgaard catalog deck presets into a deterministic match state.
- Setup emits coarse serializable events.
- No engine code depends on React, Redux, DOM, localStorage, or `Math.random()`.
- Tests cover deterministic setup, distinct runtime instances, ownership/controller/zone correctness, initial hand draw, and leader/side-deck representation.
- `npm test` passes.
- `npm run build` passes.
- Existing live gameplay behavior is not intentionally changed.

## Things To Watch Out For

- Do not thread current `PlayerState`, `GameState`, or Redux types into the engine. The point is to leave that shape behind.
- Avoid placing full catalog card objects inside every zone. Zones should point to runtime instances by ID.
- Keep setup deterministic. `Math.random()` can remain in legacy code for now, but not inside `src/game/core`.
- Do not try to solve all rule bugs in this phase. This is the state and setup foundation only.
- Design `ZoneRef` carefully. Later phases need to move Spies, Decoys, weather, Horns, side-deck cards, and removed-from-game cards without guessing ownership.
- Make event payloads useful but not too detailed. Coarse events are enough for this phase.
- If the current catalog deck presets preserve audited legacy omissions or over-limit counts, keep them as current-parity data and document that. Do not silently "correct" deck contents here.
- Avoid generated build artifacts in commits.
