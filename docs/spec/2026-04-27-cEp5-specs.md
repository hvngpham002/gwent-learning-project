# Implementation Spec: Cluster E, Phase 5 - Catalog-Backed Deck Builder V1

## Goal

Implement the first production deck builder for the authentic UI track.

cEp5 should turn the disabled deck-builder entry from cEp4/cEp4.5 into a usable, catalog-backed screen where the player can inspect the current catalog card pool, edit browser-local deck presets, validate deck legality, import/export deck JSON, save/load local decks, and start a playable human-vs-AI match with a valid built deck.

This phase is not Card Studio. It edits deck composition from already-present catalog cards and leaders. Future card authoring, image upload workflows, permanent repo writes, and custom card creation belong to cEp6.

## Architecture Position

Before this phase:

- `/` remains the legacy UI.
- `/?engine=1` remains the diagnostic engine shell.
- `/?engine=1&ui=authentic` opens the authentic pre-game setup.
- `/?engine=1&ui=authentic&view=match` opens the direct match route.
- `/?engine=1&ui=authentic&view=harness` opens the cEp1 foundation harness.
- The pre-game screen lists current catalog deck presets and starts matches through `AuthenticMatchSetupConfig`.
- The deck-builder entry is visible but disabled.

After this phase:

- Add an authentic deck-builder route, preferably `/?engine=1&ui=authentic&view=deck-builder`.
- Enable the pre-game deck-builder entry and route it to the new deck builder.
- The deck builder uses `currentCatalogCards`, `currentCatalogLeaders`, and current deck preset data, not prototype stubs.
- Browser-local saved decks can appear in the pre-game deck selector and can be used as the human deck for match start.
- `startEngineMatch` may receive a custom `CatalogDeckPreset` object for the human seat through the existing `humanDeckPreset` option. Do not change engine rules to support deck building.

## Scope

### 1. Route And Navigation

Add a deck-builder view to the authentic UI route layer.

Requirements:

- Extend `AuthenticUiView` in `src/appMode.ts` to include `deck-builder`.
- `/?engine=1&ui=authentic&view=deck-builder` should open the deck builder.
- `/?engine=1&ui=authentic` and `view=pregame` remain pre-game.
- `view=match` and `view=harness` remain unchanged.
- Invalid views still fall back to pre-game.
- Enable the pre-game `open deck builder ->` and `+ create or edit a deck...` controls.
- Deck-builder top bar must include `← back` returning to pre-game in the in-app flow.
- Preserve the default route and diagnostic shell behavior.

Implementation guidance:

- Keep `AuthenticGameApp` as the small authentic route coordinator.
- It may hold local view state and selected setup/deck state.
- Do not introduce a router dependency.
- Prefer a simple callback flow:
  - pre-game `onOpenDeckBuilder`;
  - deck builder `onExit`;
  - deck builder `onPlay(deckPreset)`.

### 2. Production Data Model

Create a small deck-builder data model over current catalog types.

Requirements:

- Use `CatalogDeckPreset` as the gameplay/export-compatible deck shape:
  - `presetId`
  - `name`
  - `faction`
  - `leaderSourceId`
  - `mainDeck`
  - `sideDeck`
- V1 may keep `sideDeck: []` and should not build side-deck editing UI yet.
- Build card pool rows from `currentCatalogCards`.
- Build leader options from `currentCatalogLeaders`.
- A deck's selectable card pool must include:
  - neutral cards;
  - cards matching the deck faction.
- Do not hard-code current Northern Realms or Nilfgaard source IDs except in tests where needed for deterministic assertions.
- Future catalog additions should automatically appear in the correct deck-builder pool if they are exported through `currentCatalogCards` and match the selected deck faction.

Recommended helper files:

- `src/components/gwent/deckBuilderTypes.ts`
- `src/components/gwent/deckBuilderViewModel.ts`
- `src/components/gwent/deckBuilderStorage.ts`
- `src/components/gwent/AuthenticDeckBuilderScreen.tsx`
- `src/components/gwent/authentic-deck-builder.css`

Use different filenames if the surrounding implementation suggests a cleaner split, but keep pure helpers separate from React where practical.

### 3. Local Persistence

Implement browser-local persistence for editable deck presets.

Requirements:

- Use a production-specific localStorage key, recommended: `gwent_authentic_decks_v1`.
- Seed local decks from current catalog deck presets when no saved decks exist.
- Do not mutate the imported `currentDeckPresets` objects.
- Persist only serializable deck data. Do not persist runtime engine card instance IDs.
- Storage failures must not crash the app. Surface a compact warning or fallback to in-memory state.
- Provide deterministic helper coverage for:
  - empty storage seeds from current presets;
  - invalid/corrupt storage falls back safely;
  - save/load round trip preserves deck preset data.

Implementation guidance:

- Store an object such as:

```ts
interface AuthenticDeckStoreV1 {
  readonly schemaVersion: "authentic-decks-v1";
  readonly decks: CatalogDeckPreset[];
  readonly activePresetId?: string;
}
```

- It is acceptable to normalize imported or saved decks before persistence, for example by sorting `mainDeck` entries by source ID.
- Do not write files to the repository from browser code.

### 4. Deck Validation

Add a deck-builder validation helper that combines catalog reference validation with match-readiness rules.

Required validation:

- Deck has a non-empty name.
- Deck faction is a known non-neutral faction.
- Leader exists and belongs to the deck faction.
- Every `mainDeck` entry references an existing catalog card.
- Every `mainDeck` count is a positive integer.
- Every card in `mainDeck` is either neutral or matches the deck faction.
- Every card count is at or below that card's `deckLimit`.
- Battlefield card count is at least 22. For the current catalog shape, count `kind === "unit"` and `kind === "hero"` as battlefield cards.
- Special count is at most 10. For the current catalog shape, count `kind === "special"` as special cards, including weather and neutral specials.
- `sideDeck` must exist and be an array, but V1 may require it to be empty.

Warnings, not hard errors:

- Card ability metadata with `status !== "implemented"`.
- Leader ability metadata with `status !== "implemented"`.
- Missing image files cannot be proven reliably in browser tests, but image path strings should be displayed when useful and `AuthenticCard` fallback must still work.

Important:

- Unknown ability IDs are already catalog-validation errors; do not introduce unknown ability IDs.
- Do not silently hide planned/placeholder abilities. If a deck includes them, show a warning in the stats panel or card detail. The Play button may remain enabled if structural deck validation passes, but the warning must be visible near validation/play context.
- Do not change engine behavior to make unsupported abilities work.

Recommended output shape:

```ts
interface DeckBuilderValidationIssue {
  readonly severity: "error" | "warning";
  readonly code: string;
  readonly message: string;
  readonly sourceId?: string;
}

interface DeckBuilderStats {
  readonly totalCards: number;
  readonly battlefieldCards: number;
  readonly unitCards: number;
  readonly heroCards: number;
  readonly specialCards: number;
  readonly totalStrength: number;
  readonly rowCounts: Record<"close" | "ranged" | "siege", number>;
  readonly issues: readonly DeckBuilderValidationIssue[];
  readonly playable: boolean;
}
```

### 5. Deck Builder UI

Recreate the handoff's deck-builder composition using production CSS and components.

Target desktop composition:

- top bar with:
  - `← back`
  - `Deck Builder`
  - action row: `+ New`, `Import`, `Export .json`, `copy`, `Save`, `Play ->`
- body as a three-column table:
  - left deck list around `220px`;
  - center card pool;
  - right validation/stats/selected deck panel around `320px`.

Left deck list:

- Shows saved local decks.
- Each deck tile shows name, faction, total count, and validity state.
- Selected deck has accent border/tint.
- Delete current is available only when more than one editable deck exists.
- Deleting should require a simple confirmation or at least use a clearly labeled destructive button; do not make delete easy to click accidentally.

Center card pool:

- Header shows editable deck name.
- Show deck faction and leader summary.
- Provide filter pills:
  - `all`
  - `heroes`
  - `units`
  - `specials`
- Add a search input if practical; if omitted, explain in the report. Search is strongly preferred because future card population will make the pool much larger.
- Pool grid uses `AuthenticCard` at `md` size where practical.
- Each pool item shows a compact mono card name/caption.
- Clicking a card adds one copy if below `deckLimit`.
- Cards at max count are visibly dimmed and not clickable.
- A circular badge shows `n/max` for cards currently in deck.
- Card metadata should make future card population easier:
  - source ID visible in hover title, selected-detail text, or inspector;
  - image path visible in selected-detail text or a compact details area;
  - ability status visible when not implemented.

Right stats/deck panel:

- Composition stats:
  - battlefield cards / 22 min;
  - specials / 10 max;
  - heroes;
  - total strength;
  - total cards;
  - validation issue list.
- Leader select filtered by deck faction.
- Leader description and ability status.
- Cards in deck list sorted by useful deterministic order:
  - strength descending;
  - then kind;
  - then name/source ID.
- Each deck-list row shows strength or dot, name, count, and a remove button.
- Removing decrements one copy and deletes the entry at zero.

Responsive requirements:

- Desktop should match the handoff's dense tactical table feel.
- At tablet/mobile widths, columns may stack.
- No document-level horizontal overflow at `390px`.
- Text in buttons, pills, tiles, and deck rows must not overflow its container.

### 6. New, Rename, Save, Delete

New deck:

- Creates a browser-local editable deck.
- Default faction can be `northern_realms`.
- Default leader should be the first leader for that faction, preferably the first implemented leader if one exists.
- New deck may start empty.
- New deck should immediately become active and rename-focused if practical.

Rename:

- Deck name can be edited inline.
- Empty names should be invalid and show a validation error.

Save:

- Persists the current local deck list to localStorage.
- If the app already auto-saves on every edit, the Save button can still write and show a compact confirmation. Document this in the report.

Delete:

- Cannot delete the last deck.
- Must update active deck deterministically after deletion.

Do not add cloud/account persistence.

### 7. Import, Export, Copy

Implement browser-only import/export for deck presets.

Export:

- Export selected deck as JSON compatible with the current catalog deck preset shape.
- Recommended wrapper:

```json
{
  "schemaVersion": "catalog-deck-preset-v1",
  "preset": {
    "presetId": "...",
    "name": "...",
    "faction": "northern_realms",
    "leaderSourceId": "...",
    "mainDeck": [{ "sourceId": "...", "count": 1 }],
    "sideDeck": []
  }
}
```

- Download via `Blob` and object URL is acceptable.
- Clipboard copy should copy the same JSON text.
- Button label should be compact lowercase `copy` for visual consistency with the pre-game seed copy button.

Import:

- Provide a modal with textarea paste.
- File upload using a hidden `<input type="file">` and `FileReader` is allowed.
- Accept both the wrapper above and a raw `CatalogDeckPreset` object.
- Validate imported decks before adding.
- If `presetId` conflicts with an existing local deck, generate a new local ID or require a rename. Do not overwrite silently.
- Show parse/validation errors in the modal.
- Imported decks should be persisted only after successful validation.

Do not:

- write imported deck data into `src/data/catalog`;
- generate TypeScript source files;
- add Card Studio fields.

### 8. Pre-Game Integration

Saved local decks must be usable from the product pre-game path.

Requirements:

- Pre-game deck selector includes valid local decks, in addition to current catalog presets.
- Local deck options should be visually distinguished subtly, for example `local` note or title text. Do not make them look disabled if they are playable.
- Invalid local decks may appear disabled with validation reason, or may be hidden if the deck builder is the only repair path. Prefer disabled with reason.
- Selecting a local human deck should preserve the current opponent suggestion behavior.
- Opponent choices may remain built-in current catalog presets in cEp5. Do not make custom local decks AI opponents yet unless it is very low risk.
- Begin Match with a local human deck should pass a `CatalogDeckPreset` object to `startEngineMatch`, not require the deck to be added to `currentDeckPresets`.

Implementation guidance:

- Extend `AuthenticMatchSetupConfig` to support either:
  - a built-in human deck preset ID; or
  - an inline custom human `CatalogDeckPreset`.
- Keep the setup config serializable and free of runtime card instance IDs.
- Keep current built-in pre-game behavior unchanged when no local decks exist.

### 9. Play From Builder

The top-bar `Play ->` action should start a playable match from the current builder deck when validation passes.

Requirements:

- `Play ->` is disabled when the current deck has validation errors.
- If validation warnings exist, show them before play; the button may remain enabled.
- On play:
  - save the current deck;
  - generate or use a visible seed;
  - start human-vs-AI using the current deck for `seat_a`;
  - choose a built-in opponent preset using the same "not same deck if possible" policy as pre-game;
  - preserve AI policy `legal-heuristic-v0`;
  - transition to `AuthenticMatchScreen`.
- The match top bar should show the generated/selected seed as it already does.

Do not add:

- local PvP;
- AI-vs-AI product mode;
- ranked/training behavior;
- Bo1 behavior;
- route promotion to `/`.

### 10. Product Boundaries

This phase must not touch engine rules.

Do not:

- modify `src/game/core` rule transactions unless a compile-only type extension is unavoidable;
- compute legal moves in React;
- import legacy rule helpers or legacy AI;
- expose hidden opponent match data;
- add Card Studio/custom card authoring;
- upload or write card images;
- write deck JSON to repository files from browser code;
- add backend/server persistence;
- add new dependencies;
- port prototype `CARD_POOL`, `LEADERS_NR`, localStorage model, or inline style blocks.

Deck validation can be a UI/catalog helper. It must be deterministic and unit-tested.

## Tests

Add focused tests for pure helpers and route behavior.

At minimum:

- `tests/appMode.test.ts`
  - `view=deck-builder` routes to deck-builder;
  - unknown view still falls back to pre-game.
- Deck-builder view model tests:
  - pool contains selected faction + neutral cards only;
  - pool automatically derives from catalog data;
  - filters and search are deterministic;
  - add respects `deckLimit`;
  - remove decrements/deletes;
  - stats count battlefield, specials, heroes, total strength;
  - validation catches too few battlefield cards;
  - validation catches too many specials;
  - validation catches over-limit copies;
  - validation catches wrong-faction cards;
  - non-implemented ability/leader metadata appears as warning, not hidden.
- Storage/import/export tests:
  - empty localStorage read seeds decks;
  - corrupt localStorage read falls back safely;
  - save/load round trip;
  - export JSON parses back to an equivalent preset;
  - import wrapper and raw preset shapes;
  - duplicate preset IDs do not overwrite silently;
  - invalid import returns structured errors.
- Pre-game integration helper tests:
  - valid local decks appear as deck options;
  - invalid local decks are disabled or omitted according to implementation choice;
  - local selected deck converts into a start-match config with an inline `CatalogDeckPreset`.

Update Playwright smoke:

- Pre-game shows enabled deck-builder entry.
- Clicking deck-builder entry opens the deck builder.
- Direct `/?engine=1&ui=authentic&view=deck-builder` opens the deck builder.
- Deck builder shows:
  - deck list;
  - card pool;
  - stats/validation panel;
  - leader select;
  - import/export/copy/save/play controls.
- A simple add/remove action changes a visible count badge or stats value.
- `Play ->` with the seeded valid deck starts `AuthenticMatchScreen`.
- Hidden-info checks still pass after match start.
- Mobile width has no horizontal overflow for pre-game, deck builder, and match.

Keep browser smoke short. Do not require assembling a full 22-card deck by clicking one card at a time in Playwright if seeded decks already cover the path.

## Acceptance Criteria

cEp5 is complete when:

- `/?engine=1&ui=authentic&view=deck-builder` opens the authentic deck builder.
- Pre-game deck-builder controls are enabled and navigate to the deck builder.
- The deck builder uses current catalog cards/leaders and no prototype card/leader stubs.
- The card pool updates from catalog data and supports future added cards without code changes.
- Users can create, rename, save, delete, import, export, copy, and select local decks.
- Validation clearly reports legal errors and unsupported/placeholder ability warnings.
- A valid local deck can start a human-vs-AI match through the engine-backed authentic match screen.
- Pre-game can list and start with valid local decks.
- The default route, diagnostic shell, direct match route, and harness route still work.
- No legacy rule helpers, legacy AI, legacy Redux game paths, or `GameBoard` imports are introduced in `src/components/gwent`.
- Hidden opponent match data remains hidden.
- Mobile/deck-builder browser smoke has no horizontal overflow at 390px.
- `docs/PROJECT_STATE.md` is updated.
- A report exists at `audit/reports/2026-04-27-cEp5-report.md`.
