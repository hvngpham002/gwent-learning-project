# Implementation Spec: Cluster E, Phase 11 - Board Targeting Polish

## Intent

Make selected-card targeting in the authentic match UI feel spatial, legible,
and product-ready without changing engine rules.

cEp10 made round and match flow coherent. cEp11 should tighten the core
in-round interaction loop:

- selecting a playable hand card should make its legal destinations obvious;
- row, card, horn-slot, weather, and global targets should each have clear
  visual and accessible affordances;
- right-rail target actions should support the spatial model instead of being
  the primary way to understand where a card can go;
- every target click must dispatch the exact existing engine legal move;
- no UI code should invent legal targets, compute rule outcomes, or expose
  hidden opponent card identities.

This is a product UI phase. The engine already owns legal move generation and
command execution.

## Scope

### 1. Pure Selected-Card Target View Model

Add a product-specific target presentation helper in
`src/components/gwent/matchViewModel.ts`.

Recommended name:

```ts
buildSelectedCardTargetViewModel(...)
```

The exact type shape is up to the coding instance, but it must be pure and
covered by unit tests. It should consume only:

- the currently selected human hand card, if any;
- `PlayCardMove[]` legal moves for that selected card;
- public visible-card lookup data for labels;
- seat labels / row display metadata as needed.

Required output concepts:

- no selection / selected with no legal play moves / selected with legal
  targets;
- selected card label and concise instruction copy;
- row targets keyed by engine board row (`seatId:row`) with exact `moveId`,
  side label, row label, badge label, and aria label;
- board-card targets keyed by visible `cardId` with exact `moveId`, safe card
  label, badge label, and aria label;
- row-horn targets keyed by own row with exact `moveId`, row label, badge
  label, and aria label;
- weather target, when the selected card has a legal `target.kind ===
  "weather"` move;
- non-spatial fallback actions for `target.kind === "none"` and any target
  kind that cannot be represented spatially yet;
- compact right-rail fallback actions that are hidden-info-safe.

Labels must be human-readable and must not surface raw runtime instance IDs or
hidden opponent source IDs. Public visible card names are allowed. The selected
human hand card is public to the human player, so its name may appear in labels
and aria text.

Move any authentic-match-specific target grouping out of the diagnostic engine
shell helper path. `AuthenticMatchScreen.tsx` should not rely on
`groupTargetActions` from `src/components/game/engine/engineShellViewModels.ts`
for product target presentation after cEp11. Keep the diagnostic helper itself
if the engine shell still uses it.

### 2. Spatial Board Row Targets

Refine board-row targeting in `AuthenticMatchScreen.tsx`.

Requirements:

- Board rows with a legal `board_row` target should be visibly highlighted and
  clickable.
- The target affordance should include a small, readable badge such as
  `play here` or an equivalent short label.
- The row target must dispatch the exact legal `PlayCard` move id associated
  with that row.
- The row target must have a useful aria label, for example
  `Play <card> on your close combat row`.
- Focus-visible styling must make keyboard navigation clear.
- Do not wrap an entire row in a `<button>` if that creates nested interactive
  elements with board-card target buttons. Use a non-interactive row container
  plus a dedicated target button/overlay, or another accessible structure that
  avoids nested buttons.
- Empty legal target rows must be just as clear as occupied target rows.
- Existing row score, weather tint, horn display, and card inspection behavior
  must remain intact.

### 3. Spatial Board Card Targets

Refine visible board-card targeting for `card_instance` moves such as Decoy.

Requirements:

- Visible legal card targets should render a clear target badge or focus ring
  on the card surface.
- The click target must dispatch the exact legal move id for that visible card.
- The target button must have a useful aria label, for example
  `Choose <card> for <selected card>`.
- Right-click inspection must still work and must not dispatch the target move.
- Non-target board cards should remain inspectable but should not look
  actionable.
- Do not add any target affordance to hidden AI hand/deck cards.

### 4. Horn Slot And Weather Targets

Add spatial targets for selected cards whose legal move target is not a normal
board row.

Requirements:

- `row_horn` moves should render an explicit horn-slot target on the relevant
  own row. The target should be visually distinct from a unit row target and
  should dispatch the exact horn move.
- `weather` moves should render an explicit target on the Weather panel.
  Clicking it should dispatch the exact weather move. This should work whether
  the weather zone is empty or already contains weather cards.
- Global/no-target card plays, such as whole-board Scorch or Clear Weather
  style special cards if represented as `target.kind === "none"`, should remain
  in the right rail as a compact action. Do not force global effects into a fake
  board location.
- Existing weather card right-click inspection must keep working.
- Do not change leader weather choice behavior from cEp8. cEp11 is for selected
  hand-card play targets.

### 5. Right-Rail Target Copy

Refine the right-rail `Actions` area so it supports the spatial model.

Requirements:

- When no hand card is selected, keep a compact empty state.
- When a selected card has spatial targets, the right rail should tell the
  player what to do, for example `choose a highlighted row` or `choose a
  highlighted card`.
- Keep compact fallback buttons for accessibility and for non-spatial targets,
  but do not make a bulky duplicate target panel the primary presentation.
- Fallback buttons must still dispatch exact legal move ids.
- Fallback labels must be safe and user-facing; do not expose raw ids.
- Button styling must use the existing `authentic-button` variants documented
  in `docs/ui/authentic-button-style-guide.md`.

### 6. Interaction And Accessibility

Requirements:

- All spatial targets must be reachable by keyboard and operable with Enter /
  Space through native button behavior where practical.
- Visible target badges should not overlap card strength medallions, row labels,
  or score columns at desktop or 390px mobile width.
- Selecting a different hand card must recompute spatial targets immediately.
- If the selected card leaves the hand or the phase/prompt/turn changes so the
  move set is stale, existing selection-clear behavior must still prevent stale
  dispatch.
- Target hover/focus should be restrained: use the existing accent, ink, rule,
  and parchment tokens. Do not add a new one-off color system.
- No target surface should dispatch on right-click, context-menu open, Escape,
  click-outside of modals, or hover.

### 7. Hidden-Info Safety

Add assertions where practical:

- Target view-model labels and right-rail target text do not include raw
  `seat_a:...` / `seat_b:...` instance IDs.
- AI hand/deck card names/source IDs do not appear in target affordances.
- Public board/weather/discard card names may appear only because those cards
  are already public.
- Browser hidden-info smoke patterns should still pass after target polish.

## Out Of Scope

Do not implement:

- engine rule changes;
- legal move generation changes;
- command execution changes except dispatching existing exact commands from new
  UI surfaces;
- scoring, gem, round-result, or game-end recomputation in UI;
- full drag-and-drop card play;
- card flight / death / revive animations;
- AI strategy changes;
- deck-builder, Card Studio, official porting, catalog, or asset changes;
- default-route promotion;
- deterministic match-end browser smoke;
- modal click-outside policy unification;
- new game modes, ranked systems, rewards, MMR, or progression;
- legacy UI migration.

If the implementation discovers that a target affordance needs a new engine
legal target shape, stop and report the gap instead of adding UI-side rules.

## Acceptance Criteria

- Selecting a normal unit with legal row moves highlights the correct board
  row targets and clicking a highlighted row dispatches the exact existing
  `PlayCard` move.
- Selecting a card with `card_instance` targets highlights only visible legal
  board cards and clicking one dispatches the exact existing move.
- Selecting Commander's Horn or an equivalent `row_horn` card shows explicit
  horn-slot targets and dispatches the exact existing move.
- Selecting a weather card shows an explicit Weather panel target and dispatches
  the exact existing move.
- Selecting a global/no-target card play shows a compact right-rail action and
  does not create a fake board target.
- The right rail no longer depends on the diagnostic engine-shell
  `groupTargetActions` helper for authentic selected-card target presentation.
- No nested interactive elements are introduced in board rows.
- Right-click inspect behavior remains intact on visible cards.
- Hidden AI hand/deck identities remain hidden.
- Desktop and 390px mobile layouts avoid target badge/text overlap.
- `docs/PROJECT_STATE.md`, `docs/ui/authentic-product-flow.md`, and the phase
  report are updated.
