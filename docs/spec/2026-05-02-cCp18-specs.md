# Implementation Spec: Cluster C, Phase 18 - Remaining Leader Ability Rules Matrix

## Intent

Create a documentation-only rules matrix for every official leader ability that
is still `placeholder` in the catalog. This phase must not implement engine
behavior.

cEp8 closed the authentic UI gap for multi-move leaders. The next blocker is
not UI plumbing; it is rule clarity. The remaining official leaders include
active row-wide effects, tutor/discard effects, opponent-hand/discard effects,
start-of-game/passive effects, and leader-cancel effects. Several local sources
also appear to conflict with each other. cCp18 should identify those conflicts
before cCp19 implements anything.

The output of cCp18 should be the source material for the next implementation
spec, not the implementation itself.

## Required Audit Work

### 1. Enumerate Every Placeholder Leader

Build a matrix with one row per placeholder leader source record.

Required columns:

- faction
- leader source ID
- leader display name
- ability ID
- ability metadata status
- catalog description
- local rule/source text
- likely official behavior
- active vs passive vs setup-time classification
- expected legal move shape
- expected command transaction shape
- prompt / choice UI need
- hidden-info risk
- implementation difficulty (`low`, `medium`, `high`)
- recommended tranche
- unresolved questions

Include all 14 currently unimplemented official leader records if that remains
the current count.

### 2. Group By Implementation Pattern

The matrix must also summarize leaders by shared implementation pattern.

Expected groups to evaluate:

1. **Row-wide horn-like leaders**
   - `double_siege`
   - `double_close`
   - `double_ranged`

2. **Deck tutor / discard-cost leaders**
   - `discard_two_draw_one_from_deck`

3. **Discard restore / steal leaders**
   - `restore_discard_to_hand`
   - `draw_opponent_discard`

4. **Spy / board-state modifier leaders**
   - `double_spies`

5. **Agile row optimizer**
   - `optimize_agile_rows`

6. **Start-of-game / setup-time draw leader**
   - `draw_extra_card`

7. **Discard-pile shuffle leader**
   - `shuffle_discards_into_decks`

8. **Opponent hand information leader**
   - `look_three_cards`

9. **Leader-cancel / suppression leader**
   - `cancel_leader`

10. **Medic-rule mutation leader**
    - `random_medic`

If a local source proves a different grouping is more accurate, document the
change.

### 3. Identify Source Conflicts

Create a conflict table comparing at least:

- catalog leader descriptions in `src/data/catalog/leaders/*.ts`
- leader ability metadata in `src/game/catalog/abilities.ts`
- `docs/gwent-rules.md`
- Game8 staging data under `audit/scrapes/2026-04-29-game8-gwent-cards.json`
- Witcher Fandom scrape snapshot under
  `audit/scrapes/2026-04-30-witcher-fandom/fandom-card-snapshot.json`

Known conflicts or likely conflicts to check explicitly:

- `docs/gwent-rules.md` currently labels **Eredin, Destroyer of Worlds** as
  a discard restore effect, while the catalog labels that leader as
  `discard_two_draw_one_from_deck` and assigns discard restore to
  **Eredin: Bringer of Death**.
- `docs/gwent-rules.md` currently labels **Emhyr var Emreis, The Relentless**
  as a deck tutor, while the catalog labels that leader as
  `draw_opponent_discard`.
- Clarify which leader, if any, owns "draw a Unit or Special from your deck,
  then shuffle" in the permanent catalog.
- Clarify `random_medic`: whether it changes all Medic effects for the match,
  only the acting player's Medic effects, whether it is active/passive, and
  whether it affects Medic chains.

For each conflict, classify:

- **confirmed catalog bug**
- **confirmed rules-doc bug**
- **local sources disagree; product decision needed**
- **resolved by local source majority**

Do not fix source conflicts in production code during cCp18 unless the fix is a
documentation-only clarification explicitly inside the allowed files.

### 4. Define Engine/UI Implications

For each ability group, specify likely future implementation surfaces.

Required dimensions:

- Legal move target shape needed:
  - no target
  - board row
  - visible card instance
  - hand card instance
  - deck source / deck card
  - discard card instance
  - opponent hidden hand sample
  - setup-time automatic event
- Whether a `pendingPrompt` is required.
- Whether the authentic cEp8 leader-choice menu is sufficient.
- Whether a new product prompt/modal is needed.
- Whether hidden information can be shown to the human.
- Whether AI can choose safely with current `legal-heuristic-v0`.
- Whether simulation export schemas would need new target refs.
- Whether the effect is a one-shot active action, an ongoing row modifier, a
  passive match modifier, or a setup-time effect.

### 5. Recommend cCp19+ Tranches

End the matrix with a ranked recommendation.

Do not simply rank by what is most interesting. Rank by:

- ambiguity level;
- implementation blast radius;
- value to official starter decks;
- UI/prompt complexity;
- hidden-info risk;
- testability.

The expected output is likely:

- a low-ambiguity tranche (for example row-wide horn-like leaders if the audit
  confirms their rules);
- a prompt-heavy tranche (deck/discard/hand target leaders);
- a passive/setup tranche;
- a high-risk hidden-info/cancel tranche.

But the audit should justify the ordering from the evidence it finds.

## Acceptance Criteria

- No production code, catalog, test, UI, AI, simulation, or config files are
  changed.
- `docs/leader-ability-matrix.md` exists and covers every remaining placeholder
  leader source record.
- Every remaining placeholder ability ID is grouped by implementation pattern.
- Known local source conflicts are explicitly listed and classified.
- Each ability group has engine, legal move, prompt/UI, hidden-info, AI, and
  simulation implications.
- cCp19+ implementation tranches are ranked and justified.
- `docs/PROJECT_STATE.md` is updated.
- `audit/reports/2026-05-02-cCp18-report.md` exists and includes the required
  report sections.
- Required checks pass, or any skipped/failed check is explained.
