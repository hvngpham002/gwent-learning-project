# cFp49 Specs: Robust Failure-Mining Casebook

## Summary

`cFp49` is an analysis-only phase over the `cFp48` 1000-record robust starter
matrix artifact boundary.

The goal is to turn the robust failure-mining output into a compact decision
artifact before the next behavior patch. Do not change `legal-heuristic-v1`
behavior in this phase.

The cFp48 robust queue says the largest actionable cluster is still
`round_resource_exhaustion`, followed by `weathered_row_low_tempo`,
`medic_no_target_timing`, `skellige_matchup_skew`, and broad
`remaining_suspicious_pass`. cFp49 must determine which of those signals is
actually narrow enough to become cFp50, and which signals need better
instrumentation before tuning.

## Research Grounding

Batch B established the evaluation ladder:

1. Deterministic headless fixed-suite ledgers.
2. Hidden-info-safe failure mining.
3. Rating/RD reports.
4. Rating snapshot comparisons.
5. Larger robustness probes.
6. Later search/model work.

cFp48 completed the first robust fixed-suite probe. cFp49 should use that
larger probe to decide whether another hand-tuned v1 behavior patch is
justified.

Interpretation rules:

- Failure-mining findings are triage signals, not proof of a defect.
- Compare robust counts to expanded/current counts using rates where possible.
  The robust suite has 1000 records; the expanded suite has 400 records.
- Broad `suspicious_pass` totals are not directly actionable unless a narrow
  repeated contradiction appears.
- Do not infer hidden card identities from public aggregate fields.
- Do not compare ratings across different suite pools as if they share one
  rating universe.

## Required Analysis

Use only committed public artifacts from:

```text
docs/research/literature/ai/benchmark-results/benchmark-v1-starter-matrix-robust-v1/
```

Do not read or embed raw engine states, command logs, private-zone arrays, deck
orders, runtime card instance ids, private observations, or hidden hand card
names.

The decision note must include the sections below.

### 1. Source Artifact And Hidden-Info Boundary

List the exact artifact files used, their schema versions where available, and
the hidden-info boundary.

Explicitly state that the robust failure-mining `findings.jsonl` contains only
public benchmark identifiers and public aggregate evidence fields.

### 2. Robust Suite Topline

Summarize:

- robust benchmark record count;
- v1 W/L/D against v0;
- policy failure count;
- engine/replay failure count if available;
- robust failure-mining total finding count;
- top finding-kind counts;
- suppressed suspicious-pass categories;
- robust policy-level rating/RD if useful.

Expected cFp48 baseline values:

```text
records: 1000
v1 result: 776 win / 206 loss / 18 draw
failure findings: 2301
suspicious_pass: 1752
weathered_row_play: 240
round_three_low_resource: 226
round_one_overinvestment: 71
medic_timing_risk: 11
matchup_skew: 1
suppressed suspicious-pass findings: 920
```

If the committed artifacts disagree, trust the artifacts and explain the
difference in the report.

### 3. Expanded-Vs-Robust Rate Comparison

Compare cFp48 robust findings against the latest expanded/current boundary
where useful. Use rates, not just raw counts.

At minimum compare:

- `round_one_overinvestment`
- `round_three_low_resource`
- `weathered_row_play`
- `medic_timing_risk`
- broad `suspicious_pass`

Example format:

| Finding kind | Expanded count/rate | Robust count/rate | Interpretation |
|---|---:|---:|---|

For broad `suspicious_pass`, call it a finding-rate because multiple findings
can occur in one record.

### 4. Cluster Classification

Classify each queue cluster:

- `round_resource_exhaustion`
- `weathered_row_low_tempo`
- `medic_no_target_timing`
- `skellige_matchup_skew`
- `remaining_suspicious_pass`

Use one of these labels:

- `behavior_actionable`
- `needs_trace_instrumentation`
- `analyzer_noise_or_broad_signal`
- `watch_only`
- `defer`

The classification must explain why the label follows from public evidence.

### 5. Required Breakdown: Round Resource Exhaustion

Break down `round_resource_exhaustion` into:

- `round_one_overinvestment`
- `round_three_low_resource`

For `round_one_overinvestment`, aggregate by:

- faction;
- matchup id;
- `round1PlayCardCount`;
- `resolvedRoundCount`;
- `matchOutcome`;
- severity.

For `round_three_low_resource`, aggregate by:

- faction;
- `matchOutcome`;
- `unitCardCount`;
- `positiveUnitMoveCount`;
- `selectedKind`;
- `futureRoundHandQuality`;
- `specialOnlyHand`.

The decision note must say whether this cluster supports:

- a behavior patch;
- trace-level instrumentation first;
- no action.

### 6. Required Breakdown: Weathered Row Low Tempo

For `weathered_row_play`, aggregate by:

- `selectedMoveSide`;
- `selectedMoveRow`;
- `selectedPrintedStrengthBucket`;
- `selectedEffectiveStrengthBucket`;
- `candidateWeatheredOwnRowPlayCount`;
- `candidateWeatheredOpponentRowPlayCount`;
- faction.

The decision note must say whether remaining weathered-row cases are likely:

- own-row low-tempo placement misses;
- opponent-row spy/weather interaction cases;
- broad analyzer findings without enough proof;
- already covered by cFp38/cFp30 behavior but still visible because the
  analyzer is intentionally broad.

### 7. Required Breakdown: Medic Timing

List all 11 robust `medic_timing_risk` findings in a compact table using only
public fields:

- finding id;
- faction;
- matchup id;
- seed;
- mirror index;
- `ownDiscardReviveCandidateCount`;
- `bestReviveStrengthBucket`;
- `bestReviveValueBucket`;
- `noTargetMedicRisk`;
- `selectedMedicWithNoTarget`;
- `selectedKind`;
- severity.

Classify each finding as:

- `true_no_target`
- `weak_target`
- `acceptable_target`
- `needs_trace_instrumentation`

### 8. Required Breakdown: Suspicious Pass

Aggregate robust `suspicious_pass` findings by:

- round;
- `isOpponentPassed`;
- `roundInvestmentRecommendation`;
- `hasSingleMoveCatchUp`;
- `singleMoveCatchUpIgnored`;
- `policyUpperBoundCanWinRound`;
- `fightLastGemUpperBoundCanWin`;
- `stopLossRecommended`;
- `activeVoluntaryUnsafe`;
- score-delta buckets.

Do not recommend tuning broad `suspicious_pass` unless the data exposes a
narrow repeated contradiction that is not already covered by suppressions.

### 9. Required Breakdown: Matchup Skew

Summarize the single `matchup_skew` finding and cross-reference the robust
rating report. Do not propose a faction-specific behavior patch unless the
evidence is stronger than "one matchup has a bad aggregate".

### 10. Decision And Next Phase Recommendation

The decision note must end with one recommended cFp50 scope.

Allowed recommendation shapes:

1. **Behavior patch** — only if one robust cluster has a narrow repeated public
   pattern and an obvious rule-limited patch shape.
2. **Trace instrumentation** — if findings are frequent but public fields cannot
   determine the real policy decision state.
3. **Analyzer calibration** — if the signal is mostly broad/noisy and should be
   filtered before more policy tuning.
4. **Ratings/search/evaluation ladder** — if v1 tuning is no longer supported by
   the current findings.

The recommendation must explicitly say why the other obvious candidates are
not chosen.
