# Implementation Spec: Cluster C, Phase 9 - Official Card Rule Gaps

## Goal

Implement the remaining official non-leader card rule gaps surfaced by `cBp3`:

- Skellige Storm is already functionally close to implemented, but its catalog metadata and official-porting classification still mark it incomplete.
- Mardroeme must be a real row-based ongoing ability.
- Berserker must transform through the side deck when Mardroeme is active on its row.

This is a pure engine/catalog rules phase. Do not promote official Game8 candidates into product decks, do not download images, and do not implement leader abilities in this phase.

## Current Context

`cBp3` staged official Game8 candidates but intentionally kept them out of runtime decks. Its report lists these official card-rule gaps:

- `mardroeme`: 4 physical copies flagged.
- `berserker`: 4 physical copies flagged.
- `skellige_storm`: 3 physical copies flagged as a metadata/implementation mismatch.

The current engine already has:

- `sideDeck` and `removedFromGame` zones in `MatchState`;
- deterministic deck instantiation for side decks;
- weather scoring support for `skellige_storm` over ranged and siege rows;
- legal weather target generation for `skellige_storm`;
- round cleanup and Scorch discard behavior that keeps removed-from-game cards out of discard.

The current engine does not yet have:

- legal row targets for special Mardroeme cards;
- Mardroeme row settlement;
- Berserker transformation;
- explicit transform events/reasons;
- official-porting reclassification after these rules become implemented.

## Product And Architecture Decisions

Use these decisions unless the user explicitly changes them later:

- The pure engine owns Mardroeme/Berserker behavior.
- React, Redux, AI, and UI view models may observe resulting legal moves/events, but they must not compute these rule outcomes.
- Use existing `CatalogCardSource.linkedSourceIds` as the Berserker transform link for this phase. The first linked source ID is the replacement source that must be found in the controlling seat's side deck.
- Do not add a new catalog field unless implementation proves `linkedSourceIds` is insufficient.
- Do not promote cBp3 official candidates into `currentCatalogCards`, deck presets, deck-builder source sets, or runtime product decks.
- Do not implement Summon or Avenger.
- Do not implement official leader abilities.
- Do not add timers.
- Preserve hidden-information boundaries in UI, AI, simulation, and export paths.

## Scope

### 1. Mark Skellige Storm As Implemented

Update catalog metadata so `skellige_storm` is no longer a placeholder.

Requirements:

- `CATALOG_ABILITY_METADATA.skellige_storm.status` must become `"implemented"`.
- Existing scoring behavior must continue:
  - Skellige Storm affects both ranged and siege rows.
  - Heroes ignore it.
  - ordinary units on affected rows become strength 1 under normal weather policy.
  - King Bran weather policy continues to halve friendly weather penalty instead of setting to 1.
- Existing legal move behavior must continue:
  - Skellige Storm targets the shared weather zone.
  - Clear Weather removes Skellige Storm along with all other weather.
- Remove the cBp3 official-porting special-case issue that treats `skellige_storm` as a metadata mismatch.
- Update official-porting tests so `skellige_storm` is no longer counted in unsupported card ability counts.

### 2. Add Legal Row Targets For Special Mardroeme

Special Mardroeme is a row-based special card, not a shared weather card and not a global one-shot.

Requirements:

- A special card with ability `mardroeme` must generate legal play moves for the acting player's own `close`, `ranged`, and `siege` rows.
- These legal moves should use the existing `board_row` target shape unless implementation strongly justifies a new target type.
- Playing a special Mardroeme to a row should move the card to that board row as a row occupant.
- It must not contribute strength.
- It must not be eligible for Scorch.
- It must not be eligible for Decoy.
- It must not be eligible for Monsters keep-one-unit or Skellige round-three return.
- It must be swept at round cleanup like other row-occupying battlefield cards.

Implementation note:

The current `RowState.units` array is historically named but already guarded by catalog `kind` checks in scoring and faction abilities. It is acceptable in cCp9 for row-occupying Mardroeme special cards to live in the existing `board_row` zone and row occupant array, as long as all rule consumers continue to filter by `source.kind`.

### 3. Implement Mardroeme Row Settlement

Mardroeme is ongoing. It transforms Berserkers on its row when:

- a Mardroeme card is played onto a row;
- a unit or hero with Mardroeme is played onto a row;
- a Berserker is played onto a row where Mardroeme is already active;
- a Berserker is revived by Medic onto a row where Mardroeme is already active;
- a Berserker is placed by Muster or another engine board-entry path onto a row where Mardroeme is already active;
- future engine board-entry paths call the same helper.

Requirements:

- Add a centralized pure helper for row settlement. Suggested shape:

```ts
settleMardroemeRow({
  state,
  events,
  catalogLookup,
  boardSeat,
  row,
  triggerCardId,
})
```

- The helper should:
  - check whether the given row has at least one active Mardroeme card;
  - find all Berserker cards on that same row and board side;
  - transform all eligible Berserkers in a deterministic order;
  - avoid duplicate zone membership;
  - avoid infinite recursion;
  - emit explicit events for trigger, transform, success, and missing-replacement cases.
- Deterministic order should be row order at the time settlement begins.
- If multiple Berserkers are on the row, all transform in the same logical settlement.
- If a Mardroeme row settlement transforms zero cards, emit a resolved outcome such as `no_targets`; do not treat this as an error.
- If a Berserker has no transform link, do not remove it. Emit a structured deferred or resolved event that clearly says `missing_transform_link`.
- If the linked replacement source is not present in the controlling seat's side deck, do not remove the Berserker. Emit a structured deferred or resolved event that clearly says `missing_transform_replacement`.

### 4. Implement Berserker Transformation

When a Berserker transforms:

- the Berserker is removed from the game;
- it is not sent to any discard pile;
- it is not eligible for Skellige round-three return later;
- the replacement card is moved from the controlling player's side deck onto the same board side and row;
- the replacement should preserve the row position where practical;
- the replacement card controller should be the same as the Berserker controller;
- the replacement card owner remains unchanged;
- the replacement becomes a normal row unit for scoring, Scorch, round cleanup, and Skellige discard-return eligibility after it later reaches discard.

Use the Berserker source's first `linkedSourceIds` entry as the replacement source ID.

Controller policy:

- Use the Berserker card instance's `controller` to choose the side deck.
- Use the Berserker card instance's current `board_row` zone to choose the board side and row where the replacement lands.
- This keeps the behavior stable even if future cards create unusual control/board-side interactions.

Events and movement reasons:

- Add a new `card_moved.reason` such as `mardroeme_transform` for both:
  - Berserker -> removed_from_game;
  - replacement side_deck -> board_row.
- Add a focused event if useful, for example:

```ts
{
  type: "card_transformed";
  triggerCardId: CardInstanceId;
  fromCardId: CardInstanceId;
  fromSourceId: string;
  toCardId: CardInstanceId;
  toSourceId: string;
  seatId: SeatId;
  row: CatalogRow;
  abilityId: "berserker";
}
```

- Existing activity summaries and simulation logs should remain hidden-info safe. If adding event rendering, use public source lookup and do not expose hidden hand/deck identities.

### 5. Hook Settlement Into Existing Board Entry Paths

Mardroeme/Berserker must not depend on UI timing or ad hoc code paths.

Requirements:

- When `PlayCard` moves any card to a board row, row settlement must occur through the central helper where appropriate.
- When Medic resolves a prompt and revives a card, row settlement must occur through the same helper where appropriate.
- When Muster moves linked cards to a board row, row settlement must occur through the same helper where appropriate.
- When Skellige round-three return moves units from discard to board, row settlement should use the same helper where appropriate.
- Do not let `handoffTurn` happen before a Mardroeme/Berserker settlement that was caused by the played card finishes.
- If settlement opens no prompt, turn handoff behavior should remain as it is today.
- Do not implement Summon/Avenger as part of this hook work.

### 6. Keep Official Porting Classification Honest

After cCp9, `mardroeme`, `berserker`, and `skellige_storm` should no longer be reported as unsupported because the rule itself is unimplemented.

However, do not incorrectly mark the cBp3 combined official Berserker scrape candidates as catalog-ready if they still need data work.

Requirements:

- Update `src/data/catalog/official/game8Mapping.ts` so:
  - `skellige_storm` is not flagged as a metadata mismatch;
  - `mardroeme` is not flagged as an unimplemented rule;
  - `berserker` is not flagged as an unimplemented rule;
  - official Berserker candidates that are still represented as combined base/replacement rows, have null/zero source strength from the scrape, or lack a transform link remain visibly flagged with a non-rule issue such as `catalog_split_required` or `transform_link_required`.
- `officialPortingSummary.unsupportedAbilityCounts` should no longer count these abilities as unsupported.
- Candidate `portingStatus` should remain conservative:
  - image-missing candidates may still be `needs_image`;
  - split/link/strength problems may be `needs_review`;
  - only genuinely complete candidates should be `ready_for_catalog`.
- Update `tests/data/officialCatalogImport.test.ts` to reflect the new classification.

### 7. Card Studio Compatibility Guard

Changing `mardroeme` and `berserker` metadata to implemented can affect Card Studio playability.

Requirements:

- Mardroeme custom cards may become playable if they pass existing structural validation.
- Do not silently allow arbitrary custom Berserker cards to become playable unless the custom record has a valid transform link.
- At minimum, Card Studio validation should prevent a non-draft custom Berserker from being playable when:
  - it has no `linkedSourceIds[0]`;
  - the linked source ID cannot be resolved to a known card source.
- If the implementation cannot guarantee side-deck authoring support for custom Berserkers yet, keep custom Berserker records draft-only with a clear validation issue such as `berserker_requires_side_deck`.
- Add/update Card Studio tests for this guard if Card Studio validation changes.

### 8. Tests

Add focused tests. Prefer a small custom test catalog/deck fixture over promoting official cards.

Recommended new file:

```txt
tests/game/coreMardroemeBerserker.test.ts
```

Required coverage:

- Special Mardroeme legal moves:
  - special Mardroeme exposes own-row board targets;
  - it does not target weather;
  - it does not use the row horn slot.
- Skellige Storm:
  - metadata status is implemented;
  - scoring still treats it as ranged plus siege weather;
  - official-porting unsupported ability counts no longer include `skellige_storm`.
- Mardroeme play:
  - playing special Mardroeme onto a row with one Berserker transforms it;
  - playing special Mardroeme onto a row with multiple Berserkers transforms all of them;
  - Berserkers on other rows do not transform;
  - the Mardroeme card remains on the row until cleanup;
  - the Berserker moves to removed-from-game, not discard;
  - replacement comes from side deck and lands on the same board side and row;
  - no duplicate zone membership exists after transformation.
- Ongoing Mardroeme:
  - playing a Berserker onto an already-active Mardroeme row transforms immediately;
  - Medic reviving a Berserker onto an already-active Mardroeme row transforms immediately;
  - Muster or a direct engine board-entry helper path settles through the same code if practical.
- Missing replacement behavior:
  - missing `linkedSourceIds[0]` does not crash and does not remove the Berserker;
  - missing side-deck replacement does not crash and does not remove the Berserker;
  - each case emits a clear deferred/resolved event.
- Discard and later interactions:
  - a transformed Berserker is not returned by Skellige round-three discard return;
  - a transformed replacement that later goes to discard is eligible as a normal unit;
  - Scorch destroying a transformed replacement sends that replacement to the board-side discard pile.
- Official staging:
  - `mardroeme`, `berserker`, and `skellige_storm` are no longer counted as unsupported abilities;
  - official Berserker combined candidates still have a visible data/split/link issue until cBp4 promotion resolves them.
- Card Studio guard:
  - if ability metadata changes make Berserker "implemented", custom Berserker records without a valid transform link do not become silently playable.

## Acceptance Criteria

- Skellige Storm metadata is implemented and still scores correctly.
- Special Mardroeme has legal row targets and resolves through the engine.
- Unit/hero Mardroeme resolves through the engine.
- Berserker transforms from the side deck when Mardroeme is active on its row.
- Multiple Berserkers on one row transform in one settlement.
- Later Berserkers entering an active Mardroeme row transform immediately.
- Transformed Berserkers go to removed-from-game, not discard.
- Missing transform links/replacements are explicit, non-crashing outcomes.
- Official-porting card ability unsupported counts no longer list Mardroeme, Berserker, or Skellige Storm as unimplemented rule gaps.
- Official Berserker scrape candidates remain conservatively flagged for data split/link work until promotion.
- Existing current decks still play.
- Existing Card Studio custom behavior does not silently become less safe.
- Hidden-info boundaries remain intact.
- `docs/PROJECT_STATE.md` and the phase report are updated.
