# Implementation Spec: Cluster D, Phase 2 - Engine UI Shell and Mulligan/Pass Flow

## Goal

Create the first engine-backed UI surface using the Redux engine adapter from Cluster D Phase 1. This phase should make the pure engine visible and manually smoke-testable without replacing the legacy playable UI by default.

The target is a narrow vertical slice: start an engine match, complete human and AI mulligans, render engine state, allow pass, resolve round end through `ResolveRoundEnd`, and show game end/new game controls. Full card play, AI strategy migration, Medic/Decoy UI, and leader UI stay out of scope.

## Architecture Position

Cluster D Phase 1 added:

- `engineSlice`;
- `engineThunks`;
- `engineSelectors`;
- engine reducer registration;
- adapter tests.

The live app still defaults to `ReduxGameManager.tsx`, which uses legacy Redux state, legacy thunks, legacy score helpers, timers, and pre-decrement game-end logic. Phase 2 should add a parallel engine UI shell and an explicit opt-in switch so the current default playable screen remains available while the new path is exercised.

## Scope

1. Add an engine-backed UI shell.
   - Suggested component: `src/components/game/EngineGameManager.tsx`.
   - Optional supporting components may live under `src/components/engine/` or `src/components/game/engine/`.
   - The shell should use only the engine Redux lane for rules and state:
     - `startEngineMatch`;
     - `dispatchEngineCommand`;
     - `resolveEngineRoundEnd`;
     - `engineSelectors`.
   - Do not read from or dispatch to legacy `gameSlice`, legacy `gameThunks`, legacy `gameSelectors`, or `useReduxAI` inside the engine shell.

2. Add an explicit app switch.
   - Update `src/App.tsx` so the legacy `ReduxGameManager` remains the default.
   - Render `EngineGameManager` only when explicitly enabled.
   - Accept at least one of:
     - query parameter `?engine=1`;
     - environment flag `VITE_ENGINE_UI=1`.
   - Prefer supporting both if simple.
   - Do not persist the flag to localStorage.
   - The report must document the exact URL or env command used for manual smoke testing.

3. Start an engine match on shell mount.
   - If no engine match exists, dispatch `startEngineMatch`.
   - Support a deterministic seed from query parameter, for example `?engine=1&seed=smoke-dp2`.
   - If no seed is provided, allow the Phase 1 default seed policy.
   - Display the seed somewhere compactly enough for debugging, but avoid turning the page into a diagnostics panel.
   - Add a "New Game" control that starts another engine match after game end or when explicitly clicked. It must not auto-start a new match.

4. Render engine state, not legacy state.
   - Use engine view-model selectors as the source of truth.
   - Render at minimum:
     - both seat statuses;
     - faction/leader status;
     - gems;
     - current round;
     - current phase;
     - current turn;
     - hand size for both seats;
     - human hand card details;
     - AI hand count only by default;
     - board rows for both seats;
     - weather cards;
     - deck/discard counts;
     - score totals from `selectEngineScoreBreakdown`.
   - If current selectors lack image paths or display fields needed by UI cards, extend engine selectors with serializable view-model fields rather than importing catalog data directly in many components.
   - Do not use legacy `calculateTotalScore`, `calculateRowStrength`, or `src/utils/gameHelpers.ts`.

5. Reuse visuals carefully.
   - Reuse existing CSS and `GwentCard` for display only if a small, pure adapter converts an engine card view model into a legacy display-card shape.
   - That adapter must not encode rules, legal moves, scoring, or ownership policy.
   - If reusing `GwentCard` causes type or rule leakage, create a small engine card component instead.
   - Do not pass engine state into `GameBoard` if doing so requires fake legacy `GameState` reconstruction with rule meaning. A purpose-built engine board view is preferred.

6. Implement human mulligan UI.
   - During `match.phase === "mulligan"`:
     - show the human hand;
     - allow selecting zero, one, or two human hand cards;
     - enable a "Keep" or "Confirm" control that dispatches `ChooseMulligan` for the human seat with selected card IDs;
     - use legal moves or engine constraints to enforce the max of two cards.
   - After human mulligan is complete, the human should not be able to mulligan again.
   - Do not use the legacy `GameCardsSelector` redraw modal for engine mulligan.

7. Add a scripted preview AI for this shell only.
   - This is not the full AI migration.
   - If the AI seat is in mulligan and not complete, dispatch `ChooseMulligan` with `cardIds: []`.
   - If the AI seat is current turn during `playing`, dispatch `Pass`.
   - Do not use `useReduxAI`, `AIStrategyCoordinator`, or legacy AI score helpers.
   - Avoid timers. If an effect is used to dispatch the scripted AI action, guard it carefully against duplicate dispatch by checking phase, status, lock, current turn, and pass/mulligan completion.
   - The report should call this "scripted preview AI" and not present it as strategic AI.

8. Implement human pass and round resolution.
   - During `playing`, if it is the human seat's turn and the human has not passed, show an enabled Pass control.
   - Pass must dispatch `{ type: "Pass", seatId: humanSeat }` through `dispatchEngineCommand`.
   - When both seats have passed and `match.phase === "round_end"`, show a Resolve Round control.
   - Resolve Round must dispatch `ResolveRoundEnd` through `resolveEngineRoundEnd` or `dispatchEngineCommand`.
   - Do not use `setTimeout` for pass-to-round-end or round resolution.
   - Do not compute round winner, gem loss, cleanup, next turn, or game winner in React.

9. Show prompt state generically.
   - If `match.pendingPrompt` exists, render prompt options from `selectEnginePrompt`.
   - Selecting an option dispatches `ChoosePromptOption`.
   - The prompt renderer can be visually simple in this phase because ordinary card play is out of scope.
   - Do not reuse legacy Medic-chain state as authoritative.

10. Handle game end.
    - If `match.phase === "game_end"`, show the winner from engine selectors and a New Game control.
    - Do not auto-new-game.
    - Do not write match wins to localStorage in this phase.
    - Do not increment legacy `gameScore`.

11. Manage selected UI state through the engine lane.
    - Use `engineSelectedCardSet` and `engineSelectedMoveSet` or equivalent UI-only engine slice actions.
    - Clear selection after mulligan confirmation, pass, round resolution, and new game.
    - Selection must not drive rule outcomes except by choosing an engine legal command.

12. Add smoke checklist documentation.
    - Create or update a smoke note in the implementation report.
    - Required manual flow:
      1. open legacy default app and confirm it still renders;
      2. open engine shell with `?engine=1&seed=dp2-smoke`;
      3. confirm engine match starts with human NR and AI Nilfgaard;
      4. choose zero, one, or two mulligan cards and confirm;
      5. confirm scripted AI mulligan completes;
      6. pass as human;
      7. confirm scripted AI passes when it is AI turn;
      8. click Resolve Round;
      9. confirm round/game state updates from engine events and no auto-new-game occurs.

13. Add tests.
    - Add focused tests where practical without introducing a large browser test stack.
    - Suggested options:
      - pure tests for any engine card display adapter;
      - Redux tests for the scripted preview AI helper if extracted;
      - selector tests for extended engine view-model fields such as image paths;
      - a lightweight React render smoke using `react-dom/server` and a test store if feasible.
    - Do not add React Testing Library unless the report explains why the dependency is justified.

14. Create the required implementation report:
    - `audit/reports/2026-04-25-cDp2-report.md`

## Out Of Scope

- Do not make the engine UI the default route unless explicitly enabled by query/env flag.
- Do not migrate full card play UI.
- Do not implement legal row targeting, weather targeting, Horn placement, Decoy selection, Medic revive selection, Scorch targeting, or leader use in the live engine shell beyond generic prompt display.
- Do not migrate strategic AI.
- Do not remove or rewrite legacy `ReduxGameManager`, `GameBoard`, `gameSlice`, `gameThunks`, `gameSelectors`, `useReduxAI`, or legacy card data.
- Do not persist match history, game scores, or flags to localStorage.
- Do not add deck builder, Card Studio, PvP, AI-vs-AI simulation, or ML export.

## Acceptance Criteria

- Legacy app remains the default and still renders.
- Engine shell renders only under the explicit flag/query parameter.
- Engine shell starts a match through `startEngineMatch`.
- Engine shell uses engine selectors and thunks, not legacy rule helpers.
- Human can complete mulligan with zero, one, or two cards.
- Scripted preview AI completes mulligan with zero cards.
- Human can pass through an engine `Pass` command.
- Scripted preview AI can pass through an engine `Pass` command.
- Round end is resolved only through engine `ResolveRoundEnd`.
- No new engine UI path computes scores, round winner, gem loss, game winner, or cleanup outside the engine.
- No new engine UI path uses `setTimeout` for rule transitions.
- Game end displays from engine state and does not auto-start a new game.
- AI hand card details are not shown in the default human engine view.
- Existing live legacy UI behavior is not intentionally changed.
- `npm test` passes.
- `npm run build` passes.

## Required Tests

At minimum, cover:

- App switch helper or component selection returns legacy by default and engine when enabled, if extracted.
- Engine card display adapter maps instance/source fields without adding rule behavior, if one is added.
- Engine view-model selectors expose image/display fields needed by the shell.
- Human mulligan command flow through Redux adapter updates engine match and clears UI selection.
- Scripted preview AI mulligan dispatches only once for an incomplete AI mulligan.
- Scripted preview AI pass dispatches only when it is AI turn, phase is `playing`, no prompt is pending, and no lock blocks action.
- Resolve Round button/helper dispatches `ResolveRoundEnd` and records `round_resolved`.
- Default human-facing engine view exposes AI hand count but not AI hand card details.
- No new engine UI files import `src/utils/gameHelpers.ts`.

## Notes For The Coding Instance

- Keep this phase as a bridge. The engine UI can be limited, but it must be honest and stable.
- Prefer small new engine-specific components over forcing normalized engine state through legacy `GameBoard` props.
- It is acceptable for cards to be display-only during `playing`; pass/round resolution is the intended vertical slice.
- Do not introduce another rules adapter in the UI. Every rule transition must go through `dispatchEngineCommand`.
- If a UI action is not backed by a legal engine command yet, leave it disabled rather than approximating behavior.
