# Implementation Spec: Cluster C, Phase 4 - Legal Move Generator

## Goal

Add the pure engine legal-move generator over the normalized match state. This phase should make the engine the single source of legal actions for future UI, AI, PvP, AI-vs-AI simulation, and ML action masks. It should not execute moves yet; it should only answer "what can this seat legally do from this state?"

## Architecture Position

Phase 3 created compact runtime state:

- `cardsById` stores runtime instances;
- zones store `instanceId[]`;
- instances carry `sourceId`, `owner`, `controller`, and `zone`;
- catalog source data lives outside runtime instances.

Phase 4 must preserve that model. Legal move generation may accept catalog source data or a catalog lookup as input, but it must not copy full catalog card records into runtime card instances.

## Scope

1. Add a legal move module.
   - Suggested file: `src/game/core/legalMoves.ts`.
   - Export it from `src/game/core/index.ts`.
   - Keep it pure: no React, Redux, DOM, localStorage, timers, or mutation of input state.

2. Define legal-move types.
   - Add a serializable `LegalMove` union suitable for UI rendering and AI/ML action masks.
   - Each legal move should have:
     - stable deterministic `moveId`;
     - `seatId`;
     - action type;
     - source card/leader instance where applicable;
     - target metadata where applicable;
     - enough display/diagnostic metadata to let adapters render options without recalculating rules.
   - Suggested move kinds:
     - `choose_mulligan`
     - `play_card`
     - `pass`
     - `use_leader`
     - `choose_prompt_option` as a placeholder shape if useful.

3. Add target types.
   - Suggested target union:
     - own or opponent `board_row`;
     - `row_horn`;
     - `weather`;
     - `card_instance`;
     - `none`.
   - Targets must be explicit and serializable.

4. Add catalog lookup support.
   - Suggested API:
     ```ts
     getLegalMoves({
       state,
       seatId,
       catalogCards,
       catalogLeaders,
     }): LegalMove[]
     ```
   - A prebuilt lookup helper is acceptable.
   - Do not store full catalog records inside `MatchState.cardsById`.

5. Support mulligan-phase legal moves.
   - In `phase === "mulligan"`, return legal `choose_mulligan` moves for the acting seat.
   - Use the current rules baseline of choosing 0, 1, or up to 2 hand cards unless the implementation adds a clear future-compatible mulligan state field.
   - The moves must reference only the acting seat's hand card IDs.
   - Do not expose opponent hand IDs through the acting seat's legal moves.
   - Do not implement `ChooseMulligan` execution in this phase.

6. Support playing-phase turn gates.
   - In `phase === "playing"`, only the current turn seat can play, pass, or use leader.
   - A passed seat has no card/leader/pass moves unless later rules explicitly require a prompt response.
   - In non-playing phases, do not return play/pass/leader moves.

7. Support basic card play legal moves.
   - Unit and Hero cards:
     - legal rows come from catalog `rows`;
     - normal cards target the acting seat's board rows;
     - Spy cards target the opposing seat's board rows;
     - Agile/multi-row cards must produce one legal move per legal row.
   - Special Weather cards:
     - Frost, Fog, Rain, Skellige Storm, and Clear Weather target the shared weather zone.
     - Clear Weather should be legal even if no weather is active, matching the rulebook-derived no-op-but-discard behavior.
   - Special Commander's Horn:
     - targets own `row_horn` slots;
     - must not produce a move for an occupied horn slot.
   - Special Decoy:
     - targets non-Hero unit card instances on the acting seat's own board side;
     - must not target opponent board cards;
     - must not target Heroes;
     - must not target row horn cards, weather cards, or other non-unit placeholders.
   - Special Scorch:
     - may target `none` or a global target placeholder, because target resolution belongs to the future ability resolver phase.
   - Planned/unimplemented ability cards:
     - If a current catalog card has an ability with no legal placement semantics yet, either omit it from legal moves or emit a clearly marked unsupported diagnostic through a separate helper. Do not treat unsupported moves as legal executable moves.

8. Support leader legal moves minimally.
   - If necessary, extend `SeatState` with a pure engine field such as `leaderUsed: boolean`, initialized to `false` in setup.
   - Return `use_leader` only in `playing` phase for the current turn seat when:
     - the seat is not passed;
     - a leader instance exists;
     - the leader is not used;
     - the leader ability is known in catalog metadata.
   - Do not resolve leader effects in this phase.
   - If a leader requires target selection, represent target requirements as metadata or omit until prompt support, but document the decision.

9. Add hidden-information discipline.
   - Legal moves for a seat must not include opponent hand card IDs, opponent deck order, or other hidden private info.
   - It is acceptable for the generator to inspect full state internally, but returned moves must only include public targets and acting-seat private cards.
   - Add tests for this.

10. Add tests.
   - Mulligan moves include only acting-seat hand IDs and support 0/1/2-card choices or the documented equivalent.
   - Wrong-turn and passed-seat gates work.
   - Pass move is present only for current turn, unpassed seat during playing phase.
   - Normal unit row moves use catalog rows.
   - Agile/multi-row cards produce moves for every legal row.
   - Spy targets opponent rows.
   - Horn does not target occupied horn slots.
   - Decoy targets own non-Hero units only and excludes opponent units/Heroes.
   - Weather and Skellige Storm target weather.
   - Clear Weather is legal even with no active weather.
   - Leader use is gated by turn/pass/used status.
   - Returned legal moves do not leak opponent hand IDs.
   - Existing setup/catalog tests continue to pass.

11. Create the required implementation report:
   - `audit/reports/2026-04-25-cCp4-report.md`

## Out Of Scope

- Do not execute legal moves.
- Do not implement `PlayCard`, `Pass`, `UseLeader`, `ChooseMulligan`, or prompt command resolution.
- Do not implement scoring.
- Do not implement ability effects.
- Do not implement round end or game end.
- Do not migrate Redux/UI/AI to legal moves yet.
- Do not add UI diagnostics unless needed for tests.
- Do not change live gameplay behavior.
- Do not fix legacy audit bugs in the active Redux path.

## Acceptance Criteria

- `src/game/core` exports a pure legal-move generator.
- Legal moves are deterministic and serializable.
- Legal moves use normalized runtime instances plus external catalog lookup data.
- Mulligan and playing-phase gates are represented.
- Basic current card placement legality is represented for units, heroes, Spies, weather, Horn, Decoy, Scorch, Clear Weather, and leaders.
- Agile/multi-row cards produce all legal row options.
- Legal moves do not expose hidden opponent hand/deck information.
- Tests cover the legal-move surfaces listed above.
- `npm test` passes.
- `npm run build` passes.
- Existing live gameplay behavior is not intentionally changed.

## Things To Watch Out For

- The generator is a query, not a resolver. Avoid mutating state or partially applying rules.
- Do not smuggle full card sources into `CardInstance`.
- Do not implement a parallel AI rules model. This legal-move API is the future AI action source.
- Be careful with Decoy and Spy. The audit found multiple current bugs there, and this phase should avoid reproducing those target-scope mistakes in the new engine.
- Be careful with Horn. The new engine has explicit `row.horn`, so legal moves should reject occupied horn slots.
- Keep legal move IDs stable. They will become useful for UI keys, replay, AI policies, and ML action masks.
- If supporting all 0/1/2 mulligan combinations feels too broad, document the chosen representation and ensure it can still express the full legal choice later.
- If this phase needs a small state field such as `leaderUsed`, add it in the core state only and update setup tests. Do not touch legacy Redux state.
