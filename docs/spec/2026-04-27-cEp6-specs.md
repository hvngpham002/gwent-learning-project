# Implementation Spec: Cluster E, Phase 6 - Mulligan Screen And Product Navigation

## Goal

Turn the authentic product flow from "pre-game directly drops into the match table's mulligan phase" into a clearer front-facing flow:

1. Pre-game setup.
2. Dedicated mulligan screen.
3. Match table.
4. Round and match-end navigation.

cEp6 should make the game feel like a coherent product path without changing card content, AI policy, deck validation, route promotion, or unrelated rules. The underlying engine owns mulligan legality. This phase should present that engine phase as a polished screen and make the navigation between existing product screens explicit and predictable.

This phase intentionally replaces the earlier tentative "cEp6 Card Studio" slot. Card Studio and content authoring move to the next Cluster E content phase after the playable product loop is less awkward.

Post-implementation amendment, 2026-04-28: user review clarified that the intended Gwent mulligan rule is sequential one-card redraws up to two times, not choosing up to two cards in one command. This spec now reflects the implemented final behavior: each legal redraw command contains zero or one selected current-hand card, the replacement card is immediately part of the hand, and that replacement may be selected for the second redraw.

## Architecture Position

Before this phase:

- `/` remains the legacy UI.
- `/?engine=1` remains the diagnostic engine shell.
- `/?engine=1&ui=authentic` opens authentic pre-game.
- `/?engine=1&ui=authentic&view=deck-builder` opens the authentic deck builder.
- `/?engine=1&ui=authentic&view=match` starts a direct authentic match.
- `AuthenticMatchScreen` renders the full match table even while `match.phase === "mulligan"`.
- Human mulligan is currently selected from the hand strip and confirmed from the right action panel.
- AI mulligan is already driven by `legal-heuristic-v0` through legal engine moves.

After this phase:

- Route behavior remains opt-in and backward compatible.
- Starting any authentic match first shows a dedicated product mulligan flow before the match table. The screen remains through human mulligan, hidden-safe AI presentation, player review, and the `Start the match?` modal.
- Confirming mulligan dispatches the exact engine `ChooseMulligan` command for a legal move. The match table appears only after the engine has left mulligan, the AI presentation has completed, and the player confirms the start modal.
- The match table no longer needs to expose mulligan controls in its normal action rail.
- Product navigation actions have stable meanings: back to setup, deck builder, rematch, next round, and match-end exits.
- No hidden AI hand/deck identities are exposed on the mulligan screen or in navigation summaries.

## Scope

### 1. Add A Dedicated Authentic Mulligan Screen

Create a product mulligan screen for the authentic UI track.

Recommended files:

- `src/components/gwent/AuthenticMulliganScreen.tsx`
- `src/components/gwent/authentic-mulligan.css`
- pure helper additions in `matchViewModel.ts` or a small adjacent helper if needed.

Requirements:

- The screen should render for the authentic product mulligan flow from match creation until the player confirms the start-match modal. This includes human mulligan, AI choosing/presentation, and post-mulligan review.
- It should be shown for:
  - pre-game `begin match →`;
  - deck-builder `play →`;
  - direct `/?engine=1&ui=authentic&view=match`;
  - rematch.
- It should use real engine state:
  - human hand from `selectEngineHumanHand`;
  - legal moves from `selectEngineLegalMovesForHuman`;
  - human/AI seat/faction/leader/deck count context from existing selectors;
  - seed/policy labels from existing setup/status context.
- It must not compute or mutate rule state outside engine commands.
- It must not use timers for rule transitions.
- It must not reveal AI hand identities. AI hand should be represented only as card backs/counts/status.
- It should use existing authentic card components and shared dimensions.
- Human cards should be selectable one card at a time.
- Selected cards should have a clear product affordance such as lift, checkmark, or accent outline.
- Do not add a second visible card name or duplicate strength overlay outside the card face. The real card face should remain the primary visual.
- When one card is selected, clicking another unselected card must not change the selected set. Deselecting the selected card should allow another choice.
- Confirming zero or one card should be possible only when that exact selection maps to an engine legal `choose_mulligan` move. Zero selected cards is the keep-hand path; one selected card redraws immediately and leaves the seat in mulligan if a second redraw remains.
- The primary button label should make sense for zero cards, for example `keep hand`, and for a selected card, for example `confirm mulligan`.
- If no legal confirm move exists, disable the primary action and surface a compact non-blocking status.

Visual direction:

- Use the same parchment table vocabulary as pre-game and match.
- Target a centered product surface, not a diagnostic panel.
- Suggested layout:
  - top bar with `← setup`, title `Mulligan`, round/setup seed context, and policy label;
  - opponent summary strip with hidden hand count and faction/leader;
  - central hand row/grid with authentic cards;
  - bottom action bar with selected count and primary confirm action.
- Mobile must stack cleanly at `390px` without horizontal overflow.

### 2. Legal-Move-Backed Mulligan Command Flow

Use the existing legal-move contract.

Requirements:

- Derive the currently selected mulligan move by comparing selected card instance IDs to legal `choose_mulligan` moves.
- Dispatch:

```ts
{
  type: "ChooseMulligan",
  seatId: humanSeat,
  cardIds: selectedMulliganMove.cardIds
}
```

- Do not construct a mulligan command from selected IDs unless a legal move exists.
- Clear local/Redux card selection after successful command application.
- Do not change the engine's mulligan semantics:
  - draw 10 during setup;
  - allow up to two redraw commands per seat;
  - each redraw command selects zero or one current-hand card;
  - a one-card redraw draws the replacement immediately, then shuffles the chosen card back into the deck;
  - the replacement card from the first redraw is eligible for the second redraw.
- AI mulligan remains controlled by `legal-heuristic-v0`. If the human completes mulligan while AI is still resolving or presenting, the mulligan screen should show a hidden-safe waiting/presentation state until the player can confirm starting the match.

Implementation guidance:

- If reusable selection helpers are added, keep them pure and test them.
- Avoid duplicating existing `sameCardSelection` logic in several components. Move it to a helper if both `AuthenticMatchScreen` and `AuthenticMulliganScreen` need it.
- Once the dedicated screen owns mulligan, remove or hide the old in-match mulligan block from `ActionPanel` during normal match-table rendering.

### 3. Product Navigation State

Make the authentic app's screen transitions explicit without adding a router dependency.

Requirements:

- Keep `AuthenticGameApp` as the small route coordinator.
- Preserve current query route behavior:
  - default authentic route = pre-game;
  - `view=pregame` = pre-game;
  - `view=deck-builder` = deck builder;
  - `view=match` = direct match;
  - `view=harness` = harness.
- Add any needed in-app state to distinguish setup/deck-builder/match flow, but do not encode runtime engine state into the URL.
- Pre-game `begin match →` should start the selected setup and land on the mulligan screen first.
- Deck-builder `play →` should start the selected deck setup and land on the mulligan screen first.
- `← back` from deck builder should continue returning to pre-game.
- `setup` or equivalent from mulligan should return to pre-game and discard the in-progress match after confirmation.
- Confirming setup return from mulligan or match should clear the engine adapter state so a later start with the same setup/seed creates a fresh mulligan instead of reusing prior command history.
- Match table top navigation should use clear product labels. Recommended:
  - `rematch` for restarting the same setup;
  - `change deck` or `setup` for returning to pre-game.
- Returning to setup from an in-progress match should require an authentic confirmation modal, not `window.confirm`.
- Leaving after game end does not need the same warning.
- Keep local deck store state intact across navigation.
- Do not introduce browser history complexity in this phase.

Seed/rematch rule for this phase:

- Preserve existing deterministic behavior unless there is a compelling implementation reason to change it: rematch may reuse the same setup and seed.
- If the implementation changes seed behavior, it must be explicit in the report and visible in the UI.

### 4. Round And Match-End Navigation

Tighten the existing round/match alert actions so they complete the product loop.

Requirements:

- Round-resolved ledger stays a confirmation overlay with `next round →` behavior that dismisses the overlay only. It must not compute or dispatch round rules.
- Match-concluded ledger should provide clear exits:
  - rematch: restarts the same setup and returns to the mulligan screen;
  - change deck/setup: returns to pre-game;
  - if a `main menu` label is introduced, it should also return to the authentic pre-game surface for now, because there is no separate main menu yet.
- Do not invent ranked/MMR/progression data.
- Do not add a new route promotion or change `/`.
- Continue using `Alert` ledger components from `src/components/gwent/alert/`.
- Keep button hover behavior consistent with the current alert/button decisions; do not add new decorative hover transforms.

### 5. Visual Quality Guardrails

Cluster E frontend work has been brittle. Treat this as an acceptance area, not a nice-to-have.

Requirements:

- Reuse existing authentic token classes and button visual language.
- Keep typography compact. Do not enlarge body/control text beyond the surrounding pre-game/deck-builder/match scale.
- No nested cards inside cards.
- No marketing hero layout.
- No duplicated labels under cards when the card face already communicates the name.
- No duplicated strength overlays.
- No wrong-faction/back/card-art fallback regressions.
- Buttons on new screens should feel consistent with current pre-game/match/deck-builder controls.
- Verify desktop and mobile visually through Playwright, not only unit tests.

## Out Of Scope

Do not implement:

- Card Studio.
- Custom card creation.
- Image upload or repo image management.
- Catalog code generation.
- New card content.
- New deck-construction rules.
- Unrelated mulligan variants such as Bo1, training free mulligans, undo, or bulk two-card redraw commands.
- Drag-and-drop card play.
- Match animations beyond existing safe motion hooks.
- Ranked mode, MMR, progression, or account state.
- Bo1, training mode, free mulligans, undo, or seed-suite UI behavior.
- PvP or AI-vs-AI product modes.
- Promotion of authentic UI to `/`.
- Deleting or rewriting the diagnostic engine shell.

## Tests

Add risk-scaled tests. Required coverage:

Unit/helper tests:

- selected mulligan IDs map only to a legal `choose_mulligan` move;
- selected-card cap is enforced at one card per redraw command;
- deselecting a selected card frees the redraw slot;
- a second one-card redraw can select the replacement card from the first redraw when legal;
- zero-card keep-hand confirmation is legal when the engine exposes that move;
- mulligan view model does not include AI hand card names/source IDs/instance IDs;
- navigation helper/state, if extracted, maps setup/deck-builder/rematch/change-deck actions predictably.

## Acceptance Criteria

cEp6 is complete when:

- authentic match starts route through a dedicated mulligan screen before the match table;
- human mulligan is fully legal-move-backed and uses sequential one-card redraws up to two times;
- AI mulligan presentation runs after the human keep/confirm decision and before the match-start modal;
- AI hidden information remains hidden;
- old match-table mulligan controls no longer clutter normal play;
- pre-game, deck-builder, mulligan, match, round overlay, and game-end exits form a coherent loop;
- leaving an in-progress match uses an authentic confirmation modal and clears stale engine state when setup return is confirmed;
- rematch returns to the mulligan screen and starts a fresh engine match using the documented seed behavior;
- route behavior for `/`, `?engine=1`, `?engine=1&ui=authentic`, `view=deck-builder`, `view=match`, and `view=harness` is preserved;
- desktop and mobile browser smoke pass;
- `docs/PROJECT_STATE.md`, any product-flow docs, and the phase report are updated.
