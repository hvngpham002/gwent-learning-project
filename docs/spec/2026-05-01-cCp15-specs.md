# Implementation Spec: Cluster C, Phase 15 - King Bran Weather Passive

## Intent

Implement King Bran's passive leader ability:

```text
Friendly Units only lose half their Strength in bad weather conditions. (Rounded down.)
```

cCp14 finished active weather-pulling leaders. cCp15 should finish the weather rules tranche by wiring the already-existing scoring policy concept (`WeatherPolicy = "king_bran"`) to the actual leader identity in match state.

This is a pure-engine rules phase. King Bran is passive. He must not become a clickable `UseLeader` command and must not consume `leaderUsed`.

## User-Facing Rule Decision For This Phase

King Bran is passive and always on for the seat whose leader source is `skellige.king-bran`.

Required interpretation:

- Applies only to the King Bran player's friendly non-hero Unit cards.
- Applies only when a unit's row is affected by active bad weather:
  - Frost affects Close;
  - Fog affects Ranged;
  - Rain affects Siege;
  - Skellige Storm affects Ranged and Siege.
- Does not affect Heroes.
- Does not affect the opponent.
- Does not depend on which player controlled or played the weather card.
- Replaces normal weather's "set Strength to 1" effect for that seat's affected units.
- Formula is already documented in `docs/gwent-rules.md`: the unit loses half its printed/current weather-stage strength, rounded down. In the current scoring pipeline this is:

```ts
afterWeather = printedStrength - Math.floor(printedStrength / 2)
// equivalent to Math.ceil(printedStrength / 2) for positive printed strengths
```

Examples:

- printed 7 under matching weather becomes 4 before Tight Bond/Morale/Horn;
- printed 4 under matching weather becomes 2 before Tight Bond/Morale/Horn;
- printed 1 under matching weather remains 1.

Then existing scoring order continues unchanged:

1. weather / King Bran weather policy;
2. Tight Bond;
3. Morale Boost;
4. Commander's Horn.

## Required Implementation

### 1. Ability Metadata

Promote `weather_half_penalty` in `CATALOG_LEADER_ABILITY_METADATA` from `placeholder` to `implemented`.

Keep every other placeholder leader ability unchanged.

After cCp15, the implemented leader ability metadata set should include:

```text
clear_weather
play_any_weather
play_fog
play_frost
play_rain
weather_half_penalty
```

Important: implemented metadata does **not** mean every ability produces an active `use_leader` move. King Bran is implemented as a passive.

### 2. Separate Active Leaders From Passive Implemented Leaders

Update official leader manifest/tests carefully.

Current cCp14 wording equates implemented metadata with `executableLeaderSourceIds`. That becomes misleading in cCp15 because King Bran is implemented but passive.

Required outcome:

- `skellige.king-bran` must be treated as implemented for rule-gap and validation purposes.
- `skellige.king-bran` must **not** be treated as an active executable `UseLeader` command.
- `getLegalMoves` must emit no `use_leader` move for King Bran.

Preferred manifest cleanup:

- Keep `executableLeaderSourceIds` for active leader commands only:
  - clear weather Foltest;
  - the four cCp14 weather-pulling leaders.
- Add a clear passive/implemented manifest field if useful, for example:
  - `implementedPassiveLeaderSourceIds: ["skellige.king-bran"]`, or
  - `implementedLeaderSourceIds` containing active + passive implemented leaders.
- Remove `weather_half_penalty` from `placeholderLeaderAbilityIds`.
- Update comments so future agents do not confuse "implemented" with "active command".

If you choose a different manifest shape, keep the same semantic distinction explicit in code and tests.

### 3. Derive Weather Policy From Leader Identity

Add a small pure helper in `src/game/core/scoring.ts` or a closely related pure module.

Recommended shape:

```ts
export const getWeatherPolicyBySeat = (
  state: MatchState,
  catalogLeaders: readonly CatalogLeaderSource[],
): Partial<Record<SeatId, WeatherPolicy>> => { ... }
```

Required behavior:

- Look up each seat's `leaderSourceId` in `catalogLeaders`.
- If the leader's ability is `weather_half_penalty`, set that seat's policy to `"king_bran"`.
- Do not infer King Bran from faction alone. A Skellige seat with Crach should use normal weather.
- Missing leader catalog entries should not throw from scoring; treat as normal policy.
- The helper must be deterministic and side-effect-free.

### 4. Integrate Policy Into Scoring

`calculateScores` already accepts:

```ts
weatherPolicyBySeat?: Partial<Record<SeatId, WeatherPolicy>>;
catalogLeaders?: readonly CatalogLeaderSource[];
```

Wire those together so normal callers get King Bran automatically when they pass `catalogLeaders`.

Recommended precedence:

```ts
const derived = catalogLeaders ? getWeatherPolicyBySeat(state, catalogLeaders) : {};
const policyBySeat = { ...derived, ...weatherPolicyBySeat };
```

This preserves existing direct tests that pass `weatherPolicyBySeat` explicitly while letting production consumers derive the policy from the match's leaders.

Keep the existing modifier marker:

```text
weather:king_bran
```

on affected score entries. Normal weather should continue to mark `weather`.

### 5. Use King Bran Policy Everywhere Effective Strength Matters

Do not wire King Bran only into final round settlement. Effective strength is used for several engine surfaces.

Ensure King Bran policy affects:

- round totals and `roundHistory.scoreBySeat`;
- game-end and gem-loss decisions through `ResolveRoundEnd`;
- row totals exposed by `calculateScores`;
- effective-strength badges/selectors that already consume engine score breakdowns;
- Special Scorch target selection;
- unit-source whole-board Scorch target selection;
- row-scoped unit Scorch target selection;
- AI/observation/simulation score summaries that already call `calculateScores` with `catalogLeaders`.

Implementation implications:

- `determineRoundResult` already passes `catalogLeaders` to `calculateScores`; after step 4, that should be enough for final round scoring.
- `src/store/selectors/engineSelectors.ts`, `src/game/ai/seatObservation.ts`, `src/game/sim/exportObservation.ts`, and `src/game/sim/metrics.ts` already pass `catalogLeaders`; after step 4, they should inherit the passive automatically.
- `src/game/core/commands.ts` and `src/game/core/abilities.ts` have Scorch paths that currently call `calculateScores` without leader catalog context. Update these paths so Scorch uses the same effective-strength policy as round scoring.
- If `resolveCardAbilities` or prompt resolution needs `catalogLeaders` to make Scorch correct after Medic revival, thread `catalogLeaders` through those pure engine calls rather than using global imports.

Do not import runtime catalog singletons into pure core modules.

### 6. Legal Moves And Commands

`weather_half_penalty` is passive.

Required behavior:

- King Bran should not generate a legal `use_leader` move.
- `UseLeader` with King Bran should remain illegal because no legal move exists.
- `leaderUsed` should remain `false` for King Bran throughout normal play.
- No `leader_used` event should fire for the passive.

`getLeaderMove` currently returns `[]` for implemented abilities that are neither `clear_weather` nor weather-pulling. Keep or make this explicit with tests.

Update `docs/gwent-rules.md` near §17.12.

Document:

- His weather-half rule applies to friendly non-hero units only.
- It applies to Frost/Fog/Rain/Skellige Storm on matching rows.
- Formula and examples:
  - 7 becomes 4;

- King Bran's weather adjustment happens in the weather step before Tight Bond, Morale Boost, and Horn.
- Opponent rows still use normal weather unless they also somehow have King Bran as leader.

Do not rewrite the rulebook wholesale.

## Acceptance Criteria

- `weather_half_penalty` metadata is `implemented`.
- `skellige.king-bran` is treated as an implemented passive leader, not an active executable `UseLeader` command.
- King Bran derives weather policy from leader identity, not faction alone.
