# Implementation Spec: Cluster C, Phase 19 - Row-Wide Horn-Like Leader Passives

## Intent

Implement Tranche 1 from `docs/leader-ability-matrix.md`: the passive
row-wide horn-like official leader abilities.

This phase should make these four leader records mechanically playable through
the pure scoring pipeline:

- `northern-realms.foltest-the-siegemaster` — `double_siege`
- `monsters.eredin-commander-of-the-red-riders` — `double_close`
- `scoiatael.francesca-findabair-queen-of-dol-blathanna` — `double_close`
- `scoiatael.francesca-findabair-the-beautiful` — `double_ranged`

These are passive, always-on leader effects. They must not produce legal
`use_leader` moves, must not set `leaderUsed`, and must not emit a
`leader_used` event. They should behave like a row-specific Commander's Horn
effect for the leader owner's matching row, with normal horn non-stacking
rules.

The implementation should mirror the shape of cCp15's King Bran passive:
derive a policy from the acting leader identity, feed it into scoring, and
ensure any engine path that depends on effective strength observes the same
policy through the central scoring pipeline.

## Locked Product Decisions From Post-cCp18 Review

Record these in `docs/leader-ability-matrix.md` during cCp19 so future specs do
not re-ask the same questions. Implement only the row-horn subset in this
phase.

1. `docs/gwent-rules.md` §16 mislabeled an Eredin row. `Eredin: Bringer of
   Death` is the discard-restore leader; `Eredin: Destroyer of Worlds` remains
   `discard_two_draw_one_from_deck`.
2. `Emhyr: The Relentless` is `draw_opponent_discard`: draw a card from the
   opponent's discard pile. Update the rulebook text to match the catalog.
3. `optimize_agile_rows` is automatic placement, not player row choice.
4. `discard_two_draw_one_from_deck` sequence: discard up to two cards from hand,
   then show all remaining deck cards, choose any one card, draw it, then
   shuffle the remaining deck.
5. `discard_two_draw_one_from_deck` may be used with one card in hand; zero
   cards in hand makes it unusable.
6. `random_medic` is a passive mutation of Medic effects. The randomly revived
   candidates are non-hero unit cards only. It does not affect hero sources
   that have Medic.
7. `look_three_cards` is a one-time modal. If the player dismisses it, it
   cannot be reopened.
8. `cancel_leader` can be used as a reaction. It suppresses the opponent
   leader effect for the current round only. If it cancels an active leader,
   the canceled leader is still consumed. If it suppresses a passive, scoring
   recalculates immediately for the current round.
9. `double_spies` is a passive for the entire game.
10. `shuffle_discards_into_decks` is unusable when both discard piles are empty.

## Rule Semantics For cCp19

### Row-Horn Leader Policy

Create a pure row-horn policy helper, analogous to cCp15's
`getWeatherPolicyBySeat`.

Recommended shape:

```ts
export type RowHornPolicyBySeat = Partial<
  Record<SeatId, Partial<Record<CatalogRow, boolean>>>
>;

export function getRowHornPolicyBySeat(
  state: MatchState,
  catalogLeaders: ReadonlyMap<string, CatalogLeaderDefinition> | readonly CatalogLeaderDefinition[],
): RowHornPolicyBySeat
```

Exact signatures may vary to fit existing local types, but the helper must:

- derive from leader source identity, not faction;
- map `double_close` to `close`;
- map `double_ranged` to `ranged`;
- map `double_siege` to `siege`;
- return no policy for missing leaders, unsupported ability IDs, or leaders not
  present in the supplied catalog;
- be exported from the core public surface if existing tests/import patterns
  make that appropriate.

Extend `calculateScores` input with an optional explicit
`rowHornPolicyBySeat` override for focused tests, similar to
`weatherPolicyBySeat`.

### Scoring Behavior

When a seat has a row-horn policy for a row:

- friendly non-hero units in that row are doubled at the normal horn stage;
- heroes are not doubled;
- the leader itself is not a board card and never appears as a horn source;
- existing special Commander's Horn on that row suppresses the leader horn;
- existing unit/hero `commanders_horn` source on that row suppresses the leader
  horn;
- horn effects do not stack;
- if a physical horn source applies, `CardScoreEntry.modifiers` should keep
  using `"commanders_horn"`;
- if only the leader policy applies, `CardScoreEntry.modifiers` should include a
  distinct `"leader_horn"` marker;
- the existing `multiple_horn_sources` diagnostic should only describe physical
  row horn sources. A suppressed leader policy should not create a new duplicate
  horn diagnostic.

Keep the existing modifier order intact as much as possible: weather, Tight
Bond, Morale Boost, then horn-style multiplication.

Any engine behavior that already calls `calculateScores` for effective strength
should inherit the row-horn policy. Do not add one-off strength calculations.

### Legal Moves And Commands

These leader abilities are passive:

- `getLeaderMove` must return no `use_leader` move for `double_siege`,
  `double_close`, or `double_ranged`.
- `executeCommand({ type: "use_leader" ... })` must not gain an executable
  branch for them.
- `leaderUsed` must remain `false`.
- No `leader_used` event should be emitted for these passives.

If the existing command path returns a structured unsupported-leader error for
manual `UseLeader` attempts, preserve that pattern and add a focused regression
test.

- normal score totals;

## Acceptance Criteria

- `double_siege`, `double_close`, and `double_ranged` metadata are
  `implemented`.
- The four official row-horn leader records are listed as implemented passive
  leaders in the official promotion manifest.
- Remaining placeholder leader ability IDs are exhaustive after cCp19.
- Scoring correctly applies the passive row horn to the owning seat's matching
  row.
- Physical row horn sources suppress the passive leader horn rather than
  stacking with it.
- Heroes remain immune as doubled receivers.
- Scorch and round-end winner/gem-loss logic use the row-horn effective
  strengths.
- Passive row-horn leaders emit no legal `use_leader` move and no
  `leader_used` event.
- `docs/gwent-rules.md`, `docs/leader-ability-matrix.md`,
  `docs/PROJECT_STATE.md`, and the cCp19 report are updated.
