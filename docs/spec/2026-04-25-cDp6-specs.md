# Implementation Spec: Cluster D, Phase 6 - Engine Shell Playability Polish

## Goal

Make the opt-in engine shell substantially easier to click through as a human-vs-AI game without changing the rule engine, switching the default route, or starting the simulation/ML slice.

After `cDp5`, the engine shell is functionally richer: the human can act through legal moves and the AI now uses `legal-heuristic-v0`. The main remaining problem is playability clarity. A human tester needs to understand whose turn it is, what action is expected, what the AI just did, which hand cards are playable, what targets are available for the selected card, when prompts block ordinary play, and how round/game progression should be driven.

This phase should turn the existing button-driven engine shell into a reliable smoke-test surface for current engine gameplay. It is still not the final spatial board UX.

## Architecture Position

Current state after `cDp5`:

- legacy UI remains the default route;
- engine UI is opt-in through `?engine=1` or `VITE_ENGINE_UI=1`;
- engine shell starts current Northern Realms vs Nilfgaard catalog presets;
- human actions use engine legal moves for mulligan, card play, leader use, prompt choice, pass, and round resolution;
- AI actions use `legal-heuristic-v0`, selected from engine legal moves;
- the UI can show raw-ish recent command/event types, but not enough context for human smoke testing;
- card play target actions exist, but they are noisy and not grouped by target kind;
- prompt, AI turn, and round-end states are technically represented, but not yet easy to read quickly;
- browser click-through is still mostly manual and under-documented.

Phase 6 should improve the shell around the engine. The engine remains the rule authority. React and Redux may format view models, but they must not compute legal outcomes.

## Scope

### 1. Add a shell view-model helper layer

Add or extend small pure helper modules under:

- `src/components/game/engine/`

Suggested files:

- `engineShellViewModels.ts`
- or focused additions to `playMoveHelpers.ts` if the file stays readable.

Keep these helpers React-free and Redux-free where practical. They should consume engine view models, legal moves, command history, events, phase/status, prompts, and seat labels, then return display-ready objects.

At minimum, provide helper coverage for:

- active turn/state summary;
- human action availability;
- selected-card target grouping;
- recent command/event summaries;
- round-history summary;
- hidden-info-safe card labels.

Do not put large formatting branches directly in `EngineGameManager.tsx` if they can be tested as helpers.

### 2. Add a clear match status and next-action banner

Replace the current dense header-only status text with a compact status banner or status strip that answers:

- current phase;
- round number;
- whose turn or whose prompt;
- adapter status/lock in human terms;
- what the human can do next.

Required state messages:

- idle/startup;
- human mulligan available;
- waiting for AI mulligan;
- human playing turn;
- AI playing turn;
- human prompt pending;
- AI prompt pending or resolving;
- both players passed / round ready to resolve;
- game end with winner or draw;
- last adapter error.

Examples of acceptable human-facing copy:

- `Mulligan: select up to 2 cards, then confirm.`
- `Your turn: choose a playable card, use leader, or pass.`
- `AI turn: legal-heuristic-v0 will act from legal moves.`
- `Prompt: choose one legal Medic option.`
- `Round end: both players passed. Resolve the round.`

Keep labels concise and stable on mobile.

### 3. Improve human hand affordances

The hand should make playable and unplayable cards easier to scan.

Required behavior:

- playable cards are visually distinct from disabled cards;
- selected card remains obvious;
- disabled cards get a safe reason where practical through title text or adjacent status, not rule recomputation;
- mulligan selection still supports up to two selected cards;
- prompt, AI turn, round end, game end, and passed-human states disable ordinary hand play.

Allowed reason categories:

- not your turn;
- prompt pending;
- card has no legal move;
- already passed;
- not in playing phase;
- mulligan already complete.

Do not compute card legality in React. Derive playability from legal moves and phase/status selectors.

### 4. Group selected-card target actions

The current target action panel can list many buttons without context. Improve it while keeping the interaction button-driven.

Required behavior:

- when no card is selected, show the count of playable cards and a short next action;
- when a card is selected, show the selected card name/kind/ability summary and group target buttons by target kind;
- support all existing target shapes:
  - `board_row`;
  - `row_horn`;
  - `weather`;
  - `card_instance`;
  - `none`;
- each target button must still dispatch the exact legal move target;
- target grouping and labels must be generated from legal moves and visible view-model data only.

Suggested target groups:

- `Rows`
- `Horn Slots`
- `Weather`
- `Cards`
- `Global`

Do not implement drag/drop in this phase.

### 5. Improve prompt rendering and blocking clarity

Prompt controls already come from legal `choose_prompt_option` moves. Make the prompt state more obvious and smoke-testable.

Required behavior:

- prompt panel must clearly say which seat owns the prompt;
- human-owned prompts show legal option buttons;
- AI-owned prompts do not expose hidden hand details and should either be resolved by the AI controller or show a clear "AI resolving prompt" state;
- ordinary play, leader, pass, and round resolution controls remain inactive while a human prompt is pending;
- prompt source/option labels should use visible card names when public or human-owned, and safe fallback labels otherwise.

Do not add rule-specific prompt execution in React.

### 6. Improve AI action visibility without changing AI strategy

`legal-heuristic-v0` should remain the same strategic policy unless a tiny bug fix is required. This phase is about showing the human what happened.

Required behavior:

- display the active AI policy id somewhere compactly;
- display the latest AI-applied command in human terms after it happens;
- display enough recent events to verify card played, prompt opened/resolved, leader used, weather cleared, pass, round resolved, game ended;
- never display AI hand card names, source IDs, or selected mulligan card IDs before they become public;
- AI `PlayCard` labels may resolve to the card name only if the card is now visible in a public zone such as board, weather, discard, or event payload that is already public.

Do not add AI timers for rule transitions. If a presentation delay is desired, defer it to a later spec.

### 7. Add round and game progression clarity

Round and game state should be easy to verify manually.

Required behavior:

- show current scores by row and total as today, but make round-end score comparison easier to read;
- show gems for both seats prominently;
- show a compact round history list after at least one round resolves;
- at round end, the Resolve Round action should include enough context to tell who is winning the round or if it is tied;
- at game end, show winner/draw and final gems.

Do not auto-resolve `round_end` in this phase.

### 8. Keep the shell opt-in and hidden-info safe

Preserve these invariants:

- `/` still renders the legacy default app;
- `/?engine=1` renders the engine shell;
- default human engine view shows AI hand count only;
- do not import or render `selectEngineDebugAiHandCards` in `EngineGameManager.tsx`;
- do not show AI deck order or AI hand card details;
- do not introduce localStorage persistence, deck editing, PvP, or simulation controls.

### 9. CSS/layout polish

Update `src/styles/components/engine-game.css` only as needed to support the shell changes.

Required layout constraints:

- no nested card-in-card panels;
- controls must not overlap on mobile;
- action buttons must wrap text cleanly;
- card names and target labels must not overflow their containers;
- use stable grid/flex sizing so selecting a card does not cause major layout jumps;
- keep the page utilitarian and game-focused, not a marketing-style landing page.

Do not spend time on final art direction. The shell can remain simple, but it should be usable.

### 10. Add tests

Add focused tests for the helper/view-model layer and any selector changes.

At minimum, cover:

- turn/status helper for human turn, AI turn, human prompt, round end, and game end;
- hand-card disabled reason helper for playable, not-your-turn, prompt-pending, no-legal-move, and passed states;
- selected-card target grouping covers `board_row`, `row_horn`, `weather`, `card_instance`, and `none`;
- command/event summary helper hides AI mulligan card IDs and AI hidden hand details;
- command/event summary can label public AI card play after the card is visible;
- prompt view helper labels human-owned prompts and safe fallback labels;
- round-history helper handles win/loss/draw rows;
- existing `playMoveHelpers` tests still pass;
- Redux adapter / AI policy tests still pass.

If a behavior is only practical to verify manually in the browser, document that in the report and explain why helper coverage is enough.

### 11. Manual smoke

Run a manual or semi-automated smoke pass for:

- `/`
- `/?engine=1&seed=dp6-smoke`

If `dp6-smoke` does not produce a useful card mix, choose a deterministic replacement seed and document it.

Required click-through checklist:

1. Open `/` and confirm the legacy default still renders.
2. Open engine shell with the documented seed.
3. Confirm the status banner says the correct phase/next action.
4. Complete human mulligan.
5. Confirm AI mulligan/action feedback appears without exposing hidden AI hand details.
6. Select a playable human card and confirm target groups/labels are understandable.
7. Play at least one human card through a grouped target action.
8. Let AI take at least one legal action and confirm recent action/event output describes it safely.
9. Exercise a non-basic target or prompt if the seed makes one available; otherwise document test coverage for those target shapes.
10. Pass both seats as needed, reach `round_end`, and confirm Resolve Round explains the score context.
11. Resolve the round and confirm round history updates.
12. Confirm no auto-new-game occurs.

Include route smoke with HTTP status or dev-server notes in the report.

## Out Of Scope

- Do not make the engine UI the default route.
- Do not replace or delete legacy `ReduxGameManager`.
- Do not add AI-vs-AI simulation or ML export.
- Do not build deck builder, Card Studio, persistence, PvP, replay viewer, or match setup.
- Do not change engine rules, scoring, legal move generation, or command semantics unless a small bug is discovered and explicitly documented.
- Do not strengthen or port legacy strategic AI in this phase.
- Do not use timers for rule transitions.
- Do not auto-resolve `round_end`.
- Do not add drag/drop or final spatial board UX.
- Do not expose AI hidden hand/deck details in the default human view.

## Acceptance Criteria

- Engine shell still renders only under explicit query/env flag.
- Legacy default app remains selected by default.
- Shell has a clear status/next-action banner for all major phases.
- Human hand clearly distinguishes playable, selected, and disabled cards.
- Disabled hand-card reasons are safe and derived from phase/status/legal moves.
- Selected-card target actions are grouped and still dispatch exact legal move targets.
- Prompt panel clearly distinguishes human-owned and AI-owned prompt states.
- Ordinary controls are inactive while a human prompt is pending.
- AI policy id and recent AI action feedback are visible.
- AI action feedback does not expose hidden AI hand or mulligan details.
- Round-end and game-end states are clearer and include score/gem context.
- Round history is displayed after round resolution.
- No engine UI/adapter/AI code imports legacy rule helpers, legacy `GameBoard`, legacy AI, or legacy game Redux.
- `docs/PROJECT_STATE.md` is updated.
- `audit/reports/2026-04-25-cDp6-report.md` exists.
- `npm run ci` passes before commit when intended files are staged.
- `git diff --check` passes.

## Notes For The Coding Instance

- Treat legal moves as the only executable action contract.
- Prefer pure helper functions with tests over expanding JSX branches.
- Use visible public zones for card labels. Do not render raw AI hand IDs or source IDs as a shortcut.
- The current `selectEngineDebugAiHandCards` selector is for tests/debugging; do not import it into the default shell.
- The AI controller may continue to act immediately. Make the aftermath legible rather than adding delay.
- Keep the shell button-driven. Grouped target buttons are enough for this phase.
- If a small core/selector bug blocks playability, fix it narrowly and document why it was necessary.
