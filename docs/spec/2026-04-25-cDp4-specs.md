# Implementation Spec: Cluster D, Phase 4 - Engine UI Leader, Prompt, and Special Action Polish

## Goal

Make the opt-in engine shell able to drive every currently executable human engine action through visible, legal-move-backed controls. Cluster D Phase 3 proved generic human `PlayCard` dispatch. Phase 4 should close the next usability gap: leader use, prompt readability, action diagnostics, and smoke coverage for Specials/Decoy/Medic-style flows.

This is still not the final board UX. Keep the implementation compact and button-driven where that is safer. The rule remains: React may choose among engine-provided legal actions, but it must not compute card rules.

## Architecture Position

Current engine shell behavior:

- legacy UI remains default;
- engine UI is opt-in through `?engine=1` or `VITE_ENGINE_UI=1`;
- engine shell starts current Northern Realms vs Nilfgaard catalog presets;
- human and scripted preview AI can mulligan;
- human can play cards by selecting engine legal `play_card` moves;
- scripted preview AI only mulligans zero and passes;
- pass, round resolution, prompts, and game end already flow through the engine lane;
- leader status is displayed, but there is no human `UseLeader` control.

Phase 4 should make the engine shell more honest and smoke-testable without switching the default app or migrating strategic AI.

## Scope

1. Add human leader action support in the engine shell.
   - Use `selectEngineLegalMovesForHuman` as the only source of executable leader actions.
   - Render a compact leader action near the human leader/status area or in the existing control panel.
   - If a human legal move exists with `move.kind === "use_leader"`, show a Use Leader action that dispatches exactly:
     ```ts
     dispatchEngineCommand({
       type: "UseLeader",
       seatId: humanSeat,
       target: move.target,
     })
     ```
   - Do not reconstruct or reinterpret the target.
   - Disable or hide leader use when it is not the human turn, the leader is already used, a prompt is pending, or no legal `use_leader` move exists.
   - Show leader readiness from engine state only.

2. Keep legal move generation consistent with command execution.
   - Verify that `getLegalMoves` does not advertise executable `use_leader` moves that `executeCommand` rejects only because the leader ability is still placeholder/planned.
   - If this mismatch exists, fix it in the core legal move layer.
   - Current executable leader scope is `clear_weather`.
   - Placeholder/planned leaders may still be visible in leader status, but they should not appear as executable legal command moves until their command implementation exists.
   - Direct `executeCommand` should still reject unsupported leader commands if called manually.

3. Improve leader action labels and diagnostics.
   - Add small UI helper coverage rather than embedding formatting in JSX.
   - Suggested helpers:
     - `getUseLeaderMoves(legalMoves)`;
     - `describeLeaderMove(move)`;
     - `shouldDisableLeaderAction(...)`.
   - Labels should include the leader name and ability name/status when available.
   - Do not add card-rule branching in React. Formatting metadata from legal moves or catalog view models is acceptable.

4. Use legal prompt moves for prompt controls.
   - When `match.pendingPrompt` exists, derive prompt action buttons from legal moves with `kind === "choose_prompt_option"` for the prompted seat.
   - If the prompt belongs to the human seat, use `selectEngineLegalMovesForHuman`.
   - If a future prompt belongs to the AI seat, do not expose hidden AI hand details; the scripted preview AI may remain unable to resolve non-trivial prompts in this phase unless the report documents the limitation.
   - Dispatch exact `ChoosePromptOption` commands from the legal move:
     ```ts
     dispatchEngineCommand({
       type: "ChoosePromptOption",
       seatId: move.seatId,
       promptId: move.promptId,
       optionId: move.optionId,
     })
     ```

5. Improve prompt readability without adding rule logic.
   - Show prompt kind, source card/ability when available, and option labels.
   - Resolve option card names/rows through engine view data or a small selector/helper, not by reading legacy state.
   - Prompt rendering should handle Medic revive chains and future prompt kinds generically.
   - Ordinary play, leader use, pass, and round resolution controls must remain inactive while a human prompt is pending, except prompt option buttons.

6. Improve action panel grouping.
   - Keep Phase 3's selected-card target action panel, but make the controls easier to scan:
     - leader action;
     - pass action;
     - selected card target actions;
     - prompt actions;
     - resolve round action.
   - Avoid nested card panels. This can be a compact toolbar/control section.
   - Preserve mobile-safe text wrapping and stable button sizes.

7. Preserve generic support for all current play target shapes.
   - Do not regress `board_row`, `row_horn`, `weather`, `card_instance`, or `none` target rendering.
   - Add coverage or manual smoke for at least two non-basic target types from the current catalog if practical:
     - weather or Clear Weather;
     - Commander Horn;
     - Decoy;
     - Scorch;
     - Medic prompt.
   - If deterministic browser smoke cannot hit all of these naturally, document which were verified by tests vs manual click-through.

8. Add minimal card/action diagnostics for smoke debugging.
   - Recent command/event output should be enough to confirm:
     - `leader_used`;
     - `weather_cleared`;
     - `prompt_opened`;
     - `prompt_resolved` or equivalent events emitted by the current engine.
   - Keep this compact. Do not build a full replay log.
   - Do not expose AI hidden hand card names in the default human view.

9. Keep scripted preview AI intentionally simple.
   - The preview AI remains:
     - zero-card mulligan;
     - pass when it owns the playing turn.
   - Do not make the preview AI use leaders or play cards.
   - Do not import or call `AIStrategyCoordinator`, `useReduxAI`, or legacy score helpers.

10. Add focused tests.
    - Extend helper tests for leader and prompt action helpers.
    - Extend Redux adapter tests for a human `UseLeader` flow:
      - start match;
      - complete mulligans;
      - ensure human can act;
      - put or play a weather card through legal engine commands if needed;
      - dispatch the legal human `UseLeader` command;
      - assert weather clears, `leaderUsed` becomes true, events record leader/weather behavior, and selection clears.
    - Add or update legal move tests so unsupported/placeholder leaders are not advertised as executable `use_leader` moves.
    - Add prompt-control test coverage for deriving prompt option commands from legal moves.

11. Add manual smoke coverage.
    - Run the shell at an engine URL. Prefer:
      - `http://127.0.0.1:5173/?engine=1&seed=dp4-smoke`
    - If that seed does not naturally produce useful special/leader coverage, pick and document a deterministic replacement seed.
    - Required smoke checklist:
      1. open `/` and confirm legacy default still renders;
      2. open engine shell with the documented seed;
      3. complete human and scripted AI mulligans;
      4. play at least one normal card through the Phase 3 target panel;
      5. play or observe one non-basic action target if available, such as weather, Horn, Decoy, Scorch, or Medic prompt;
      6. use the human leader if a legal implemented `use_leader` move is available;
      7. confirm prompt buttons, if any, come from legal prompt moves;
      8. pass and resolve the round;
      9. confirm no auto-new-game occurs.

12. Create the required implementation report:
    - `audit/reports/2026-04-25-cDp4-report.md`

## Out Of Scope

- Do not make the engine UI the default route.
- Do not replace or delete legacy `ReduxGameManager`.
- Do not migrate strategic AI.
- Do not add AI card play or AI leader use.
- Do not implement placeholder/planned leader abilities beyond preventing misleading legal moves.
- Do not build final drag/drop or fully spatial board UX.
- Do not build deck builder, Card Studio, PvP, AI-vs-AI simulation, ML export, persistence, or match replay.
- Do not introduce new card rules in React or Redux.
- Do not use timers for rule transitions.

## Acceptance Criteria

- Engine shell still renders only under explicit query/env flag.
- Legacy default app remains selected by default.
- Human can use an implemented legal leader move through the engine shell.
- Placeholder/planned leaders are not surfaced as executable legal `use_leader` moves.
- Leader use dispatches exact engine command target and updates state from engine selectors.
- Prompt controls are derived from legal `choose_prompt_option` moves.
- Prompt option dispatch uses exact legal move identifiers and does not reconstruct prompt identity from labels.
- Ordinary play/leader/pass controls are inactive while a human prompt is pending.
- Phase 3 card play target support does not regress.
- Scripted preview AI still only mulligans zero and passes.
- No new engine UI code imports legacy rule helpers, legacy `GameBoard`, legacy AI, or legacy game Redux.
- AI hand card details remain hidden in default human engine view.
- `npm test` passes.
- `npm run build` passes.
- `git diff --check` passes.

## Required Tests

At minimum, cover:

- Helper extracts human `use_leader` moves from legal moves.
- Helper describes implemented and non-executable/absent leader action states.
- Legal moves include human Clear Weather leader only when it is the current human turn, not used, and executable.
- Legal moves do not include placeholder/planned leader commands as executable moves.
- Redux adapter can dispatch a legal human `UseLeader` command and mark the leader used.
- Human leader Clear Weather clears active weather and emits expected events.
- Selection clears after successful `UseLeader`.
- Prompt helper maps legal `choose_prompt_option` moves into button view models.
- Prompt choice dispatch through Redux resolves a prompt without ordinary play being enabled during the prompt.
- Existing card-play helper tests for all target shapes still pass.
- Scripted preview AI still does not play cards or use leaders.

## Notes For The Coding Instance

- Treat legal moves as the UI contract. If the UI needs to know whether an action is executable, fix or enrich the legal move layer rather than adding rule guesses to React.
- The current human leader is Foltest Clear Weather, which is implemented. The current Nilfgaard leader is placeholder; that should be visible as status only, not as an executable command.
- Prefer extracting small helpers over making `EngineGameManager.tsx` grow another large block of inline formatting logic.
- Keep smoke diagnostics compact but useful. The implementation report should make it easy to tell whether leader use, prompt choice, and special targets were actually exercised.
