## Catalog Model Summary

The catalog module defines `CatalogCardSource`, `CatalogLeaderSource`, and `CatalogDeckPreset` as JSON-compatible source data. Cards carry stable `sourceId` values, declared `kind`, `strength`, legal `rows`, `abilities`, `tags`, `deckLimit`, `image`, and optional `linkedSourceIds`, `description`, and status metadata.

Runtime identity is modeled separately as `RuntimeCardIdentity`, where repeated deck copies share one `sourceId` but receive distinct `instanceId` values when instantiated later.

Ability metadata is exported as `CATALOG_ABILITY_METADATA` and `CATALOG_LEADER_ABILITY_METADATA`. Each entry has a status of `implemented`, `planned`, or `placeholder`; this is descriptive metadata only and does not implement resolver behavior.

## Audit Findings Touched

This phase only created foundation for later findings and did not directly fix gameplay defects. It prepares explicit identity and catalog structures for `R-010` side-deck support, `R-011` source/runtime identity separation, linked summon/muster card references, and removal of future card hardcoding.

## Risks / Follow-ups

- The new catalog does not migrate legacy card data yet; Phase 2 should map existing `src/data/cards/*` content into source packs.
- Ability status values reflect current audit understanding and should be adjusted when the pure engine resolver replaces legacy paths.
- Image validation checks string convention only; it does not verify file existence.
- Deck legality rules such as minimum unit count and maximum special count are intentionally deferred until deck-builder/deck-composition phases.
