## Simulation Architecture

`runHeadlessMatchSimulation` starts `sim:${seed}` with the current Northern Realms preset as `seat_a`, the current Nilfgaard preset as `seat_b`, and both seats set to `controllerKind: "ai"`.

Each policy-owned step calls `getLegalMoves`, builds the acting seat's `SeatObservation`, asks the configured `EnginePolicy` to select a legal move, converts the selected move with `commandFromLegalMove`, and applies it through `executeCommand`. Both seats default to `legal-heuristic-v0`.

## Acting Seat And Round-End Behavior

- Pending prompts act by `state.pendingPrompt.seatId`.
- Mulligan acts incomplete seats in fixed order: `seat_a`, then `seat_b`.
- Playing acts by `state.currentTurn`.
- `round_end` is auto-resolved only in the simulation path by selecting the legal `resolve_round_end` move for `seat_a`.
- `game_end` terminates the loop.

The runner defaults to `maxSteps: 300` and returns `max_steps_exceeded` if a policy does not reach `game_end`.

## Policy / Observation / Legal Move Flow

The simulation path reuses the cDp5 AI contract. Policies receive legal moves plus a hidden-info-disciplined seat observation. The runner does not construct commands directly except by converting the selected legal move, preserving the engine as the rule authority.

## Logs And Metrics Shape

Step logs include only step number, phase, round, seat, policy id, legal move count, chosen move id/kind, command type, and event types. They do not include full observations, full state snapshots, opponent hand arrays, or deck order.

Summary metrics include status, winner, rounds played, step/command/event counts, policies by seat, final gems/scores, pass count, rounds resolved, average legal moves, card plays by seat, prompt resolutions, leader uses, weather plays, and max-step limit.

`commandLog` is intentionally included for replay/debugging and may contain card instance IDs. It should not be treated as a hidden-info-safe ML dataset.

## Replay Helper Behavior

`replayHeadlessMatchCommands` starts the same current catalog AI-vs-AI config from the same seed, applies the command log through `executeCommand`, and returns the final `MatchState`. It throws if a command is invalid during replay.

Replay currently verifies final essentials in tests: phase, gems, and round history. It is not a replay viewer, intermediate-state hash checker, or cross-version compatibility layer.

## Deviations / Limits

- The fixed smoke seed naturally opens and resolves a Medic prompt; no synthetic prompt helper was needed.
- Step logs keep chosen move IDs because the spec allows them, but move IDs can contain card instance/source identifiers. This is acceptable for debugging, not for hidden-info-safe ML export.
- Replay validates final essentials, not every intermediate state.
- No batch runner, CLI, JSONL writer, random policy, action encoding, reward shaping, Python tooling, notebooks, or model training was added.
- No UI/browser behavior changed.

## Risks And Follow-Ups

- Non-termination risk: `maxSteps` prevents unbounded runs, but future policies can still consume the whole budget with legal no-progress choices. Batch simulation should track max-step rates by seed and policy.
- Prompt handling: the smoke seed covers a Medic prompt and `ChoosePromptOption`; broader prompt types and chained prompt-heavy seed suites remain future work.
- Hidden-info leakage in logs: compact `steps` avoid full observations and hand/deck arrays, but `commandLog`, events, and final state include replay identifiers. Do not use them as default ML training rows without redaction or observation hashing.
- Deterministic replay weakness: replay uses the current catalog config and command sequence only. It does not store catalog version hashes or assert intermediate state hashes.
- Policy failures: missing acting seat, thrown policy exceptions, no selected move, illegal selected moves, and conversion failures become structured `policy_failed` results. Future policies should add richer diagnostics and illegal-action metrics.
