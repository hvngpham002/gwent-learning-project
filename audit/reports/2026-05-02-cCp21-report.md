# Cluster C Phase 21 — Optimize Agile Rows Active Leader

- Spec: `docs/spec/2026-05-02-cCp21-specs.md`
- Branch: `dev`
- Date: 2026-05-02

## Summary

cCp21 implements the next narrowly scoped leader-rule tranche from the
cCp18 Leader Ability Matrix: `optimize_agile_rows` for
`scoiatael.francesca-findabair-hope-of-the-aen-seidhe` (Francesca
Findabair: Hope of the Aen Seidhe).

The post-cCp18 product decision §3 was refined in this phase to the
settled local contract: **auto-place all eligible own-board non-hero
Agile units to the common row that yields the highest acting-seat
score; if multiple rows tie for the best score, expose only the tied
best rows as legal `use_leader` moves through the existing cEp8
leader-choice path.** Pure no-op rows are never executable, and worse
movable rows are not offered when the current no-op row is uniquely
best, so the once-per-game leader is never consumed without changing
board state or lowering the acting seat's current score.

The implementation adds a focused pure helper module that returns a
deterministic plan derived from public board state and the central
`calculateScores` pipeline. `getLeaderMove` and `executeLeader` both
consume the helper — there is no per-call drift between legal-move
shape and command resolution. The leader emits `ability_triggered`,
zero-or-more `card_moved` events with the new
`reason === "leader_optimize_agile"`, `ability_resolved.moved`,
`leader_used`, and a turn-handoff event sequence on success, and
raises `EngineRuleError` without consuming the leader on rejection.

## Files Changed

Production:

- `src/game/core/leaderOptimizeAgile.ts` — **New.** Pure planning
  helper module. Exports `OptimizeAgileRowsOutcome`,
  `OptimizeAgileRowsEligibleCard`, `OptimizeAgileRowsCandidate`,
  `OptimizeAgileRowsPlan`, `PlanOptimizeAgileRowsInput`, and
  `planOptimizeAgileRows({ state, seatId, catalogCards,

## Behavior Changed

Engine pure helper:

- `planOptimizeAgileRows({ state, seatId, catalogCards,
  catalogLeaders })` is the new planning function. It is pure,
  deterministic, and clones state during simulation. The plan
  returns a `bestCandidates` set keyed on the highest scoring
  executable row(s); rows where no eligible card actually moves are
  filtered out so the once-per-game leader is never consumed
  without changing board state.

Engine legal moves:

- `getLeaderMove` now exposes one no-target `use_leader` move with
  `targetRequirement === "none"` when the leader is Hope of the Aen
  Seidhe and the helper outcome is `auto`; one
  `target.kind === "board_row"` move with
  `targetRequirement === "agile_row_choice"` per tied best row when
  the outcome is `choice`; and no `use_leader` move on
  `no_eligible` / `no_candidate_row` / `no_executable_row`. The
  emitted moves carry the new metadata fields `currentScore`,
  `bestScore`, `candidateRows`, plus the existing `targetRow`,
  `targetSeatId`, `targetCardIds`, `targetCount`, and
  `targetLabel`.

Engine command execution:

- `executeLeader` recomputes the plan, validates the target shape
  per the auto/choice contract, moves every eligible card in
  deterministic board order (`close → ranged → siege`, preserving
  unit order within each row), skips cards already on the chosen
  destination row (no `card_moved` event for them), uses the
  existing `moveCard` helper with the new
  `card_moved.reason "leader_optimize_agile"`, emits the standard
  `ability_triggered` / `ability_resolved.moved` / `leader_used`
  events, and hands off the turn. Rejection raises
  `EngineRuleError` and never mutates the input state.

## Deviations From The Spec

None of substance. Two notes:

1. **Helper output naming.** The spec recommended exact field
   names for `OptimizeAgileRowsPlan` such as `eligibleCardIds` and
   `candidates`. Both are present. I additionally exposed
   `eligibleCards` (a richer per-card view of `cardId`, `sourceId`,
   `currentRow`, `legalRows`) so tests and future consumers can
   debug exclusion decisions without re-running the catalog
   lookup. This is purely additive; the spec's recommended fields
   are still part of the export.

2. **Row label format.** The spec example mentioned `"Close
   Combat"` or `"Ranged Combat"`. The existing
   `displayMetadata.ts` `ROW_DISPLAY` map uses `"Close Combat"`,
   `"Ranged"`, `"Siege"`. To match the spec example exactly, I
   added a small `ROW_DISPLAY_LABEL` constant in `legalMoves.ts`
   (`"Close Combat"` / `"Ranged Combat"` / `"Siege Combat"`) and
   used it as `metadata.targetLabel`. The cEp8 leader-choice menu
   renders this label verbatim through the existing fallback
   chain, so the UI does not need a `getRowDisplay` round-trip.

The Foltest row-Scorch leader interaction with
`optimize_agile_rows` was not added as a dedicated test — Foltest
row-Scorch leaders run through `findUnitScorchRowTargets`, not
through `planOptimizeAgileRows`, so the cross-leader interaction
is degenerate. Existing cCp16 / cCp19 / cCp20 tests cover those
scoring-pipeline composition cases, and the new helper uses the
same `calculateScores` entrypoint, so no regression coverage gap
is introduced.

## Risks / Follow-Ups

- **`UseLeaderMove.metadata.targetRequirement` union grew.** The
  union now includes `"agile_row_choice"` alongside
  `"none"`, `"future_prompt"`, and `"deck_weather_source"`. Any
  consumer that hard-codes the union (e.g. an exhaustive `switch`)
  would need an update; the existing cEp8 leader-choice helper
  reads only `metadata.targetCardName`, `metadata.targetLabel`,
  `metadata.targetSourceId`, and `move.label`, so it is
  unaffected. No production UI consumer hard-codes the union
  today.
- **`card_moved.reason` union grew.** The new
  `"leader_optimize_agile"` movement reason is part of the typed
  event union. JSONL export and replay infrastructure inherits
  the new variant automatically through the typed union; no
  additional schema bump is needed because the reason field
  already accepts string-literal extensions.
- **Foltest row-Scorch composition not directly tested.** Foltest
  row-Scorch leaders are downstream of `optimize_agile_rows` only
  in the sense that moving Agile units onto a row could push that
  row over the 10-strength row-Scorch threshold for the opponent
  next turn. This is straightforward composition through the
  `calculateScores` pipeline and is not exercised by a focused
  test in cCp21. The existing cCp16 row-Scorch tests cover the
  threshold logic, and the cCp21 weather/horn/morale tests cover
  the planner's responsiveness to scoring-pipeline modifiers.
- **`cancel_leader` deferred (Tranche 4).** When `cancel_leader`
  lands, the simplest integration point is a guard inside
  `getLeaderMove` for the cancelled seat — short-circuiting before
  `planOptimizeAgileRows` is called. The execution path does not

## Reporting Notes For The Coding Agent

- **One-common-row plan.** The helper chose a single common
  destination row for every fire rather than per-card independent
  placement. Candidate rows are the intersection of every eligible
  card's legal source rows (so a future `agile` card that printed
  on `close + siege` would still produce a single common row when
  combined with other agiles). The bulk-move-to-one-row contract
  matches the spec's "one destination row" requirement and the
  catalog text "the row that yields the most strength."
- **Tied-row legal moves render through cEp8.** The cEp8
  leader-choice menu renders the tied-row options through the
  existing `metadata.targetLabel → move.label` fallback. No UI
  layout work was needed in cCp21. The view model's
  `buildLeaderActionOption` looks at `move.target.kind`,
  `move.target.sourceId`, `move.metadata.targetCardName`,
  `move.metadata.targetLabel`, `move.metadata.targetSourceId`, and
  `move.label`. For `target.kind === "board_row"` plus
  `metadata.targetLabel === "Close Combat"`, the helper produces a
  clean option with `label === "Close Combat"`. The
  `affectedRows` field stays empty (the existing
  `WEATHER_SOURCE_TO_ROWS` map only knows about weather sources),
  but that is cosmetic — the menu still renders the row name
  correctly.
- **No production catalog `agile + spy` or `agile + hero` source
  is broken.** Production catalog has `monsters.kayran` (hero +
  agile + morale_boost), `neutral.villentretenmerth` (hero +
  agile), and `skellige.cerys-an-craite` (hero + agile +
  morale_boost). All three are heroes and excluded as eligible.
  No production card combines `agile + spy`; the cCp21
  test-local fixture pins the engine's behavior for that
  hypothetical combination.
- **Both auto and tied-choice paths reject no-op consumption and
  worse moves.** The helper scores all candidate rows before no-op
  filtering. The `auto` outcome is only emitted when exactly one
  executable candidate ties the highest score across all candidate
  rows. The `choice` outcome is only emitted when more than one
  executable candidate ties that highest score. Single-agile-on-close
  with an equal ranged score emits `auto` because ranged actually
  moves the card; single-agile-on-close with a close-row Horn emits
  no leader move because the current no-op row is uniquely best and
  ranged would lower the score. The leader is never consumed without
  changing board state or by moving to a worse row.
