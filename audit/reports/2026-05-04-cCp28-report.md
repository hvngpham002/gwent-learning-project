## Reporting Notes

Per the spec's reporting requirements:

- **Final acknowledgement prompt shape:** `kind === "choose_option"`,
  `abilityId === "look_three_cards"`,
  `stage === "opponent_hand_reveal"`,
  `context: { revealedCardIds: [...] }`, exactly one option
  `{ optionId: "look-three-cards:acknowledge", label: "Continue",
  target: { kind: "none" } }`, `seatId === actingSeat`,
  `sourceCardId === leaderCardId`, `sourceId === leader.sourceId`.
- **Reveal selection algorithm and RNG advancement policy:** Hand
  length 1-3 reveals every card in opponent hand order without
  invoking RNG; `state.rng.state` is preserved. Hand length > 3
  builds a candidate set from the opponent's natural hand order,
  uses `createSeededRngFromState(state.rng.seed, state.rng.state)`
  + `shuffleWithRng(candidateCardIds, rng)`, takes the first three
  shuffled IDs as a `Set`, then returns the **intersection of the
  opponent's hand order with that set**. This means the visible
  reveal order is deterministic and equals opponent hand order even
  though the underlying selection is a shuffle. RNG advances to
  `rng.getState()` after the shuffle.
- **Exact manifest counts after cCp28:** `executableLeaderSourceIds`
  = 13, `implementedPassiveLeaderSourceIds` = 7,
  `implementedSetupLeaderSourceIds` = 1,
  `implementedLeaderSourceIds` = 21,
  `placeholderLeaderAbilityIds` = 1 (`cancel_leader`).
- **Whether any state field stores reveals after acknowledgement:**
  No. The reveal snapshot lives only in
  `state.pendingPrompt.context.revealedCardIds` while the
  acknowledgement prompt is open. After
  `ChoosePromptOption { optionId: "look-three-cards:acknowledge" }`
  resolves, `state.pendingPrompt` is cleared and the snapshot is
  gone. No `SeatState` or `MatchState` field stores the reveal. The
  test suite explicitly asserts this (no `revealedOpponentHand` or
  `revealedCards` field on `SeatState`, and no
  `revealedopponenthand` substring in any `MatchState` key).
- **How safe observation/export represents revealed cards:** AI seat
  observation surfaces revealed cards via the new
  `PendingPromptSummary.revealedCards` field on the prompt owner's
  observation only. Safe simulation export surfaces them via the
  new `SafePromptState.revealedCards` field with prompt-local refs
  `revealed_opponent_hand_<index>` (rather than raw opponent hand
  instance IDs) on the acting perspective only.
- **How non-acting observation/export was tested:**
  - `tests/game/coreLookThreeCardsLeader.test.ts` →
    `Hidden-info contract for look_three_cards (cCp28)` block
    asserts `getPromptMoves` returns the acknowledgement move only
    to the acting seat and `[]` to the opponent seat;
    `buildSeatObservation` returns `pendingPrompt: null` for the
    opponent perspective; `buildSafeSimulationObservation` returns
    `pendingPrompt: null` for the opponent perspective and
    serializes the opponent perspective without any of the
    revealed instance IDs.
  - `AI-owned look_three_cards prompts (cCp28)` block flips the
    leader to the AI seat and asserts the human seat sees no prompt
    moves and `pendingPrompt: null` in observation while the AI
    seat sees its own revealed cards.
- **UI behavior for human-owned vs AI-owned reveal prompts:**
  Human-owned reveal prompts open the new
  `authentic-look-three-cards-dialog` modal with the revealed cards
  visible and a single `Continue` acknowledgement button. AI-owned
  reveal prompts do not open the dialog (the

## Risks / Follow-ups

- **AI strategy timing remains unchanged.** `legal-heuristic-v0`
  does not strategically choose this leader because
  `isUsefulLeaderMove` only returns true for `clear_weather` with
  weather present. The AI policy will not call
  `Use Leader: Look Three Cards` in practice. The acting seat's
  observation now includes `revealedCards` for future heuristic
  upgrades, but cCp28 is intentionally policy-neutral — the
  acknowledgement option is the only legal move while the prompt
  is pending, so the heuristic acknowledges through the existing
  prompt-move selection path.
- **Browser smoke seed is not seed-iterated.** The new smoke uses a
  single deterministic seed (`ccp28-emperor-1`) plus a custom
  Nilfgaard deck large enough that the AI opponent has cards in
  hand after mulligan. If engine deck-shuffle behavior changes or
  the local-deck schema migrates, the seed may need to be
  revisited. The cEp8 smoke uses a small fixed seed list to find a
  deterministic state with at least two eligible weather sources;
  cCp28's leader is simpler (one no-target move when opponent hand
  ≥ 1) so a single seed suffices.
- **`opponent_hand_revealed` event payload carries cardIds /
  sourceIds.** This is intentional — the event log is internal/raw
  for replay and engine debugging. Hidden-info-safe summaries
  (`summarizeEvents`) render count-only labels and never the
  revealed names or source IDs. JSONL export and replay
  infrastructure inherit the new event variant automatically through
  the typed union; consumers that re-render the raw event log to
  hidden-info-safe surfaces should treat
  `opponent_hand_revealed.cardIds` / `sourceIds` as the
  acting-seat's observation only.
- **Pattern 6 (`cancel_leader`) is the next and final tranche
  member.** cCp29 should implement it. It cross-cuts every passive
  leader implemented in Tranches 1-3 (must check the suppression
  flag on every scoring tick) plus active leaders (must be locked
  out of `getLeaderMove` while suppression is in effect). cCp28's
  type extensions are additive on existing unions and do not
  conflict with the future cCp29 work.
- **No persistent observation state was introduced.** This is the
  intentional product decision (Settled §6). If a future feature
  needs persistent face-up opponent hand state (e.g. an Inspector-
  style debugging mode), it should be added under a separate state
  field with explicit hidden-info guards rather than through the
  cCp28 path.
