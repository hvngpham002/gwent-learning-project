# Cluster C Phase 15 Report — King Bran Weather Passive

This phase implements King Bran's leader passive `weather_half_penalty` as
the first **implemented passive** leader. It implements
`docs/spec/2026-05-01-cCp15-specs.md`.

## 1. Executive Summary

cCp14 closed the active executable weather-pulling-leader tranche. cCp15
finishes the weather rules tranche by wiring the already-existing scoring
policy concept (`WeatherPolicy = "king_bran"`) to the actual leader identity
in match state and propagating it to every score consumer that already calls
`calculateScores`.

King Bran is implemented as a passive: the engine derives his weather
policy from `state.seats[seatId].leaderSourceId` against the catalog
`CatalogLeaderSource` records, and `calculateScores` applies the half-loss
formula to his friendly non-hero units on weathered rows. He does **not**
generate a `use_leader` legal move, his `UseLeader` command is rejected,
`seat.leaderUsed` is never set, and no `leader_used` event fires.

The official-porting manifest now distinguishes three groups:
`executableLeaderSourceIds` (active commands, unchanged five from cCp14),
`implementedPassiveLeaderSourceIds` (`["skellige.king-bran"]`), and a
combined `implementedLeaderSourceIds`. `weather_half_penalty` is removed
from `placeholderLeaderAbilityIds`. Official-porting issue classification
(`leader_engine_gap`, `unsupportedLeaderAbilityCounts`) was already wired
to `metadata.status !== "implemented"` in cCp14, so it picks up the new
implemented-passive case automatically with no further engine changes.

No UI route, layout, AI policy, headless simulation engine logic, deck
builder layout, Card Studio layout, image asset, or Playwright smoke test
changes were required.

## 4. Behavior Changed

### 4.1 Implemented passive leader

`weather_half_penalty` ability metadata is now `implemented`. King Bran
(`skellige.king-bran`) is the first implemented **passive** leader.
Implemented metadata no longer means "produces an active executable
`use_leader` move"; it now means either an active executable command
(active leaders) or a passive engine rule (King Bran).

### 4.2 Derived weather policy

`getWeatherPolicyBySeat(state, catalogLeaders)` is a deterministic pure
helper that returns a `Partial<Record<SeatId, WeatherPolicy>>`. For each
seat with `leaderSourceId` matching a catalog leader whose ability is
`weather_half_penalty`, the seat is mapped to `"king_bran"`. Other seats
are unset. Missing leader catalog entries do not throw.

`calculateScores` integrates the derivation:

```ts
const derived = catalogLeaders ? getWeatherPolicyBySeat(state, catalogLeaders) : {};
const policyBySeat = { ...derived, ...(weatherPolicyBySeat ?? {}) };
```

Explicit `weatherPolicyBySeat` overrides the derived policy. Existing
direct tests that pass `weatherPolicyBySeat` keep working unchanged.

### 4.3 Score consumers automatically pick up King Bran

`calculateScores` already accepted `catalogLeaders`. Production callers
that already pass `catalogLeaders` inherit King Bran without further
changes:

- `src/store/selectors/engineSelectors.ts` (engine UI score breakdown,
  legal moves, leader/card view models, AI policy observation seat).
- `src/game/ai/seatObservation.ts`.
- `src/game/sim/exportObservation.ts`.
- `src/game/sim/metrics.ts`.
- `src/game/core/commands.ts` `determineRoundResult` (round resolution
  and gem loss).

### 4.4 Scorch paths now use leader context

The Special Scorch path in `commands.ts` and the row-scoped /
unit-source whole-board Scorch paths in `abilities.ts` previously called
`calculateScores({ state, catalogCards })` without leader context. cCp15
threads `catalogLeaders` through:

- `resolveSpecialScorch(... , catalogLeaders, ...)` in `commands.ts`;
- `resolveScorchRow(state, events, catalogCards, catalogLeaders, ...)` in
  `abilities.ts`;
- `resolveUnitScorchGlobal(state, events, catalogCards, catalogLeaders, ...)`
  in `abilities.ts`;
- `resolveCardAbilities(...)` and `resolvePromptOption(...)` accept
  `catalogLeaders?: readonly CatalogLeaderSource[]` and forward it to the
  Scorch resolvers and to nested `resolveCardAbilities` calls (e.g. after
  Medic prompt resolution → revived card abilities).

The optional shape preserves the existing seam test signatures that call
`resolveCardAbilities` without leader context (those callers just see
normal weather, which is correct for a non-King-Bran seat).

### 4.5 Legal moves and commands

`getLeaderMove` already returned `[]` for implemented abilities other than
`clear_weather` and the four cCp14 weather-pulling abilities. With
`weather_half_penalty` now implemented but not in either branch, King Bran
falls through to that `return []`. cCp15 added a doc comment at that
point explicitly describing the passive contract.

`UseLeader` for King Bran is rejected by `assertLegal` because no legal
move exists. `seat.leaderUsed` stays `false` for King Bran throughout
play; no `leader_used` event is ever emitted for the passive.

### 4.6 Manifest split

`OfficialLeaderPromotionManifest` now exposes:

- `executableLeaderSourceIds` (active commands, 5 leaders, unchanged from
  cCp14);
- `implementedPassiveLeaderSourceIds: ["skellige.king-bran"]`;
- `implementedLeaderSourceIds` (sorted union, 6 leaders);
- `placeholderLeaderAbilityIds` (no longer contains
  `weather_half_penalty`).

### 4.7 Official-porting classification

cCp14 already bound `leader_engine_gap` and
`unsupportedLeaderAbilityCounts` in `src/data/catalog/official/game8Mapping.ts`
to `metadata.status !== "implemented"`. With `weather_half_penalty`
promoted to implemented, the King Bran candidate automatically:

- drops out of `unsupportedLeaderAbilityCounts.weather_half_penalty`;
- no longer carries the `leader_engine_gap` issue;
- is no longer reported with `portingStatus === "needs_leader_rule"`.

No further changes were needed in `game8Mapping.ts`.

## 9. Reporting Notes

- **How is `weather_half_penalty` distinguished from active executable
  leader commands?** Two ways:
  1. At the manifest level, `OfficialLeaderPromotionManifest` splits
     active executable leaders (`executableLeaderSourceIds`, unchanged
     cCp14 five) from passive implemented leaders
     (`implementedPassiveLeaderSourceIds`, `["skellige.king-bran"]`).
     A combined `implementedLeaderSourceIds` is also exposed for code or
     tests that need to ask "is this leader's ability implemented at
     all?".
  2. At the engine level, `getLeaderMove` only generates a `use_leader`
     move for `clear_weather` (no-target) and the four cCp14
     weather-pulling abilities (`isWeatherLeaderAbility`). King Bran is
     implemented but neither, so it falls through to `return []` with an
     explicit "implemented passive" comment.
- **Which helper derives King Bran's weather policy from match state?**
  `getWeatherPolicyBySeat(state, catalogLeaders)` in
  `src/game/core/scoring.ts`. It iterates the `SEATS` constant, looks up
  each seat's `leaderSourceId` in a `Map<sourceId, leader>`, and assigns
  `"king_bran"` when the leader's `ability === "weather_half_penalty"`.
  Re-exported via `src/game/core/index.ts`.
- **Which score consumers were updated or inherited the policy
  automatically?** Inherited automatically through the new
  `calculateScores` derivation:
  - `src/store/selectors/engineSelectors.ts` (engine UI score breakdown,
    legal moves, AI observation seat, leader/card view models);
  - `src/game/ai/seatObservation.ts`;
  - `src/game/sim/exportObservation.ts`;
  - `src/game/sim/metrics.ts`;
  - `src/game/core/commands.ts` `determineRoundResult` (round resolution
    + gem loss).
  Updated explicitly to forward `catalogLeaders`:
  - `resolveSpecialScorch` in `src/game/core/commands.ts`;
  - `resolveScorchRow` and `resolveUnitScorchGlobal` in
    `src/game/core/abilities.ts`;
  - `resolveCardAbilities` and `resolvePromptOption` signatures
    (callers already had `catalogLeaders` in scope).
- **Did Scorch target selection use King Bran-adjusted effective
  strength?** Yes. The new test file covers all three Scorch shapes:
  - Special Scorch flips the target from an opponent ranged unit to the
    King Bran seat's own half-weathered close unit; without King Bran the
    opponent would be the highest target.
  - Row-scoped unit Scorch (`scorch_siege` via Schirru) crosses the
    threshold-of-10 only because King Bran-adjusted opposite siege total
    rises from 9 to 36 (3 catapults × Tight Bond × half-loss); without
    King Bran it would be `below_threshold`.
  - Unit-source whole-board Scorch (Clan Dimun Pirate) keeps Dimun alive
    because King Bran-adjusted Catapults become the tied highest targets;
    without King Bran Dimun would be the unique highest and self-scorch.
- **Did King Bran produce any legal `use_leader` move or consume
  `leaderUsed`?** No. The new test file pins both: `getLegalMoves` emits
  no `use_leader` move; `UseLeader` for King Bran throws and leaves state
  byte-equal; a normal Pass turn produces no `leader_used` event and
  leaves `leaderUsed === false`.
- **Did official-porting unsupported leader counts change as expected?**
  Yes. `unsupportedLeaderAbilityCounts.weather_half_penalty` is now
  undefined; the King Bran candidate no longer carries
  `leader_engine_gap` or `needs_leader_rule`. This was already wired in
  cCp14 to follow `metadata.status !== "implemented"`, so the cCp15
  metadata promotion automatically propagates.
- **Did any UI files need to change? If yes, why?** No production UI
  files changed. The only UI-test change was repointing
  `tests/components/gwent/authenticMatchViewModel.test.ts`'s
  placeholder-leader inspection sample from King Bran (now implemented)
  to Crach an Craite (still placeholder). No UI route, layout, CSS,
  image asset, or component logic was touched.
