## Summary

Promotes `random_medic` for `nilfgaard.emhyr-var-emreis-invader-of-the-north`
(Emhyr var Emreis: Invader of the North) from `placeholder` to
`implemented` as a **whole-match passive Medic mutation**, finishing
Tranche 2 of the leader ability matrix. Settles the cCp18 §C-3 conflict
in favor of the Medic-mutation reading per settled product decision §5;
the older "random Special replay from discard" wording is superseded.

While Invader of the North is the seat's leader, every non-hero Medic
source controlled by that seat
(`source.abilities.includes("medic") && source.kind !== "hero"`) revives
a random eligible non-hero Unit from that seat's own discard pile
(uniform over candidate cards through `createSeededRngFromState`;
deterministic row fallback `close → ranged → siege` for multi-row
targets) instead of opening a player-choice `medic_revive` prompt. Hero
Medic sources are unaffected and continue to use the normal prompt path.

## Behavior Changed

### Engine

- Non-hero Medic sources controlled by a seat with `random_medic` leader
  now revive a uniformly random eligible non-hero Unit from the acting
  seat's own discard pile instead of opening a `medic_revive` prompt.
  Eligibility filter: catalog source resolves, `source.kind === "unit"`,
  not a hero (`source.kind !== "hero"` is implied by `unit`), and at
  least one playable row (any of `close`/`ranged`/`siege`).
- Multi-row revived units use the deterministic canonical row fallback
  `close → ranged → siege`; the helper emits one candidate per card,
  not one per row.
- Spy placement still flips to the opponent board side and resolves
  Spy draw; `controller` becomes the acting seat with `owner` preserved.
- The chain recurses for random-revived non-hero Medics until the
  candidate set is empty; the final Medic emits
  `ability_resolved` / `outcome === "no_targets"` and the chain ends
  cleanly without a pending prompt.
- RNG advances only on a real multi-candidate roll. Zero or single
  candidate paths leave `state.rng.state` unchanged. Identical seed
  and pre-command state choose the same card and produce the same
  post-state.
- Hero Medic sources controlled by a seat with `random_medic` leader
  continue to use the existing `medic_revive` prompt (Hero immunity,
  §17.1).
- Ordinary Medic prompts for non-`random_medic` leaders remain
  unchanged.
- `random_medic` emits no `use_leader` legal move, never sets
  `seat.leaderUsed`, and never emits `leader_used`. Manual `UseLeader`
  attempts reject through the existing legal-move/unsupported-leader
  path without state mutation.
- New `ability_resolved` outcome `"random_revived_card"` distinguishes
  the random path from the prompt-based `"revived_card"`.

### Resolver factoring

- `placeMedicRevival` is a new internal helper inside
  `src/game/core/abilities.ts` that handles `controller` reset,
  `card_moved` with `reason === "medic_revive"`, `card_played`
  emission, the medic `ability_resolved` event, recursive
  `resolveCardAbilities`, and `settleMardroemeRow` after placement.
- Both `resolveMedic` (random path under `random_medic`) and
  `resolvePromptOption` (prompt-based `medic_revive` path) now call
  `placeMedicRevival` so Spy placement, controller reset,
  `card_played`, child ability resolution, and Mardroeme settlement
  cannot diverge between the two flows.
- The prompt-resolution path now emits `prompt_resolved` and clears
  `state.pendingPrompt` before invoking `placeMedicRevival`. The
  resulting event order for prompt Medic is:
  `prompt_resolved → card_moved (medic_revive) → card_played →
  ability_resolved (revived_card) → child resolveCardAbilities → ... →
  settleMardroemeRow`. The previous order interleaved `prompt_resolved`
  between `card_moved` and `card_played`; existing prompt Medic tests
  use `events.some(...)` matchers and continue to pass.

### Documentation

- `docs/gwent-rules.md` §17.12j is the new authoritative section for

- `docs/leader-ability-matrix.md` Pattern 8 is now the durable

## Deviations From Spec

None.

The spec suggested helper exports `hasRandomMedicPolicyForSeat`,
`getRandomMedicCandidates`, and `chooseRandomMedicCandidate` and noted
"the exact names may differ" — the implementation uses exactly those
names. The spec required `RandomMedicCandidate` shape with `cardId`,
`sourceId`, `row`, and `boardSeat`; the implementation matches. The
spec asked for a deterministic row fallback `close → ranged → siege`;
the implementation uses exactly that order via
`ROW_ORDER.find((row) => source.rows.includes(row))`. The spec asked
for RNG advance only on a real multi-candidate roll; the
`chooseRandomMedicCandidate` helper returns
`{ candidate: candidates[0], advanced: false }` for the single-candidate
case and only writes back `state.rng.state` when `advanced === true`.

The spec also asked for a shared placement helper to prevent prompt
and random flows from diverging on Spy placement, controller reset,
`card_played`, child ability resolution, and Mardroeme settlement;
this is delivered as an internal `placeMedicRevival` helper inside
`src/game/core/abilities.ts` (not exported from the new helper module
— the helper is intimate with the engine's `moveCard` /
`resolveCardAbilities` internals and would not be portable).

## Risks / Follow-ups

- **Catalog ID stays misleading.** `random_medic` was kept for
  backward catalog stability per settled decision §5; the description
  is rewritten but a future reader who only sees the ID without the
  description may assume Special replay. The §16 row, §17.12j section,
  and §C-3 explicitly call this out.
- **Event order shift in prompt Medic.** The shared
  `placeMedicRevival` helper changed the event order in the prompt
  path from `card_moved → prompt_resolved → card_played` to
  `prompt_resolved → card_moved → card_played`. Existing tests use
  `events.some(...)` matchers that do not assert ordering, so they
  continue to pass; if any external consumer of the simulation export
  depends on the prior ordering, it will need to be updated. No such
  consumer is known in-repo.
- **Hero Medic fixture is test-local.** No production hero source
  currently has the Medic ability; the hero-Medic exception is
  exercised through a test-local catalog augmentation. If a future
  catalog promotion adds a real hero Medic, the production path is
  already covered by the existing logic.
- **AI heuristic value.** `legal-heuristic-v0` does not score the
  Medic source any differently under Invader vs other leaders. This
  is correct because the random pick is deterministic from engine RNG
  (i.e. the value of firing the Medic source is decidable from public
  state once the RNG seed is fixed), but a future heuristic upgrade
  could weight Invader's discard-pool composition explicitly.

## Recommended Next Step

Tranche 2 is complete. Start Tranche 3 with one of:

1. **`draw_extra_card`** (Pattern 7, Francesca: Daisy of the Valley):
   setup-time event, no `use_leader` move, smallest engine surface
   area in this tranche. Implementing this first gives a complete
   cross-tranche test exercise (setup-time leaders must not produce a
   `use_leader` move and must not flip `leaderUsed`, mirroring King
   Bran).
2. **`discard_two_draw_one_from_deck`** (Pattern 3, Eredin: Destroyer
   of Worlds): the engine's first multi-stage prompt. Requires a new
   `pendingPrompt` shape (or extension of `choose_card`) and is a
   precondition for some Tranche 4 work. Higher complexity but more
   architectural value.

`docs/leader-ability-matrix.md` Tranche 3 (Setup-Time Event and
Multi-Step Prompt) recommends starting with `draw_extra_card` because
of its minimal scope and trivial implementation; the spec author can
make the final call.
