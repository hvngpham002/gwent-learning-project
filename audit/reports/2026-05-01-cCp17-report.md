# Cluster C Phase 17 Report — Generic Summon Discard Trigger

This phase implements the generic `summon` discard-trigger ability for unit
cards that replace themselves with a linked side-deck card when they are
discarded from the battlefield. It implements
`docs/spec/2026-05-01-cCp17-specs.md`.

## 1. Executive Summary

cCp11 introduced the centralised `resolveAvengerForCard` helper for
battlefield-removal replacement (Cow / Kambi) and made it the engine path used
by round cleanup, Special / unit Scorch, and Decoy bounce. cCp16 added the
Foltest row-Scorch leaders that share the same Avenger destruction loop. The
remaining cCp12/cCp13 linked-effect TODO around generic `summon` was the last
discard-trigger ability still tagged `planned`.

cCp17 closes that gap by promoting `summon` from `planned` to `implemented`
and adding a thin centralised resolver `resolveSummonForCard` that mirrors
`resolveAvengerForCard` in shape. The key rule distinction is preserved:

- **Summon** triggers only when the source is **discarded from a board row**
  (Special Scorch, unit row-Scorch, unit-source whole-board Scorch, the two
  Foltest row-Scorch leaders, and round cleanup).
- **Avenger** triggers on broader battlefield removal, including Decoy bounce
  per the existing project policy.

Movement uses a new `card_moved.reason "summon_replacement"` (distinct from
Avenger's `"avenger_summon"`) and `card_summoned.abilityId` is widened from
`"avenger"` to `"avenger" | "summon"`. The on-play emit was the previous
`ability_deferred { abilityId: "summon", reason: "planned_ability" }`; cCp17
replaces it with `ability_triggered` + `ability_resolved.armed_for_discard`,
mirroring Avenger's "armed" style without summoning anything on play.

The implementation is intentionally narrow:

- pure engine plus rule docs and focused tests;
- no UI route, layout, AI policy, simulation engine logic, deck-builder
  layout, Card Studio layout, image asset, JSONL boundary, simulation export
  schema, or Playwright smoke test changes;
- no new card sources, leader sources, or starter deck contents are promoted
  into the permanent catalog;
- official catalog promotion counts are unchanged;
- Cow / Kambi remain `avenger`, Bovine Defense Force remains ability-less,
  the combined Cow/Bovine staging candidate stays blocked by its
  `catalog_split_required:avenger` / `rule_gap:avenger` issues.

    ```ts
    export interface ResolveSummonInput {
      state: MatchState;
      events: GameEvent[];
      catalogLookup: ReadonlyMap<string, CatalogCardSource>;
      cardId: CardInstanceId;
      origin?: ZoneRef;
    }
    export type SummonResolutionOutcome =
      | "no_summon"
      | "missing_link"
      | "missing_replacement"
      | "missing_origin_row"
      | "summoned";
    export const resolveSummonForCard = (input: ResolveSummonInput): SummonResolutionOutcome => { ... };
    ```
    The helper:
    1. returns `"no_summon"` when the instance is missing or the source does
       not declare `summon`;
    2. emits `ability_resolved { abilityId: "summon", outcome: "missing_link" }`
       and returns `"missing_link"` if `linkedSourceIds[0]` is missing;
    3. searches the **controlling seat's** side deck for a card whose
       `sourceId` matches the linked replacement; emits
       `outcome: "missing_replacement"` and returns when absent;
    4. derives the origin board row from the explicit `origin` parameter (if
       it is `kind: "board_row"`) or from the instance's current zone (if it
       is still `kind: "board_row"`); emits `outcome: "missing_origin_row"`
       and returns when neither is available;
    5. moves the linked replacement from side deck to the resolved board row
       with `card_moved.reason: "summon_replacement"` and sets the
       replacement's `controller` to the source's controller;
    6. emits `card_summoned { abilityId: "summon" }` with the resolved seat
       and row;
    7. emits `ability_resolved { abilityId: "summon", outcome: "summoned" }`
       and returns `"summoned"`.
  - replaced the on-play `summon` branch in `resolveCardAbilities` from
    `emitDeferred(... "planned_ability")` to
    `emitTriggered + emitResolved(... "armed_for_discard")`, mirroring the
    Avenger "armed" style. Playing a Summon unit no longer emits any
    deferred event.
  - dropped the `summon` half of the local `emitDiscardTriggerDeferrals`
    helper; it is now a comment-only block. The two row-Scorch / unit-source
    whole-board Scorch resolvers (`resolveScorchRow` and
    `resolveUnitScorchGlobal`) drop the helper call (it had become a no-op)

    `resolveAvengerForCard`. Avenger's discard-trigger deferrals stay in

## 4. Behavior Changed

### 4.1 Summon ability metadata

`CATALOG_ABILITY_METADATA.summon.status` is now `"implemented"`. The
description distinguishes Summon (discard-from-board) from Avenger
(battlefield-removal including Decoy). No other ability metadata changes.

### 4.2 Pure resolver helper

`resolveSummonForCard` is exported from `src/game/core/abilities.ts` and
re-exported through `src/game/core/index.ts`. The shape mirrors
`resolveAvengerForCard` so test patterns and call sites stay symmetric:

| Behavior | resolveAvengerForCard | resolveSummonForCard |
|---|---|---|
| Source-ability gate | `"avenger"` | `"summon"` |
| Replacement source ID | `linkedSourceIds[0]` | `linkedSourceIds[0]` |
| Side-deck origin seat | source's `controller` | source's `controller` |
| Replacement seat | `destination.seat` if `board_row`, else current zone seat | `origin.seat` if `board_row`, else current zone seat |
| Replacement row | `destination.row` | `origin.row` |
| Replacement controller | source's `controller` | source's `controller` |
| Movement reason | `"avenger_summon"` | `"summon_replacement"` |
| Card-summoned ability | `"avenger"` | `"summon"` |
| Outcomes | `no_avenger` / `missing_link` / `missing_replacement` / `missing_origin_row` / `summoned` | `no_summon` / `missing_link` / `missing_replacement` / `missing_origin_row` / `summoned` |

### 4.3 On-play handling

Playing a `summon` unit no longer emits an `ability_deferred` event with
`reason: "planned_ability"`. The new emit is `ability_triggered` followed by
`ability_resolved { abilityId: "summon", outcome: "armed_for_discard" }`.
The card is on the board and ongoing scoring effects apply normally; the
side-deck replacement does not move on play.

### 4.4 Wired discard paths

The Summon resolver fires per destroyed target in:

1. **Special Scorch** — `resolveSpecialScorch` in `src/game/core/commands.ts`.
   Captures origin per target before `moveCard`, then calls Summon, then
   Avenger.
2. **Unit row-Scorch** (`scorch_close` / `scorch_range` / `scorch_siege`) —
   `resolveScorchRow` in `src/game/core/abilities.ts`. Same per-target loop.
3. **Unit-source whole-board Scorch** (Clan Dimun Pirate) —
   `resolveUnitScorchGlobal` in `src/game/core/abilities.ts`. Same per-target
   loop.
4. **Foltest row-Scorch leaders** (`scorch_range` / `scorch_siege`) —
   `executeLeader` row-Scorch leader branch in `src/game/core/commands.ts`.
   Same per-target loop.
5. **Round cleanup** — `sweepBattlefield` in `src/game/core/commands.ts`.
   Collects `summonOrigins` parallel to the existing `avengerOrigins`,
   moves cards to discard, emits the existing `board_swept` event, then
   resolves Summon origins, then Avenger origins. Replacements persist
   into the next round.

The helper is **not** wired into:

- Decoy bounce (Decoy returns the source to hand, not discard);
- Medic revive (revives from discard onto the board, not a discard);
- Card play / Muster placement / Skellige round-3 return (not discards);
- Monsters keep (the kept card is not discarded);
- Weather cleanup (weather cards do not have a `summon` ability path);
- Berserker / Mardroeme transformation (uses
  `removed_from_game`, not discard, and is a separate transform contract).

### 4.5 Event-trace effect

- New `card_moved.reason: "summon_replacement"` events appear when Summon
  successfully resolves.
- New `card_summoned { abilityId: "summon" }` events appear in the same
  scenarios.
- New `ability_resolved { abilityId: "summon", outcome: "summoned" }` events
  appear in the same scenarios.
- New `ability_resolved { abilityId: "summon", outcome: "armed_for_discard" }`
  events appear when a Summon source is played.
- New `ability_resolved { abilityId: "summon", outcome:
  "missing_link" | "missing_replacement" | "missing_origin_row" }` events
  appear when the linked replacement cannot be summoned; these are
  non-crashing.
- The previous `ability_deferred { abilityId: "summon", reason:
  "planned_ability" }` on-play event is gone.
- The previous `ability_deferred { abilityId: "summon", reason:
  "discard_trigger_pending" }` events around Scorch / round cleanup are gone.
- Avenger `ability_deferred` events around Scorch / round cleanup remain
  unchanged.

## 7. Deviations From Spec

None of substance. Two minor implementation choices worth noting:

- The spec listed the resolver as either an export from
  `src/game/core/abilities.ts` or a small new helper module. The
  implementation places it in `abilities.ts` next to `resolveAvengerForCard`
  to keep the symmetry — both helpers share the same internal `moveCard`
  primitive and are called from the same Scorch loops.
- The spec's wording suggested resolving Summon "before or after Avenger
  is acceptable if documented and deterministic. Prefer before Avenger only
  if it keeps event order clearer." Implementation chooses **Summon before
  Avenger** at every call site (per-target loops in Scorch / Foltest leader,
  and origin-resolution after the sweep in round cleanup). No catalog source
  declares both `summon` and `avenger`, so the ordering is currently
  observationally invisible; locking the order keeps the event log
  deterministic in case a future source ever combines both abilities.

`npm run ci` was not run end-to-end because the implementation files are
intentionally unstaged at report time. `npm run ci:browser` was not run
because no UI route / layout files changed.

## 8. Risks / Follow-Ups

- **No new live `summon` catalog source ships in cCp17.** The focused test
  file uses small file-local fixtures so the resolver is exercised
  end-to-end. When a real official Summon card lands, promote it through the
  staging pipeline; the helper does not need to change.
- **Replacements are not "played".** `resolveCardAbilities` is intentionally
  not invoked on the replacement, matching the Avenger contract in §17.10b.
  All current side-deck-only replacements (Bovine Defense Force, Hemdall,
  Vildkaarl, Young Vildkaarl) carry `abilities: ["none"]` or
  board-state-only abilities (`tight_bond` / `morale_boost`), so this is
  not a present blocker. If a future Summon source's replacement ever needs
  an on-summon ability, the helper will need to opt into
  `resolveCardAbilities` (mirror the same caveat documented for Hemdall
  under Avenger).
- **`muster_roach` is still tagged `planned`** even though
  `resolveMusterLike` resolves it. cCp13 added Roach copies to every preset
  containing Geralt or Cirilla; the resolver works through `linkedSourceIds`.
  Promoting `muster_roach` to `implemented` is out of cCp17 scope but is
  the next obvious metadata cleanup if/when scoped.
- **`it.todo` placeholder** in
  `tests/catalog/linkedAbilityInvariants.test.ts` — one remains, scoped to
  placeholder leader tutor/restore effects (Eredin / Emhyr / etc.). Promote
  it when the leader resolvers land.
- **AI policy** does not yet reason about Summon's "armed for discard"
  status. Empirically `legal-heuristic-v0` plays Summon units like any
  unit; the Summon trigger only fires when the source is later destroyed.
  AI strategy improvements remain deferred.

## 9. Reporting Notes (per spec §"Reporting Notes For The Coding Agent")

- **Which movement reasons trigger generic Summon?** A board-row → discard
  movement triggered by Special Scorch (`scorch_destroyed`), unit row-Scorch
  (`scorch_destroyed`), unit-source whole-board Scorch
  (`scorch_destroyed`), the Foltest row-Scorch leader path
  (`scorch_destroyed`), and round cleanup (`round_cleanup`).
- **Which movement reasons explicitly do not trigger it?** `decoy_return`
  (returns to hand), `medic_revive` (discard → board, not a discard),
  `ability_muster` (deck/hand → board), `mardroeme_transform` (board →
  `removed_from_game`), `skellige_return` (discard → board for round-3
  return), `weather_cleared` (weather cards have no `summon` path),
  `discard_after_effect` (used for special-card self-discard like Clear
  Weather, never a summon source), and `play_card`. Monsters keep is also
  a non-trigger because the kept card is not moved at all.
- **Where is the source origin row captured before movement?** At each
  per-target call site: `const origin: ZoneRef = { kind: "board_row",
  seat: target.seatId, row: target.row }` *before* `moveCard(...)`. In
  round cleanup, the `summonOrigins` collector captures
  `{ cardId, origin: { kind: "board_row", seat: seatId, row } }` inside the
  unit-iteration loop *before* `moveCard(... discard ..., "round_cleanup")`.
- **Does the replacement come from controller side deck or board-side
  side deck?** Controller side deck — `state.seats[instance.controller]
  .sideDeck`. The board-side discard preservation regression asserts this
  for a Spy-style placement.
- **Does the replacement land on controller side or occupied board side?**
  Occupied board side and row — the `origin` parameter is the source's
  *physical* board row, not the controller's mirrored row. This matches
  Avenger.
- **What happens on missing link, missing replacement, and missing origin
  row?** Each emits a structured `ability_resolved { abilityId: "summon",
  outcome: <reason> }` event and returns the matching union value. No state
  mutation, no crash. All three are pinned by dedicated helper tests.
- **Were any `ability_deferred` Summon events left? If yes, why?** No.
  cCp17 removes the on-play `ability_deferred { abilityId: "summon",
  reason: "planned_ability" }` emit and removes the `summon` half of the
  per-target `discard_trigger_pending` emits in
  `src/game/core/abilities.ts` and `src/game/core/commands.ts`. Avenger
  `ability_deferred` events stay unchanged.
- **Did Avenger Decoy / Scorch / round-cleanup behavior stay unchanged?**
  Yes. Three dedicated regressions in
  `tests/game/coreSummonDiscardTrigger.test.ts` plus the entire existing
  `tests/game/coreAvenger.test.ts` and `tests/game/coreLeaderRowScorch.test.ts`
  Avenger regressions confirm parity. `card_moved.reason "avenger_summon"`
  still fires for Avenger paths.
- **Did official-porting unsupported counts change?** Only in absence:
  `unsupportedAbilityCounts.summon` was already undefined (the staging data
  contains no `summon` candidates), so promoting the metadata to
  `implemented` does not flip a count from defined to undefined. No live
  Summon candidates were promoted into the permanent catalog in cCp17.
- **Did any UI files need to change?** No. The on-play emit shape change
  (`armed_for_discard` instead of `planned_ability`) is consumed by activity
  log code that displays whatever string the engine emits; existing
  UI-side ability display code reads `CATALOG_ABILITY_METADATA[ability]`
  for friendly names / glyphs and continues to work since the entry remained
  under the same `summon` key.
