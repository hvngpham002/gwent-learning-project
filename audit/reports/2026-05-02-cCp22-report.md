# Cluster C Phase 22 — Restore Discard To Hand Active Leader

- Spec: `docs/spec/2026-05-02-cCp22-specs.md`
- Branch: `dev`
- Date: 2026-05-02

## Summary

cCp22 implements the next narrowly scoped leader-rule tranche from
the cCp18 Leader Ability Matrix: `restore_discard_to_hand` for
`monsters.eredin-bringer-of-death` (Eredin: Bringer of Death). It is
the third Tranche 2 member to land, after cCp20's `double_spies`
whole-match passive and cCp21's `optimize_agile_rows` active one-shot
auto-place.

The implementation follows Pattern 4 from the cCp18 matrix exactly:
an active one-shot leader resolved through a single-step
`pendingPrompt.kind === "choose_card"` over the acting seat's own
discard pile. The settled local rule contract from the spec is
honored:

- own discard pile only;
- any card kind in own discard is eligible — units, heroes, specials,
  weather, and side-deck-only / generated cards that physically reach
  discard;
- heroes are eligible because the leader text says "card" without
  Medic's non-hero unit restriction;
- empty own discard emits no legal `use_leader` move;
- the leader is consumed only after a legal prompt option resolves;
- restored cards return to hand and do **not** trigger their abilities.

The preferred prompt-open transaction shape from the spec was
implemented: `UseLeader` opens the prompt without consuming the
leader, `currentTurn` stays on the acting seat while the prompt is
pending, and `seat.leaderUsed` flips to `true` (with `leader_used`
emitted and the turn handed off) only after `ChoosePromptOption`
resolves successfully. Rejection paths raise `EngineRuleError` and
never mutate input state.

  `GetRestoreDiscardCandidatesInput`, and the function
  `getRestoreDiscardCandidates({ state, seatId, catalogCards })`. The

## Behavior Changed

Engine pure helper:

- `getRestoreDiscardCandidates({ state, seatId, catalogCards })` is
  the new candidate function. Pure, deterministic, discard-order
  output, own discard only, skips missing instances / missing
  catalog sources safely, no hidden-info reads.

Engine legal moves:

- `getLeaderMove` now emits one no-target `use_leader` move with
  `targetRequirement === "future_prompt"` when the leader is Eredin:
  Bringer of Death and the helper returns at least one candidate.
  Empty discard emits no `use_leader` move. After the leader is
  consumed by a successful restore, no further `use_leader` move is
  emitted.
- `getPromptMoves` now builds the legal `choose_prompt_option`
  target with or without a `row` field depending on whether the
  prompt option's `target.row` is defined. Medic prompt options
  continue to emit `card_instance` targets with a `row`. cCp22
  restore prompt options emit `card_instance` targets without a
  `row`.

Engine command execution:

- `executeLeader`'s `restore_discard_to_hand` branch validates the
  target shape (rejects non-`none` targets), recomputes the
  candidate set, rejects empty-discard execution, then opens the
  `pendingPrompt` (`kind === "choose_card"`,
  `abilityId === "restore_discard_to_hand"`, one option per
  candidate) without consuming the leader. The transaction emits
  `ability_triggered` and `prompt_opened`, leaves
  `seat.leaderUsed === false`, emits no `leader_used`, moves no
  card, emits no `card_played`, and keeps `currentTurn` on the
  acting seat.
- `choosePromptOption` adds a stale-target check for the new prompt
  before mutation: if the chosen card is no longer in the acting
  seat's discard pile, throws `EngineRuleError(invalid_target)` and
  never consumes the leader. The pre-mutation check guarantees the
  rejection path never mutates input state.

## Deviations From The Spec

None of substance. Two notes:

1. **Stale-target check location.** The spec describes the stale-
   target rejection in the resolver section. I placed the check in
   `commands.choosePromptOption` (before cloning state) so the
   `EngineRuleError` is raised with no mutation. The `abilities.ts`
   resolver still includes a defensive early-return on stale state
   for safety when the resolver is invoked directly from a future
   test or caller, but it never throws — the engine entrypoint
   (`choosePromptOption`) is the single source of truth for the
   `EngineRuleError`. This matches the "rejection paths never
   consume the leader and never mutate input state" guarantee
   verbatim.

2. **`PendingPromptOption.target.row` made optional, not unionized.**
   The spec offered two paths: "make `row` optional, or replace the
   target with a small union that supports both Medic board-row
   options and discard-to-hand options." I chose the optional-field
   path because it (a) requires no changes to existing Medic prompt
   construction, (b) keeps `LegalMoveTarget` minimal, and (c)
   integrates cleanly with `getPromptMoves`'s emission of
   `card_instance` legal-move targets with or without `row` based
   on the source option. The legal-move target shape itself
   (`LegalMoveTarget.card_instance.row`) was already optional, so no
   second change was needed. UI consumers that destructure
   `target.row` already treat it as optional in
   `playMoveHelpers.describePlayTarget`.

## Risks / Follow-Ups

- **`PendingPromptOption.target.row` is now optional.** Any
  consumer that destructures `option.target.row` without an
  optional-field guard would break. Verified consumers: `seatObservation`
  uses `option.target.cardId` and `option.target.sourceId` only
  (does not read `row`); `legal-heuristic-v0` uses `option.optionId`
  and `option.targetStrength` only (does not read `row`); the
  cEp5.3 inspector reads `move.target` through the runtime
  `CardTargetViewModel` which already treats `row` as a free-form
  field; `playMoveHelpers.describePlayTarget` already gates on
  `target.row` truthiness; `matchViewModel.buildMedicPromptOptions`
  is only wired when `prompt.kind === "medic_revive"` and Medic
  prompts continue to set `row`. No production consumer was
  affected.
- **`card_moved.reason` union grew.** The new
  `"leader_restore_discard_to_hand"` movement reason is part of the
  typed event union. JSONL export and replay infrastructure
  inherits the new variant automatically through the typed union;
  no schema bump is needed. The `motionByCardId` helper in
  `AuthenticMatchScreen.tsx` does not register a special motion
  class for the restore reason — restored cards land in `hand`,
  which is handled by the default fallthrough; no visible motion
  regression because the `motion` value is only consulted for board
  / weather / discard surfaces.
- **`legal-heuristic-v0` AI policy.** The existing prompt policy
  ranks options by `option.targetStrength ?? 0` with deterministic
  moveId fallback. For restore prompts, `targetStrength` is the
  catalog source's printed strength (units / heroes carry their
  printed strength; specials and weather carry strength 0 by
  catalog convention). The AI will therefore prefer to restore the
  highest-strength card in its own discard pile, breaking ties by
  `moveId` (which is `restore:<cardId>`). This is acceptable for
  cCp22 — strategic AI tuning is explicitly out of scope. A future
  AI tranche could prefer specific kinds (e.g. weather > unit) by
  weighting `option.target.sourceId`'s catalog metadata.
- **Tranche 2 remaining members.** After cCp22, the three
  remaining Tranche 2 leaders are `shuffle_discards_into_decks`
  (Crach an Craite — bulk discard-to-deck recycle with deterministic
  seeded shuffle), `draw_opponent_discard` (Emhyr: The Relentless
  under settled §C-2 — single-step prompt over opponent's discard
  that can reuse the cCp22 helper signature with the seat flipped),
  and `random_medic` (Emhyr: Invader of the North under settled
  §5 — passive Medic mutation). The recommended next phase is
  `shuffle_discards_into_decks` because it introduces the engine's
  first runtime deck shuffle, a self-contained piece of new
  infrastructure that other Tranche 2 / 3 leaders may inherit.
- **Pre-existing lint warning.** `src/hooks/useReduxAI.ts` still
  reports a `react-hooks/exhaustive-deps` warning. Unrelated to
  cCp22; not surfaced to the cCp22 scope.
- **Coverage backfill candidates remain open.** Decoy + replay
  regression, Decoy + Mardroeme regression, ranged-row Berserker
  round-3 return, and Monsters keep with no eligible units are
  still untouched. cCp22 did not address them; they remain
  candidates for a focused regression phase.

## Reporting Notes For The Coding Agent

The spec asked for the report to call out specifically:

- **Whether the prompt opens without consuming the leader.** Yes.
  The `executeLeader` `restore_discard_to_hand` branch emits
  `ability_triggered` and `prompt_opened`, sets
  `state.pendingPrompt`, and returns the transaction without ever
  setting `seat.leaderUsed`, emitting `leader_used`, moving any
  discard card, emitting `card_played`, or calling `handoffTurn`.
  `currentTurn` stays on the acting seat while the prompt is
  pending. Verified by the
  `"emits ability_triggered and prompt_opened, does not move a
  card, does not set leaderUsed, does not emit leader_used, and
  keeps current turn"` test.
- **Whether `leader_used` fires only after prompt resolution.**
  Yes. The `leader_used` event is emitted only after a successful
  `ChoosePromptOption` resolves in `resolvePromptOption`'s new
  branch. Rejection paths (non-`none` `UseLeader` target, empty
  discard, wrong-seat prompt resolve, invalid option ID, stale
  target, missing prompt) never reach the `leader_used` emission
  and never set `seat.leaderUsed`. Verified across multiple
  rejection tests that snapshot the input state via
  `structuredClone` and assert no mutation.
- **Whether all card kinds in own discard are eligible, including
  heroes.** Yes. The helper imposes no kind filter — every
  card whose catalog source resolves is included. Heroes are
  eligible because the leader text says "card" without Medic's
  non-hero unit restriction. The test suite verifies units (Fiend),
  heroes (Geralt of Rivia), specials (Scorch), weather (Frost /
  Fog), and side-deck-only / generated cards (Vildkaarl) are all
  surfaced as eligible candidates, and that opponent discard is
  excluded.
- **Whether restored cards return to hand without resolving
  abilities.** Yes. `resolvePromptOption`'s new branch moves the
  chosen card from discard to hand and emits the standard event
  sequence, but does **not** call `resolveCardAbilities`. The test
  suite verifies that a restored Yennefer (Medic) does not fire
  Medic and does not open a Medic prompt, and that a restored
  Scorch (Special) does not fire — neither produces a
  `card_played` or `ability_triggered` event. Restored weather
  cards land in hand, not in the weather zone.
- **Whether AI-owned restore prompts remain hidden from the human
  UI.** Yes. `getPromptMoves` returns `[]` for any seat that does
  not own the prompt, so the human's `promptMoves` array is empty
  for AI-owned restore prompts and the `PromptPanel` renders only
  the "AI resolving prompt from legal moves." banner without any
  option labels. `summarizeEvents` only exposes
  `prompt.seatId` and `prompt.abilityId` for `prompt_opened`
  events — never option labels or card identities. Verified by
  the `"returns no prompt moves to the non-acting seat
  (hidden-info safety)"` test.
- **Whether any UI changes were required or whether the existing
  generic prompt panel handled the new prompt.** No UI changes
  were required. The existing generic `PromptPanel` (in
  `src/components/gwent/AuthenticMatchScreen.tsx`) renders
  `medicOptions.length > 0` only when `prompt.kind ===
  "medic_revive"`; for `choose_card` prompts with non-Medic
  ability IDs, it falls through to the plain labelled-button
  path that uses `option.label` (the human-readable
  `"Restore <card name> to hand"` strings). The
  `playMoveHelpers.describePlayTarget` `card_instance` branch
  already treated `target.row` as optional. `matchViewModel.buildLeaderActionViewModel`
  classifies the new single `use_leader` move as `kind: "single"`,
  so no choice-menu is rendered. No CSS, modal, or test-id
  changes were necessary.
