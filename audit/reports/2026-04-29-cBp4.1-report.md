# Cluster B Phase 4.1 Report - Official Combined-Card Data Cleanup

## Summary

Implemented cBp4.1 as a narrow data correction over the cBp4 catalog. Split the two combined Skellige Berserker scrape candidates into four real permanent catalog records with `linkedSourceIds[0]` pointing each base Berserker to its side-deck Vildkaarl replacement, tagged the replacement forms `side_deck_only`, removed the redundant cBp4-added `neutral.cow-bovine-defense-force` combined source, kept the legacy split `neutral.cow` (still planned `avenger`) and `neutral.bovine-defense-force` records intact, flagged the combined Cow/Bovine staging candidate with `catalog_split_required:avenger` plus `rule_gap:avenger`, rewrote `officialPromotionManifest` with `splitResolutions` and direct/deferred/catalog-source counts, and added narrow Deck Builder V1 guards so side-deck-only cards cannot enter a main deck.

No engine rules, leader abilities, AI policy, simulation/export schemas, or authentic UI styling were modified. No image binaries were downloaded or committed. Default Northern Realms and Nilfgaard deck presets are unchanged.

## Side-Deck-Only Guardrails

- Cards tagged `"side_deck_only"` (currently `skellige.vildkaarl` and `skellige.young-vildkaarl`) cannot be added to or imported into a Deck Builder V1 main deck.
- `isSideDeckOnlyCard(card)` is the single reusable predicate; it is used by `buildCardPool`, `getDeckBuilderAddState`, and `validateDeckPreset`.
- Reason code `"side_deck_only"` and visible reason `"side deck only"` come back from `getDeckBuilderAddState`.
- Validation error code `"side_deck_only_main_deck"` is emitted by `validateDeckPreset` for any `mainDeck` entry whose card has the tag.
- No side-deck editing UI was added. Non-empty `sideDeck` arrays remain unsupported in Deck Builder V1 (still gated by `side_deck_not_supported`).

## Deviations From Spec

- The spec recommended `OfficialPromotionSplitResolution` plus `directPromotedCandidateCount`, `promotedCatalogSourceCount`, and `deferredCandidateCount` fields without explicitly listing the array-shaped versions. The implementation also exposes `directPromotedCandidateIds` and `promotedCatalogSourceIds` arrays (and removes the cBp4-era `promotedCount`, `deferredCount`, and `promotedSourceIds` fields). The arrays make the manifest self-describing for tests without forcing them to recompute the lists at runtime; the spec's required test assertions about counts and IDs use these arrays.
- The cross-check test in `tests/data/officialCatalogPromotion.test.ts` continues to trust the manifest snapshot rather than re-applying a defer predicate to live staging. Once split catalog records land, the staging name-matching path can produce post-hoc `source_id_conflict` issues for duplicate-name physical cards (e.g. the two Dwarven Skirmishers from cBp4 and now the new Berserker/Vildkaarl pairs); the manifest is the authoritative classification taken at promotion time. The test still verifies that every accounted-for Game8 candidate appears in the staging exports.
- The split records use the spec's exact field values for `strength`, `rows`, `abilities`, `tags`, `deckLimit`, `image`, and `linkedSourceIds`. No additional `description` text was inferred for the new records.

## Risks / Follow-Ups

- Side-deck authoring UI and persistence are still unimplemented. The `side_deck_only` tag and validation error keep stale main-deck entries from leaking, but Berserker decks cannot be played end-to-end until side decks become editable and storable in Deck Builder.
- `neutral.cow` keeps the planned `avenger` ability. Until Avenger lands as an implemented engine rule, neither the legacy split Cow/Bovine pair nor the deferred combined candidate becomes promotion-clean. The combined candidate stays deferred in the manifest with explicit reasons.
- `scoiatael.elven-skirmisher` still references a missing image asset; the deterministic SVG fallback covers it.
- The staging matching is name-keyed and remains susceptible to post-hoc `source_id_conflict` issues when duplicate-name physical cards land in `currentCatalogCards`. The promotion manifest is authoritative for tests.
