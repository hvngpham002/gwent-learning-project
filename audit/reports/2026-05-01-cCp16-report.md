# Cluster C Phase 16 Report — Foltest Row-Scorch Leaders

This phase implements the two Foltest row-Scorch active leaders by wrapping
the existing cCp11 row-Scorch helper and reusing the cCp15 King-Bran-aware
scoring pipeline. It implements `docs/spec/2026-05-01-cCp16-specs.md`.

## 1. Executive Summary

cCp14 closed the active executable weather-pulling-leader tranche; cCp15
wired King Bran as the first implemented passive leader and made the row-
scoped Scorch path leader-aware. cCp16 finishes the row-Scorch leader
tranche by promoting `scorch_range` and `scorch_siege` from `placeholder`
to `implemented` and adding `northern-realms.foltest-son-of-medell` and
`northern-realms.foltest-the-steel-forged` to `executableLeaderSourceIds`.

The legal-move policy is intentionally narrow: each leader emits exactly
one no-target `use_leader` move only when the engine can actually destroy
at least one tied-highest non-hero unit on the mapped opponent row. Below-
threshold rows and Hero-only rows emit no move so the once-per-game leader
cannot no-op. Command execution mirrors the existing row-Scorch destruction
semantics — `card_moved.reason "scorch_destroyed"`, `summon`/`avenger`
discard-trigger deferrals, and Avenger replacement summons via
`resolveAvengerForCard`.

No UI route, layout, AI policy, headless simulation engine logic, deck
builder layout, Card Studio layout, image asset, JSONL boundary, or
Playwright smoke test changes were required.

## 4. Behavior Changed

### 4.1 Implemented active leaders

`scorch_range` and `scorch_siege` leader ability metadata are now
`implemented`. `northern-realms.foltest-son-of-medell` (`scorch_range`)
and `northern-realms.foltest-the-steel-forged` (`scorch_siege`) are now
the sixth and seventh active executable leaders. Active executable leader
ability metadata records grow from six (cCp14 + cCp15) to eight
(`clear_weather`, `play_frost`, `play_fog`, `play_rain`,
`play_any_weather`, `weather_half_penalty`, `scorch_range`,
`scorch_siege`).

### 4.2 Pure helper module

`src/game/core/leaderRowScorch.ts` is a small, pure, deterministic,
catalog-agnostic helper that exposes:

```ts
export type LeaderRowScorchAbility = "scorch_range" | "scorch_siege";
export const isLeaderRowScorchAbility: (ability: CatalogLeaderAbilityId) => ability is LeaderRowScorchAbility;
export const leaderRowScorchRowForAbility: (ability: LeaderRowScorchAbility) => CatalogRow;
```

The mapping is `scorch_range`→`"ranged"`, `scorch_siege`→`"siege"`.

### 4.3 Legal-move policy

`getLeaderMove` in `src/game/core/legalMoves.ts` adds a row-Scorch leader
branch positioned after `clear_weather` and weather-pulling leaders and
before the trailing passive-leader comment. The branch:

- looks up the row from the helper;
- runs `calculateScores({ state, catalogCards, catalogLeaders })` so the
  row totals use the full scoring pipeline (Weather, King Bran, Tight
  Bond, Morale Boost, Horn);
- runs `findUnitScorchRowTargets(breakdown, seatId, row)` (cCp11);
- if `result.outcome === "destroyed"` and `result.targets.length > 0`,
  emits exactly one `use_leader` move with `target: { kind: "none" }`,
  metadata for diagnostics (`targetRow`, `targetSeatId`, `targetCardIds`,
  `rowTotal`, `targetCount`, `targetLabel: "opponent <row>"`), and the
  standard `targetRequirement: "none"`;
- otherwise returns `[]`.

The existing leader gates (phase=playing, current-turn, not-passed, no
pending prompt, leader exists, leader not used, ability metadata
implemented) are unchanged. Below-threshold and Hero-only rows emit no
move so a once-per-game leader cannot be wasted.

### 4.4 Command execution

`executeLeader` in `src/game/core/commands.ts` adds a row-Scorch leader
branch positioned after the weather-pulling leader branch and before the
unsupported-ability throw. It:

1. Calls `assertLegal(input)` first (already done at function entry).
2. Keeps a defensive target-shape check for absent or `{ kind: "none" }`
   targets. In normal command dispatch, wrong target kinds are rejected by
   `assertLegal` before this branch mutates state.
3. Clones state via `cloneState`.
4. Computes the score breakdown on the cloned state with
   `calculateScores({ state, catalogCards, catalogLeaders })` so the
   recompute reflects any state mutations the same as `getLeaderMove`.
5. Runs `findUnitScorchRowTargets` against the mapped row.
6. Emits `ability_triggered { sourceId: leader.sourceId, cardId:
   leaderCardId, abilityId: leader.ability }`.
7. For each target: `moveCard(... { kind: "discard", seat: target.seatId
   }, "scorch_destroyed")`, emits `summon`/`avenger` discard-trigger
   deferrals (matching the existing per-target loop in
   `resolveSpecialScorch`), and runs `resolveAvengerForCard` with the
   target's origin row to keep Avenger replacement parity with Special
   Scorch and unit row-Scorch destruction.
8. Emits `scorch_resolved { sourceId, cardId: leaderCardId, abilityId:
   leader.ability, targetCardIds, outcome }`.
9. Emits `ability_resolved { sourceId, cardId: leaderCardId, abilityId:
   leader.ability, outcome }`.
10. Sets `seat.leaderUsed = true`.
11. Emits `leader_used { seatId, leaderCardId, abilityId:
    leader.ability }`.
12. Calls `handoffTurn(state, events, seatId)`.

Rejection paths:

- below-threshold row total is rejected at `assertLegal` (no legal
  `use_leader` move exists);
- Hero-only row is rejected at `assertLegal` (same reason);
- wrong target kind is rejected by `assertLegal` before state mutation
  (the branch also keeps a defensive no-target shape check);
- existing gates (wrong turn / wrong phase / passed seat / pending prompt
  / already-used leader) are rejected at `assertLegal` as before.

### 4.5 Manifest split

## 7. Deviations From Spec

None. The spec offered the option to extract a shared "destroy Scorch
targets and resolve discard triggers" helper between unit-row Scorch and
leader-row Scorch; cCp16 chose the safer narrow path of inlining the
per-target destruction loop in `executeLeader` (mirroring
`resolveSpecialScorch` exactly) so the existing
`resolveSpecialScorch` / `resolveScorchRow` / `resolveUnitScorchGlobal`
behaviors are byte-equal. Future refactors can extract a shared helper
once a third caller appears.

`npm run ci` was not run end-to-end because the implementation files are
intentionally unstaged at report time. `npm run ci:browser` was not run
because no UI route/layout files changed.

## 8. Risks / Follow-Ups

- **No new risks introduced.** Row-Scorch leader execution is a thin
  wrapper around the cCp11 row-Scorch helper plus the existing Special
  Scorch destruction template. Hidden-info boundaries, deterministic
  RNG, and existing legal-move semantics are unchanged.
- **`legal-heuristic-v0` AI policy** does not yet reason explicitly
  about the new row-Scorch leader moves. Empirically the move emerges
  as a no-target `use_leader` and the existing policy will pick it up
  through its general legal-move evaluation. AI strategy improvements
  remain deferred.
- **UI inspection.** `buildMatchLeaderInspection` reads ability metadata
  directly. After cCp16 it correctly reports both Foltest row-Scorch
  leaders as `implemented` rather than `placeholder`; the product UI
  does not need a new control because `use_leader` moves with
  `target: { kind: "none" }` already render through the existing
  no-target leader button path used by Clear Weather.
- **Active executable leader set is now seven leaders.** The next
  highest-impact leader work is the generic `summon` discard-trigger
  resolver (which would also let one of the two remaining `it.todo`s in
  `tests/catalog/linkedAbilityInvariants.test.ts` become an active
  assertion), followed by Eredin/Emhyr tutors and other placeholder
  leader abilities.
- **`it.todo` placeholders** in
  `tests/catalog/linkedAbilityInvariants.test.ts` carry over from cCp13
  and are scoped to the genuinely deferred generic `summon`
  discard-trigger resolver and remaining placeholder leader
  tutor/restore effects. Unaffected by cCp16.
