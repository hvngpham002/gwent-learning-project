  `UseLeader` raised `unsupported_command`. After cCp29 the leader
  emits a single no-target `use_leader` legal move on its own normal
  turn against a cancellable opponent, and the engine opens a
  reaction prompt automatically before any non-`cancel_leader`
  active leader resolves while the opposing seat owns an unused,

## Deviations From Spec

None of substance. Minor implementation refinements documented for
the record:

- **State field name.** The spec offered both `leaderCancelledRound`
  and `leaderSuppressedRound` as acceptable names. We chose
  **`leaderCancelledRound`** to match the historical ability ID
  (`cancel_leader`) and the event name (`leader_cancelled`). The
  helper API uses the more intuitive `isLeaderSuppressedThisRound`
  name, so the implementation reads `state.seats[seatId].leaderCancelledRound
  === state.round` inside that helper.
- **Event-order choice for reaction cancel.** The spec listed the
  recommended event sequence as `prompt_resolved → ability_triggered
  → leader_cancelled (reaction) → ability_resolved → leader_used
  (White Flame) → leader_used (cancelled target) → turn_set`. The
  implementation matches this exact order. Both `leader_used`
  events are emitted; tests lock the ordering.
- **Decline-replay refactor.** The spec recommended refactoring
  `executeLeader` so the actual leader effect can be resolved by an
  internal helper with a flag like `resolveLeaderEffect({
  allowCancelReaction: false })`. The implementation chose a simpler
  variant: a private `ExecuteLeaderOptions` interface with two
  optional booleans (`bypassCancelReaction`, `skipLegalCheck`) on
  `executeLeader` itself. This avoids extracting a new exported
  helper while still letting the decline path replay the attempted
  leader exactly once through the existing per-leader branches.
- **`PendingPromptContext.leaderCancel.target`** is `unknown`-typed
  to avoid a cycle between `PendingPromptContext` and
  `LegalMoveTarget`. The reaction-cancel resolver doesn't read
  `target` (it only consumes the cancelled leader); the
  reaction-decline resolver re-validates via the existing
  `executeLeader` per-leader branch, which already does its own
  target shape validation.
- **Cancellable opponent leaders.** The spec listed several active
  abilities; the implementation maintains a single
  `ACTIVE_CANCELLABLE_ABILITIES` set in `leaderCancel.ts` and a
  separate `PASSIVE_CANCELLABLE_ABILITIES` set. `cancel_leader`
  itself is intentionally excluded from both sets so cancel of
  cancel is forbidden (no recursive reaction window) and proactive
  cancel against another White Flame emits no legal move.
- **Score-card UI.** The spec accepted either `cancelled this round`
  or `suppressed this round` as the suggested label. We chose
  `cancelled this round` because the reaction prompt button label is
  `Cancel leader` and the event is `leader_cancelled`; consistency
  beats internal helper naming.
- **No new browser smoke.** The spec said `npm run ci:browser`
  should be run because cCp29 is expected to touch visible UI. We
  did run it (and all 20 existing smokes pass), but did not add a
  new smoke. The cCp29 UI work is intentionally minimal and reuses
  the existing generic `PromptPanel` path that earlier smokes
  already exercise. Adding a focused White Flame smoke that drives
  a deterministic reaction-prompt scenario is a low-risk follow-up.

## Risks / Follow-ups

- **AI proactive use of `cancel_leader` is unimplemented in
  practice.** `legal-heuristic-v0`'s `isUsefulLeaderMove` does not
  gate `cancel_leader` proactively, so the AI never calls White
  Flame on its own normal turn. The reaction-prompt path is the
  primary AI surface and is fully covered. A future heuristic
  upgrade (`legal-heuristic-v1`) could value proactive use against
  current-round opponent passives — this is a documented follow-up,
  not a regression.
- **Reaction decline-replay state-clone cost.** The decline path
  clones state twice (once for the prompt clear, once inside the
  recursive `executeLeader`). For all current leaders this is fast
  (small `MatchState`); a future leader with a large transient state
  may want to optimize the replay. The fast path covers all 13
  pre-existing active leaders.
- **The `PendingPromptContext.leaderCancel.target` field is
  `unknown`-typed.** This avoids a cycle with `LegalMoveTarget` but
  trades type safety for the decline-replay convenience. The
  decline path validates the shape inside `executeLeader`'s
  per-leader branches, so any malformed payload rejects with the
  existing `EngineRuleError` paths. Future schema work could
  introduce a structural-typed alternative.
- **No new browser smoke for the reaction prompt.** The decision
  was deliberate (the prompt renders through the existing generic
  `PromptPanel` which is already smoke-tested), but a focused
  cCp29 smoke that drives the cancel and decline paths
  end-to-end through the human-owned reaction prompt would harden
  the UI contract. Adding it is a low-risk follow-up.
- **Score-card data attribute is only consumed by CSS.** The new
  `data-leader-cancelled-this-round="true"` attribute is used by
  the new dashed-outline CSS rule and is implicitly testable
  through the existing `authentic-seat-{role}` test ID. A focused
  unit test on the score-card label / attribute would make the
  contract explicit; it is left as a follow-up because the
  observation / export tests already cover the flag plumbing.
- **Tranche 4 closes and the official leader matrix is complete.**
  No remaining leader implementation work is queued. The
  Recommended Next Step in `docs/PROJECT_STATE.md` lists the
  follow-up regression / audit candidates (cross-pattern
  suppression coverage, AI heuristic upgrade, Cluster E UI polish,
  documentation-only §C-5 / §C-6 / §C-8 / §C-10 catalog
  alignment).
