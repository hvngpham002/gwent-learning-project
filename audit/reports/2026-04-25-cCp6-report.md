# Cluster C Phase 6 Report - Ability Resolver V1

## Summary

Added a centralized pure ability resolver for the core command path. `PlayCard` now resolves immediate on-play abilities before turn handoff, prompt-producing Medic effects are stored in `MatchState.pendingPrompt`, and `ChoosePromptOption` resolves prompt choices through the same command transaction path.

## Resolver Architecture

The resolver entry points are `resolveCardAbilities` and `resolvePromptOption` in `src/game/core/abilities.ts`. Command execution still performs placement and zone movement first, then runs the resolver before turn handoff. If the resolver opens `state.pendingPrompt`, the acting seat keeps `currentTurn`; once a prompt option resolves and no chained prompt remains, the normal handoff occurs.

The resolver remains pure and catalog-driven. It receives `MatchState`, event buffer, catalog cards, acting seat, and source card instance ID. It does not import React, Redux, UI, AI, DOM APIs, timers, local storage, or `Math.random`.

## Prompt Model

`PendingPrompt` now stores `promptId`, `seatId`, `kind`, source card/source ID, `abilityId`, and structured options. Medic option IDs use `revive:{cardId}:{row}` and each option includes the target card instance, target source ID, and row, so UI/AI adapters do not need to recalculate hidden discard contents.

While a prompt is pending, `getLegalMoves` returns only prompt-option moves to the prompt seat. The opponent gets no moves, and pass/play/leader are suppressed. `ChoosePromptOption` validates pending prompt presence, seat ownership, prompt ID, and option ID.

## Event Model Changes

New resolver events include `ability_triggered`, `ability_resolved`, `ability_deferred` with `reason`, `card_drawn`, `prompt_opened`, `prompt_resolved`, and `deck_shuffled`. New movement reasons include `ability_draw`, `ability_muster`, and `medic_revive`.

## Scorch / Scoring Deferral

Special Scorch remains rejected with `unsupported_command`, matching the conservative Phase 5 policy. Unit Scorch Close places the unit, then emits `ability_deferred` with `reason: "requires_scoring"`. This avoids implementing a wrong printed-strength approximation before the effective scoring pipeline exists.

## Risks / Follow-ups

- Special Scorch and Unit Scorch still need the scoring pipeline before destructive resolution.
- Medic-revived Muster and Spy now route through the shared resolver, but broader future abilities still need side-deck and scoring support.
- Muster row-choice deferral exists for multi-row linked cards but has no prompt implementation yet.
- Non-Clear-Weather leader abilities remain rejected rather than prompt-driven.

## Recommended Next Step

Proceed to the scoring pipeline and then round/game resolver phases so Scorch, round cleanup, faction passives, and controller-owned discard routing can be completed against effective strength and authoritative end-of-round state.
