# Cluster D Phase 3 Report - Engine UI Human Card Play V1

## Summary

Added the first engine-backed human card-play slice to the opt-in engine shell. The legacy UI remains the default route, and the engine shell still renders only with `?engine=1` or `VITE_ENGINE_UI=1`.

During `playing`, human hand cards now become selectable only when `selectEngineLegalMovesForHuman` exposes at least one legal `play_card` move for that exact card. Selecting a playable card shows generic target action buttons from the legal move metadata, and clicking one dispatches the exact engine `PlayCard` command target. Board rows, weather, hand counts, discard counts, scores, prompts, and recent events continue to render from engine state/selectors after the command resolves.

Strategic AI and final spatial card-play UX remain explicitly out of scope. The scripted preview AI still only chooses zero mulligan cards and passes; it does not play cards.

## Card-Play UI Behavior Implemented

- Human hand cards are playable only during `playing`, only when the human can act, only when no prompt is open, and only when engine legal moves include a `play_card` move for that `instanceId`.
- Mulligan keeps Phase 2 multi-card selection behavior.
- Playing uses single-card selection via `selectedCardId`.
- Selecting a playable card shows one button per legal `play_card` move.
- Target buttons use `move.metadata.cardName`, `move.label`, and generic target descriptions for `board_row`, `row_horn`, `weather`, `card_instance`, and `none`.
- Clicking a target dispatches:
  - `type: "PlayCard"`
  - `seatId: humanSeat`
  - `cardId: move.sourceCardId`
  - `target: move.target`
- The UI does not reconstruct target objects from labels and does not patch local board or hand state after play.
- Ordinary play controls are hidden/inactive while `match.pendingPrompt` is present; generic prompt option rendering remains in place.
- Selection clears after successful engine commands through the adapter and is also cleared if a selected play card leaves the hand or loses legal targets.
- Recent command display now includes compact recent event names for smoke debugging.

## Legal-Move Helper Behavior

- `getPlayableCardIds(legalMoves)` returns the set of source card instance IDs from legal `play_card` moves only.
- `getPlayMovesForCard(legalMoves, cardId)` returns legal target actions for the selected card only.
- `describePlayTarget(move, cardLookup)` produces compact labels for board rows, row Horn slots, weather, card-instance targets, and no-target/global effects.
- `shouldDisableHandCard(...)` centralizes the UI gating for ordinary play without computing card rules.

## Deviations / Limits

- Browser click automation was not run because this repo does not currently include a browser automation harness. The required URL was served locally, and the click-flow state transitions were verified through focused helper and Redux adapter tests.
- The manual smoke verified one normal own board-row play through Redux. Other target shapes are covered at helper-display level and remain dispatched generically by the UI when legal moves expose them.
- No final drag/drop or fully spatial board UX was added. The UI is intentionally button-driven for this phase.
- No strategic AI migration, AI card play, leader UX expansion, deck builder, Card Studio, PvP, AI-vs-AI simulation, ML export, persistence, or new React/Redux card rules were added.
