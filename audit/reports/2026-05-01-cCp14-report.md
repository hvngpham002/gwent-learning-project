# Cluster C Phase 14 Report — Weather-Pulling Leader Commands

This phase implements the first tranche of non-clear-weather leader commands:
leaders that pull weather cards from the acting player's deck and play them
into the shared weather zone. It implements
`docs/spec/2026-05-01-cCp14-specs.md`.

## 1. Executive Summary

cCp13 closed the linked-Muster cleanup. cCp14 makes the four catalog
weather-pulling leaders executable through the pure engine while preserving
the existing pure-engine contract (legal moves enumerate executable actions,
`UseLeader` dispatches exact legal commands, the engine owns the rule outcome,
hidden information is never leaked through opponent state or raw deck instance
IDs).

The implemented leader abilities are:

- `play_fog` — Foltest: King of Temeria
- `play_frost` — Francesca Findabair: Pureblood Elf
- `play_rain` — Emhyr var Emreis: His Imperial Majesty
- `play_any_weather` — Eredin: King of the Wild Hunt

A new hidden-info-safe legal target shape `deck_card_source` is added: it
exposes only the catalog `sourceId` and the acting `seatId`, never a raw deck
card instance ID. Behaviour is constrained to deck instances only — copies in
hand, discard, weather zone, or board are not eligible. The leader is consumed
only after a successful pull. cCp14 explicitly does **not** shuffle the deck
after the search; that follows the spec's user-facing rule decision.

No UI route, layout, AI policy, headless simulation engine logic, or asset
changes were required.

## 4. Behavior Changed

### 4.1 Implemented leader abilities

Five leader abilities now have `implemented` metadata: `clear_weather`,
`play_frost`, `play_fog`, `play_rain`, `play_any_weather`. Five leader
records are now executable through the pure engine:

- `northern-realms.foltest-lord-commander-of-the-north` (clear_weather)
- `northern-realms.foltest-king-of-temeria` (play_fog)
- `nilfgaard.emhyr-var-emreis-his-imperial-majesty` (play_rain)
- `monsters.eredin-king-of-the-wild-hunt` (play_any_weather)
- `scoiatael.francesca-findabair-pureblood-elf` (play_frost)

### 4.2 Hidden-info-safe deck source target

The new `deck_card_source` target encodes only the catalog source ID and the
acting seat ID. Raw deck instance IDs are never exposed in legal moves,
simulation export rows, or UI helper labels. The simulation export typing/
encoding accept the new target without disturbing existing redaction
patterns.

### 4.3 Legal moves

`getLeaderMove` now:

- gates exclusively on `abilityMetadata.status === "implemented"` (other
  existing gates — turn, pass, leader used, prompt pending, phase — are
  unchanged);
- keeps the `clear_weather` `{ kind: "none" }`-target move unchanged
  (legal even when no weather is currently active, matching prior cBp5
  behaviour);
- emits at most one `use_leader` move for each single-weather leader iff the
  required source exists in the acting deck;
- emits one `use_leader` move per distinct eligible weather source ID for
  `play_any_weather` (no duplicate moves for multiple deck copies of the
  same source). Moves are sorted by the fixed Frost→Fog→Rain→Storm order so
  tests do not rely on object iteration order.

Move metadata adds optional `targetSourceId`, `targetCardName`, and
`targetLabel` fields plus the `deck_weather_source` discriminant on
`targetRequirement`.

### 4.4 Command execution

`executeLeader`:

- still validates through the legal-move path (`assertLegal`) before any
  state mutation;
- preserves the Clear Weather leader path verbatim;
- for weather-pulling leaders: validates the command target is
  `deck_card_source`, that `target.seatId === command.seatId`, and that the
  catalog source matches the leader ability via
  `isEligibleWeatherSourceForLeader`;
- selects the first matching deck instance in the current deck order
  (deterministic without shuffle);
- clones state, moves the card to the weather zone with
  `moveCard(..., "leader_weather")`, sets the moved card's controller to the
  acting seat, emits `card_played` (target = weather zone) and `leader_used`,
  marks `seat.leaderUsed = true`, and hands off the turn.

Rejected paths (each leaves the leader unconsumed):

- unsupported/placeholder leader abilities;
- wrong target kind (not `deck_card_source` for a weather-pulling leader);
- target seat mismatch;
- target source not eligible for the leader ability (including
  `neutral.clear-weather` for `play_any_weather`);
- target source absent from the acting deck;
- attempts while a prompt is pending (existing prompt guard);
- already-used leader (existing legal-move gate);
- wrong turn / wrong phase / passed seat (existing legal-move gates).

### 4.5 Official porting

`leader_engine_gap` is now driven by `metadata.status !== "implemented"`
rather than hard-coded equality with `clear_weather`. The four
weather-pulling leader candidates are no longer reported as
`leader_engine_gap`, no longer contribute to
`unsupportedLeaderAbilityCounts`, and no longer carry the
`needs_leader_rule` status.

### 4.6 Engine UI labelling

The diagnostic engine shell groups deck-pull leader moves under
`Deck Sources`. The play move helper labels deck targets as
`Deck <sourceId>`. The authentic match screen view model already filters
`play_card` moves only and is unaffected.

## 8. Risks / Follow-Ups

- **No new risks introduced.** The deck_card_source target is hidden-info
  safe; existing simulation export validation (`RAW_ID_PATTERN`,
  `RAW_ACTION_REF_PATTERN`) is unchanged and is unaffected by catalog source
  IDs.
- **`legal-heuristic-v0` policy** does not yet have weather-leader-aware
  preference. Empirically it falls through to its existing leader-handling
  branch and selects whichever weather-leader move is legal at action time.
  The cCp14 spec explicitly allows this; AI strategy work is deferred.
- **`play_any_weather` leader-choice UI polish** is deferred. The match
  table currently exposes the leader's "use" button as a single primary
  action; if the legal-moves list now contains multiple `play_any_weather`
  candidates, the product UI executes the first one. The spec lists this
  as a candidate next step (Cluster E / cCp14 follow-up) rather than a
  cCp14 requirement.
- **Deck shuffle after pull** is intentionally not introduced this phase
  per the user-facing rule decision in the spec. If a future rules audit
  changes this, it is a separate phase.
- **Two remaining `it.todo` linked-effect placeholders** (carry-over from
  cCp13) — generic `summon` discard-trigger resolver and placeholder leader
  tutor/restore effects — are unaffected by cCp14.

## 9. Reporting Notes

- **Which leader source IDs became executable?** Five total. The original
  `northern-realms.foltest-lord-commander-of-the-north` (clear_weather)
  remains executable. cCp14 adds `northern-realms.foltest-king-of-temeria`
  (play_fog), `nilfgaard.emhyr-var-emreis-his-imperial-majesty` (play_rain),
  `monsters.eredin-king-of-the-wild-hunt` (play_any_weather), and
  `scoiatael.francesca-findabair-pureblood-elf` (play_frost).
- **What target shape was used for deck-weather leader commands?**
  `{ kind: "deck_card_source"; seatId: SeatId; sourceId: string }` — only
  catalog source IDs and the acting seat ID are exposed; no raw deck card
  instance IDs.
- **Does `play_any_weather` expose multiple legal moves when multiple
  weather source IDs are in deck?** Yes. One `use_leader` move per distinct
  eligible source ID, sorted Frost→Fog→Rain→Storm. Multiple deck copies of
  the same source produce a single move; `play_any_weather` cannot choose
  Clear Weather.
- **How does the command choose a physical card when multiple copies of the
  same weather source are in deck?** It selects the first matching card
  instance in the current deck order. cCp14 does not shuffle the remaining
  deck after the search.
- **Were raw deck card instance IDs exposed in legal moves or simulation
  exports?** No. The legal target shape is `(seatId, sourceId)` only; the
  `SafeActionTargetRef` deck target mirrors that with
  `(side: "own", sourceId)`. The existing simulation export validation
  patterns are unchanged.
- **Did official-porting unsupported leader counts change as expected?**
  Yes. `play_fog`, `play_frost`, `play_rain`, and `play_any_weather` are no
  longer counted in `unsupportedLeaderAbilityCounts`. Remaining placeholder
  abilities (`double_close`, `cancel_leader`, `look_three_cards`, etc.) are
  still counted.
- **Did any UI files need to change? If yes, why?** Two diagnostic-shell
  helpers were touched:
  - `src/components/game/engine/playMoveHelpers.ts` adds a label branch for
    `deck_card_source` so `describePlayTarget` keeps its exhaustive coverage.
